# Spec: 측정이 «어느 SW 빌드에서» 나왔는지 기록한다

Author: younhs21-dexter / collaborator (초안: Claude 세션)
Date: 2026-09-09
Status: draft
Slug: sample-software-version
Intent: `intent/sample-software-version/intent.md`

⚠️ **이 spec 은 미완이다.** intent §Open questions 다섯 중 셋(Q1 누가 넣는가 ·
Q2 형태 · Q4 무효 규칙)이 답을 받기 전에는 §1 요구사항을 확정할 수 없다.
여기 적힌 것은 «답이 어떻게 나오든 참인 것»과 «답에 따라 갈라지는 지점»이다.

## 1. 요구사항 (잠정)

- **R1.** `samples` 가 「받았을 때」 SW 버전을 담는다.
- **R2.** `measurement_attempts` 가 「잴 때」 SW 버전을 담는다.
- **R3.** 둘 다 nullable 이고, 값이 없으면 화면이 **「미기재」로 표시**한다 —
  빈칸이 아니라. 없는 것과 안 적은 것은 다르다.
- **R4.** 커버리지·진행률 읽기가 그 값을 그대로 통과시킨다(집계하지 않는다).
- **R5.** 「시료의 버전 ≠ 측정의 버전」인 건수를 셀 수 있다.
- **R6.** 기존 행은 깨지지 않는다. 이미 쌓인 측정은 전부 「미기재」다.

## 2. 범위 밖 (Non-goals)

- **무효 판정을 자동으로 하지 않는다.** 「빌드가 바뀌었으니 이 조건들은 다시」는
  도메인 규칙이고 아직 없다(§Q4). 이 spec 은 **사실을 기록**할 뿐이다.
- **HW 리비전을 담지 않는다** — §Q3 의 답이 「필요하다」면 이 의도는 폐기하고
  「EUT 형상」이라는 더 큰 의도로 다시 연다. 칸을 하나씩 늘려 가면 그 순간마다
  마이그레이션이 하나씩 붙는다.
- **소급 채우기를 하지 않는다**(§Q5).
- 버전 «비교» 로직(1.2.3 < 1.2.4)을 만들지 않는다. 문자열로 저장하고, 순서가
  필요해지면 그때 별건이다.

## 3. 설계 결정과 근거

| # | 결정 | 버린 대안 | 근거 |
|---|---|---|---|
| D1 | 칸을 **두 곳**에 둔다(시료 · 측정) | 시료에만 | 펌웨어는 «시료가 그대로인 채로» 바뀐다. 같은 SN 에 새 빌드를 올리는 것이 일상이므로 시료 속성으로만 두면 어제 잰 것과 오늘 잰 것이 같은 버전으로 보인다. 둘이 다른 것 자체가 정보다(R5) |
| D2 | 전용 칼럼 | `result_json` / `provenance_json` 에 넣기 | JSON 자루는 조회도 대조도 「비어 있음」의 검출도 안 된다 — 있어도 없는 것과 구별되지 않는다 |
| D3 | nullable 시작 | NOT NULL + 기본값 | 기본값을 주면 「미기재」가 «어떤 값»으로 둔갑한다. 성적서의 근거가 될 칸에서 그것은 최악이다 |
| D4 | 문자열로 저장 | 구조화(major/minor/patch) | §Q2 가 답을 받기 전에 구조를 정하면 그 구조가 답을 강제한다. ⚠️ 대신 형태 검증을 «어디서» 할지는 정해야 한다 — 아무 데서도 안 하면 이 칸은 오타 수집기가 된다 |
| D5 | 무효 판정은 하지 않고 **사실만** 기록 | 자동 무효화 | 규칙이 없다(§Q4). 규칙 없이 자동화하면 멀쩡한 측정을 지우거나 낡은 측정을 통과시킨다 |

## 4. 영향받는 경계

- **레인**: platform + contracts + ⚠️ **provider 비공개 레포**.
  측정을 실제로 보내는 쪽이 값을 실어 보내지 않으면 `measurement_attempts` 의
  칸은 영원히 비어 있다. **이 레포에서 끝낼 수 없는 의도다.**
- **DB**: ⚠️ **마이그레이션 필요.** `migrations/` 는 CODEOWNERS §③
  「되돌릴 수 없는 것」이고 적용은 사람에게 따로 묻는다.
  - `samples` + 1 칼럼
  - `measurement_attempts` + 1 칼럼
  - `coverage_by_condition_hash` 는 **materialized view** 라 재생성이 필요하다
    (그 뷰가 그 칸을 노출하려면). ⚠️ 001 의 주석이 경고한다 — 뷰의 칼럼 순서는
    APPEND-ONLY 이고, 중간 삽입은 배포된 DB 를 깬다.
- **API 계약**: 인제스트(쓰기)와 커버리지(읽기) 양쪽의 OpenAPI 표면이 바뀐다.
  커널 태그가 먼저.
- **프론트엔드**: 시료 화면 + 커버리지/항목 화면에 칸 하나씩. 시각 골든 바뀜.
- **provider 비공개 레포**: **닿는다.**

**Debt-Accepted-By**: (없음)

## 5. 정책 확인

- **인증/RBAC**: 새 권한 없음. 시료 쓰기는 기존 시료 권한, 측정 인제스트는 기존
  인제스트 권한을 그대로 쓴다.
- **개인정보**: 새 PII 없음. 빌드 문자열은 기기 정보다.
  ⚠️ 다만 빌드 문자열에 내부 브랜치명·개발자 이름이 들어가는 조직이 있다
  (`1.2.3-hyunsik-fix`). 그런 값이 성적서에 실릴 수 있다는 것은 §Q2 의 형태
  결정에서 함께 판단해야 한다.
- **오프라인 동작**: 챔버 PC 가 EUT 에서 버전을 못 읽어도 측정은 계속되고,
  중앙에는 「미기재」로 도착한다. 이 칸이 측정을 막지 않는다.

## 6. 성공 판정

| 요구 | 어떻게 관측하나 |
|---|---|
| R1·R2 | 마이그레이션 후 `\d samples` / `\d measurement_attempts` 에 칸이 있다 |
| R3 | 값이 NULL 인 행이 화면에서 「미기재」로 나온다(빈 문자열 아님) |
| R4 | 커버리지 응답에 그 값이 verbatim 으로 실린다 |
| R5 | `시료 버전 ≠ 측정 버전` 건수를 세는 질의가 돈다 |
| R6 | 마이그레이션 전후로 기존 읽기의 응답이 «칸 하나 늘어난 것 외에» 같다 |
