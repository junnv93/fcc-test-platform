# Intent: 서버가 «버티는지»를 화면이 물을 수 있어야 한다 — 서버 헬스 읽기

Author: younhs21-dexter
Date: 2026-09-09
Status: draft
Slug: server-health-reads

> 🔴 이 문서는 «계약 요청»이다. 화면은 이미 서 있고(`/diagnostics`), 그 화면의
> 절반이 「읽기 없음」으로 비어 있다. 여기 적힌 것은 그 빈칸을 채우는 데 필요한
> 읽기 목록이며, 레포 소유자와의 대화를 위한 안건이다.

## Problem

`/diagnostics` 는 두 파트다 — **서버(중앙)** 와 **그 서버에 붙은 시험 구성(TC)**.
TC 쪽은 오늘 이미 답한다: 노드별 연결 · 하트비트 · `mode_verdict` · `last_error`
가 챔버 가용성 읽기에 이미 실려 있었고, 화면은 그것을 모아 보여 준다.

**서버 쪽은 거의 아무것도 답하지 못한다.** 오늘 가진 것은 둘뿐이다:

| 있는 것 | 어디서 |
|---|---|
| 서비스 도달 여부 (platform / headless / session) | 각 클라이언트 호출의 성공·실패 |
| 브라우저 ↔ 서비스 왕복 시간 | `performance.now()` 로 감싼 것 — 새 계약 아님 |

그래서 「서버가 느리다」는 말이 들어왔을 때 이 화면이 답할 수 있는 것은
「붙기는 한다」까지다. 그 다음 질문 — 메모리가 눌렸나, DB 커넥션이 말랐나,
에러율이 올랐나 — 은 전부 서버에 SSH 로 들어가야 알 수 있다.

⚠️ 그리고 이것은 «인과»의 문제다. 서버가 눌리면 하트비트 처리가 늦어지고, 그러면
TC 가 「오프라인」으로 보인다. 지금 화면은 결과(TC 오프라인)는 보여 주는데 원인
(서버 부하)은 못 보여 준다 — 그래서 같은 화면에 두 파트를 둔 것이고, 한쪽이 비어
있는 한 그 배치가 값을 못 낸다.

## Proposed outcome

「서버가 이상한가」에 화면이 답한다. 답이 「아니오」일 때 그것이 화면에서 «보이는»
것이 절반의 값이다 — 그때 사람은 TC 쪽을 보러 간다.

## Affected users and systems

- **사람**: 개발자(주 대상) · 플랫폼 운영자
- **레인**: 읽기가 어디에 살지에 따라 갈린다(→ §Open questions Q1).
  중앙 API 에 붙으면 `fcc-test-platform`, 계약 커널의 표면이 되면
  `fcc-test-contracts` 이고 **그 경우 태그 발행이 먼저** 나가야 한다.
- **저장소**: 새 테이블이 필요한 축이 있다(요청/에러율 · 큐 적체 — 아래 표 참조).

## Constraints

- **읽기 전용이다.** 이 화면은 뷰어다 — 재시작·초기화 같은 버튼은 들어오지 않는다.
- **인증 뒤에 둔다.** 자원 지표는 규모와 부하를 노출한다. 공개 `/health`(라이브니스)
  와 «다른 물건»이므로 같은 엔드포인트에 얹지 않는다.
- **집계는 서버가 한다.** 브라우저가 원장을 받아 세면 페이지네이션이 진실을 자른다
  (오늘 커버리지에서 이미 겪었다 — 첫 페이지만 받으면 진행률이 조용히 일부만 센다).
- **없는 값은 «없다»고 말해야 한다.** 0 으로 채우지 않는다. 오늘 화면이
  「읽기 없음」이라고 적는 것과 같은 규약이고, 응답에도 그 구분이 있어야 한다
  (`null` = 관측하지 못함 ≠ `0` = 관측했고 0이었음).
- **비용.** 이 읽기는 15초마다 폴링된다. 매 호출이 DB 를 훑으면 진단이 부하를
  만든다 — 캐시하거나 샘플링 주기를 서버가 정해 응답에 실어야 한다.

## Success criteria

1. **화면의 「읽기 없음」이 0 이 된다** — `MISSING_METRICS` 배열(그 화면의 상수)이
   비면 이 의도가 끝난 것이다. 배열이 그대로 진척도다.
2. **한 번의 호출로 끝난다** — 지표 여덟 개를 여덟 번 부르지 않는다.
3. **`null` 과 `0` 이 구별된다** — 응답 스키마가 그것을 허용하고, 화면이 둘을
   다르게 그린다는 것을 검사가 확인한다.
4. **폴링이 서버를 흔들지 않는다** — 15초 주기에서 이 엔드포인트가 차지하는 비용의
   상한을 선언하고 잰다. ⚠️ 이것이 없으면 진단 도구가 장애의 원인이 된다.

잴 수 없는 것 — 적어 둔다:
- 「원인을 더 빨리 찾는다」가 진짜 목표인데, 그것을 재는 계측이 없다.

## 필요한 읽기 — 화면의 빈칸 그대로

| 화면의 줄 | 무엇 | 오늘 상태 |
|---|---|---|
| CPU 사용률 | 중앙 프로세스/호스트 | 없음 |
| 메모리 사용률 | 사용/전체 | 없음 |
| 디스크 사용률 | 아티팩트 저장소 포함 여부가 관건 | 없음 |
| DB 커넥션 풀 | 사용/최대 · 대기 | 없음 |
| 느린 쿼리 · 실패 쿼리 | 임계값은 서버가 정한다 | 없음 |
| 요청 수 · 에러율 | 창(window) 길이를 응답이 밝혀야 한다 | 없음 |
| 큐 적체 | 워커가 있는지부터 확인 필요 | 없음 |
| 라이브 채널 전역 상태 | 지금 채널은 챔버 하나에 붙는 구독이다 | 없음 |
| (별도) 최근 이벤트 | `chamber_heartbeat_events` 를 시간순으로 | **원장은 있는데 읽기가 없다** |
| (별도) 커널 핀 | 중앙이 실행 중인 `fcc-test-kernel` 태그 | 없음 |

⚠️ 마지막 둘이 값이 가장 크다.
- **최근 이벤트**는 «이미 있는 데이터»다. 원장이 존재하는데 읽기가 없어서 못 본다 —
  「있는 것」과 「읽을 수 있는 것」은 다른 명제다. 가장 싼 항목이기도 하다.
- **커널 핀**은 이 저장소에서 «실제로 조용히 갈라지는» 축이다. 핀이
  `pyproject.toml` 과 `requirements-central.txt` 두 곳에 있고 한쪽만 올리면
  아무것도 빨개지지 않은 채 두 레인이 어긋난다. 화면이 그 불일치를 말할 수 있으면
  이 저장소의 조용한 결함 하나가 시끄러워진다.

## Open questions

**Q1. 이 읽기는 어느 레인의 것인가?**
플랫폼 전용이면 `fcc-test-platform` 에서 끝나지만, 계약 커널의 표면이 되면
태그 발행 순서가 생겨 일정이 달라진다. ⚠️ 자원 지표는 «중앙 배포의 성질»이지
분야(provider)와 무관하므로 커널이 아닐 가능성이 높지만, 그 판단은 소유자의 것이다.

**Q2. 「서버」의 경계가 어디까지인가?**
중앙 API 프로세스만인가, 그 호스트 전체인가, DB 서버까지인가. 컨테이너로 돌면
프로세스의 CPU 와 호스트의 CPU 가 다른 숫자다 — 화면이 어느 쪽을 말하는지가
정해져 있지 않으면 그 숫자로 아무 판단도 못 한다.

**Q3. 요청 수·에러율의 «창»은 누가 정하나?**
1분인지 5분인지에 따라 같은 사고가 다른 숫자로 보인다. 응답이 창 길이를 함께
실어야 화면이 그것을 적을 수 있다.

**Q4. 이미 있는 것을 다시 만들고 있지 않은가?**
`otelCollectorUrl` 이 런타임 설정에 «있다». 관측 스택이 이미 계획돼 있다면 이
화면은 지표를 직접 받는 대신 그쪽을 가리키는 것이 맞을 수도 있다.
⚠️ 이 질문에 먼저 답하지 않으면 두 개의 관측 경로가 생긴다.

**Q5. 권한은?**
지금 `/diagnostics` 는 로그인만 하면 열린다. 자원 지표가 들어오면 `platform:admin`
으로 가리는 것이 맞아 보이는데, 그러면 개발자가 admin 을 받아야 한다.

**Q6. 폴링인가 스트림인가?**
15초 폴링으로 시작하는 것이 싸지만, 라이브 채널이 이미 있으므로 그쪽에 실을 수도
있다. ⚠️ 스트림으로 가면 「읽는 중의 재정렬」 문제가 따라온다(그 논의는
`console-home.tsx` 의 활동 흐름 주석에 있다).
