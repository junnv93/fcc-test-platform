# Session Playbook

## 기본 수업 구조

한 세션에 이 구조를 쓴다:

1. 주제 — 한 문장.
2. 왜 중요한가 — 운영자/소유자 관점의 이유.
3. 지도 — 프로그램 전체에서 어디에 있나.
4. 흐름 — 입력 → 처리 → 출력.
5. 코드 앵커 — 파일 2~5개. 긴 목록 금지.
6. 실패 모드 — 실제 사용에서 무엇이 잘못돼 보이나.
7. 질문 2~4개.
8. 모범답안 — 사용자가 시도한 뒤에.
9. 학습 노트 — 3~6줄.

## 설명 틀

```text
오늘 주제: <주제>

이 부분의 책임:
<쉬운 한국어 설명>

흐름:
<입력> -> <모듈/서비스> -> <출력>

중요 파일:
- <파일>: <역할>
- <파일>: <중요 클래스/함수와 무엇을 받아 무엇을 돌려주나>

무엇이 잘못될 수 있나:
- <실패 모드와 그것이 화면/DB 에 어떻게 보이나>

이것이 SSOT 인 곳:
- <파일> — 여기 적힌 것이 정본이고 나머지는 파생이다
```

## 실패 모드를 먼저 묻는 습관

이 저장소에서는 실패가 **조용한 성공**의 모양으로 나타나는 일이 반복됐다.
그래서 수업마다 이 질문을 넣는다:

> 「이 검사가 재는 축에서, 서로 다른 상태가 같은 값을 갖는 경우가 있는가?」

실제로 밟은 것들:

| 조용한 성공 | 실제 상태 | 무엇으로 구분되나 |
|---|---|---|
| 응답 200 | 거절 / 밀려남 / 저장 | 중앙 DB 행 수 |
| `pending=[]` | 최신 / **파일을 못 찾음** | 디렉터리에 파일이 있는가 |
| 검사 exit 1 | 설정 불일치 / **검사가 죽음** | 종료 코드 1 과 2 |
| 자동 검사 초록 | 정상 / **검사가 현장 값을 안 씀** | 입력이 현장 값인가 |
| `invalid_client` | 자격 삭제 / 시크릿 회전 | 인증 서버 이벤트 로그 |

## 변경을 설명할 때

건드린 층을 먼저 지목한다:

```
화면(apps/web) · 경계(platform_routes) · 합성(api_composition) ·
도메인 서비스(domain/services) · 포트 계약(domain/ports) ·
어댑터(fcc_test_platform/application/*_adapter.py) · DB(migrations) ·
검사(tests) · 배포(infra, scripts/check_*)
```

그다음 두 가지를 묻는다:
- 이 변경이 **잘못되면 어떤 증상**이 생기나?
- 그 증상이 **다른 원인의 증상과 구분되나?**

## 퀴즈 채점

- 맞은 부분을 먼저 표시한다.
- 틀린 부분은 짧게 고친다. 길게 설명하지 않는다.
- 모범답안을 준다.
- 사용자가 「검사가 통과했으니 된다」고 답하면 반드시 되묻는다:
  **그 검사가 실제로 무엇을 증명하나?**
