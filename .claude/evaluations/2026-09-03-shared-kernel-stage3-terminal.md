# 커널 3단계 — 두 완료 오라클이 모두 통과했다 (2026-09-03)

## 종료 상태

```
이름 소유권 (챔버 조건 PYTHONPATH=src)   위반 0     ← 3단계 전 2
공유 커널 폐포                            0개       ← 3단계 전 24
platform 이 주장하는 최상위 이름          fcc_test_platform 하나
```

ADR-0001 이 겨냥한 것이 정확히 이 둘이다. **같은 import 이름으로 서로 다른 코드가
도는 일이 구조적으로 불가능해졌다** — `sys.path` 순서가 정할 것이 없다.

    1단계  logger_config                    폐포 64 → 54
    2단계  application                      54 → 24
    3단계  domain · infrastructure          24 → 0

## 이동 — 두 클러스터가 각각 이미 닫혀 있었다

    3a  infrastructure   공유  2 · 중앙전용  8
    3b  domain           공유 22 · 중앙전용 54

유출 0 이라 서로 독립이었고 한 웨이브로 갔다. 재작성 **127파일 · 270줄**.

⚠️ 2단계의 과잉 재작성(`from pkg import X` 를 패키지째 옮겨 81 테스트 파손)을
피하려고, 패키지형 import 를 **가져오는 이름별로 갈랐다** — 같은 패키지에서
어떤 이름은 커널로, 어떤 이름은 `fcc_test_platform` 으로 간다.

## 이관이 드러낸 것 넷

| | 무엇 | 처방 |
|---|---|---|
| 1 | 정의 자리 검사의 기대 **경로** | `moved_module_source` 로 파생 |
| 2 | 순수성 검사 둘의 **경로 상수** | 같음 |
| 3 | **문자열 인자**로 든 모듈 이름 | 손으로 고침 + 전수 훑음 |
| 4 | `api_surface_boundary` 의 옛 접두사 | **남긴다** — provider 레인이 아직 쓴다 |

⚠️ **3번이 재작성기의 사각이다.** 내 재작성기는 `from X import` / `import X`
구문만 본다. 모듈 이름이 **데이터로** 있는 자리(문자열 인자·설정·목록)는
구조적으로 못 본다.

그런데 **잡혔다** — `moved_module_source` 가 없는 모듈에 예외를 내기 때문이다.
경로판이었으면 `FileNotFoundError` 로 죽거나, 더 나쁘게 **우연히 존재하는 다른
파일을 읽고 통과**했을 수 있다. 오늘 그 헬퍼를 도입한 것이 여기서 값을 했다.

## ⚠️ 그리고 완료가 게이트의 사각지대였다

3단계를 끝내자 폐포 게이트가 **판정 불가**를 냈다:

    공유 커널 폐포: 판정 불가 — 두 트리가 공유하는 최상위 이름이 0개다
      0개는 「공유가 없다」가 아니라 「못 찾았다」일 수 있다

씨앗 선정이 *「공유 최상위 이름」* 에 기대는데, **목표를 달성하면 그 집합이 비어
측정 자체가 불가능**해진다. 즉 이 게이트는 **자기 완료 상태를 표현할 수 없었다.**

> **성공이 실패와 같은 모양이었다.**

오늘 같은 형태를 두 번 더 봤다 — 기준선을 0 으로 만들자 「전부 통과」와
「0건 수집」이 같아졌고, `src/` 를 훑던 검사는 그 디렉터리가 없어 한 파일도 안 봤다.
**세 번 다 「0」이 두 가지를 뜻했다.**

### 가르는 증거 — 두 트리를 실제로 읽었는가

양쪽에 파이썬 파일이 있는데 겹치는 최상위가 없다면, 그것은 「못 찾았다」가 아니라
**「이름을 다 놓았다」**이고 이 결정의 종료 상태다. `measure` 가 그 사실을
`both_trees_read` 로 넣고 `judge` 가 그것으로 가른다.

봉인 셋:

    완료된 0 은 통과하고 「종료 상태」라고 말한다
    읽을 수 없는 트리의 0 은 여전히 판정 불가      ← 경로 오타를 완료로 읽지 않는다
    증거 키 없는 관측은 판정 불가                  ← 옛 판과 섞여도 안전하다

⚠️ **두 번째 팔이 없으면 이 정정이 「0 이면 통과」로 퇴화**하고, 그때 provider
경로를 잘못 준 실행이 **완료를 선언한다.**

## ⚠️ 그리고 봉인 하나가 「목표에 도달하지 않는다」를 전제하고 있었다

기준선 봉인의 술어가 *「기준선의 공유 폐포가 비어 있지 않다」* 였다. 폐포가 0 이
아닌 동안은 옳은 비-공허성인데, **3단계가 폐포를 0 으로 만들자 red 가 됐다** —
검사가 종료 상태를 금지하고 있었다.

이것이 **오늘 네 번째** 「0 이 두 가지를 뜻하는」 자리다:

    기준선 0        「전부 통과」 = 「0건 수집」
    src/ 훑기        디렉터리가 없어 한 파일도 안 봄
    폐포 0          「완료」 = 「못 찾음」
    기준선 봉인      「빈 기준선」 = 「붙잡는 것이 없음」

⚠️ **넷 다 「목표 달성」이 「측정 실패」와 같은 모양이었다.** 그리고 넷 다
비-공허성을 지키려는 팔이 만들어낸 것이다 — 팔이 **대상의 종료 상태를 상상하지
않고** 쓰였기 때문이다.

붙잡아야 할 성질은 「기준선이 비어 있지 않다」가 아니라 **「기준선이 회귀를
잡는다」**다. 빈 기준선도 그것을 한다. 축을 그리로 옮겼고, 그 팔은 0 이 된
뒤에도 계속 참이다.

> **비-공허성 팔을 쓸 때 물어라: 이 검사가 성공하면 이 팔이 red 가 되는가?**

## 남은 것 — 이 결정 밖

`fcc_test_platform/domain/` · `fcc_test_platform/infrastructure/` 는 그대로 남는다.
그것은 **이름 충돌 문제가 아니라 배치 문제**이고 이 ADR 의 축이 아니다.
provider 저장소는 자기 `src/` 를 그대로 둔다 — platform 이 그 이름을 주장하지
않으므로 충돌할 것이 없다.
