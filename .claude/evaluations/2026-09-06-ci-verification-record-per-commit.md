# 검증 기록이 커밋마다 남는가 — `concurrency` 가 자기 주석을 지키지 못했다

측정 2026-09-06 · 기준 `main` = `4ebd580` · 세션 fcc-delivery-final (a241f0f7)

## Why — 왜 이 문서가 필요한가

이 세션이 PR 다섯(#92 #95 #99 #100 #102)을 머지하면서 **결함의 증거를 스스로
만들었다.** 머지 간격은 5~7초였고 결과는 이렇다:

    2026-09-06T02:47:17Z  99f5d61  success     ← 첫 런: 자리를 잡고 달린다
    2026-09-06T02:47:23Z  8c33bc3  cancelled
    2026-09-06T02:47:28Z  4ba0585  cancelled
    2026-09-06T02:47:35Z  7827b50  cancelled
    2026-09-06T02:47:41Z  64abb7b  cancelled
    2026-09-06T02:48:18Z  ae043a5  success     ← 마지막 대기자(형제 세션의 #105)

**main 커밋 넷에 검증 기록이 없다.** 그리고 그 워크플로의 `concurrency` 주석은
정확히 그것을 막겠다고 적어 두고 있었다:

    # PR 반복만 취소한다. main 런을 취소하면 그 커밋에 검증 기록이 남지 않는다.

⚠️ 같은 의도문이 **두 워크플로에 각각** 있었다. `frontend-qa-evidence.yml` 쪽이
더 오래됐고(2026-08-07, `ci-minutes-root-cause`) 영어로 같은 말을 한다 —
*"never abandon a main/scheduled run half-verified — a cancelled post-merge run
leaves that commit with no verification record."* 둘 다 그 의도를 달성하지 못했다.

## What — 무엇이 원인인가

`cancel-in-progress: false` 는 **대기 중인 런을 지키지 않는다.** 그 값은 「이미
«달리는» 런을 취소하지 마라」만 말한다. 한 concurrency 그룹에서 대기할 수 있는
런은 하나뿐이고, 새 런이 그룹에 들어오면 **대기하던 것이 취소된다.**

    group: ${{ github.workflow }}-${{ github.ref }}   ← push 는 전부 refs/heads/main

즉 main 으로 가는 모든 push 가 **한 그룹**을 다툰다.

⚠️ **이것이 왜 여태 조용했는가.** 머지 둘까지는 증상이 없다 — 대기 자리를 다투는
셋째가 없기 때문이다. 같은 날 10초 간격의 머지 쌍(`4189dca`·`28b2bc4`)은 둘 다
`success` 다. 그래서 이 결함은 「빠르게 머지하면 깨진다」가 아니라 **「셋 이상을
연달아 머지하면 가운데가 사라진다」**이고, 평소의 한두 개짜리 머지로는 나타나지
않는다.

⚠️ **`cancelled` 는 빨간 X 가 아니다.** 다운스트림에서 「돌지 않았다」와
「통과했다」가 구별되지 않는다 — 이 저장소가 여러 번 이름 붙인 «공허함은 초록과
같은 모양이다» 형태다.

## How — 무엇을 바꿨는가

push 축만 커밋별로 가른다. 다툴 그룹이 없으면 취소는 **구조적으로 불가능**해진다.

    group: ${{ github.workflow }}-${{ github.event_name == 'pull_request'
                                      && github.ref || github.sha }}

PR 축은 손대지 않았다 — 그대로 `github.ref` 로 묶여 옛 반복이 취소된다.
두 워크플로(`checks.yml` · `frontend-qa-evidence.yml`)에 같이 적용했다.

### 봉인은 형태가 아니라 «성질»을 잰다

`tests/test_ci_leaves_a_record_for_every_pushed_commit.py`.
「`github.sha` 라는 글자가 들어 있는가」를 묻지 않는다. 그러면 다른 올바른 형태를
거짓 빨강으로 만들고, **잘못된 형태 하나를 거짓 초록으로 놓친다** — PR 축까지
커밋별로 갈라 옛 반복이 안 죽게 만드는 과잉 교정(= `ci-minutes-root-cause` 가
2026-08-07 에 이름 붙인 그 비용)이다.

대신 그룹 표현식을 **두 맥락에서 실제로 평가**하고 두 축을 각각 묻는다:

    push,         같은 ref · 다른 sha  →  그룹이 **달라야** 한다
    pull_request, 같은 ref · 다른 sha  →  그룹이 **같아야** 한다

대상 집합은 손으로 나열하지 않고 워크플로 **선언에서 파생한다**(`push` 트리거를
가진 것 전부). 새 워크플로가 생겨도 이 파일을 고치지 않아도 따라간다.

⚠️ **정직한 한계.** 평가기는 GitHub Actions 표현식의 부분집합만 안다(문맥 참조 ·
문자열 비교 · `&&`/`||` 삼항). 모르는 문법을 만나면 **통과시키지 않고 그 자리에서
멈춘다** — `TestTheEvaluatorUnderstandsThisTree` 가 그 축을 따로 지킨다. 평가하지
못한 것을 초록으로 세는 것이 이 부류 검사의 유일한 진짜 실패 방식이다.

## Verification — 실측

* 새 검사 7건 통과. `TestTheCheckWouldSeeTheDefect` 가 세 형태를 대조한다:
  옛 형태는 축 1 에서 걸리고, 과잉 교정은 축 2 에서 걸리고, 실제 배포 형태는 둘 다
  만족한다.
* **주입으로 이빨을 확인했다.** 실제 `checks.yml` 의 group 을 옛 형태로 되돌리자
  `test_push_runs_do_not_share_a_concurrency_group` 이 빨개지며 파일 이름과 그룹
  값(`'checks-refs/heads/main'`)을 말했다. 복원하니 7/7 초록.
* 두 워크플로 YAML 이 파싱된다(`yaml.safe_load`).
* 레인 전량: `lane_check` EXIT=0.

⚠️ **이 검사가 재지 못하는 것.** GitHub 이 이 표현식을 내가 평가한 대로 해석한다는
보장은 여기서 나오지 않는다. 그 축은 머지 뒤 실제 런에서만 관측되고, 아래 후속 1이
그것을 확인한다.

## 후속

1. ✅ **머지 뒤 실측으로 확인했다 — 이제 「표현식 수준」이 아니다.**

   ⚠️ 먼저, **초록만 보는 것으로는 확인이 되지 않는다.** 머지 뒤 두 커밋이 둘 다
   `success` 인 것은 아무것도 말해 주지 않는다 — 옛 설정에서도 **둘까지는 증상이
   없었기** 때문이다. 「고쳐졌다」와 「원래도 초록이었을 것」이 같은 모양이다.

   구별되는 축은 **잡이 언제 실행됐는가**다. 옛 설정에서는 둘째가 첫째를 기다려
   직렬로 돌고, 새 설정에서는 그룹이 달라 **겹쳐서** 돈다. GitHub Actions API 의
   잡 수준 시각(`/actions/runs/<id>/jobs`)으로 물었다:

       고치기 전 (group = workflow-refs/heads/main)
         99f5d61  job 02:47:19 → 02:48:33  success
         8c33bc3  **잡이 없다** — 대기 중 취소돼 시작조차 못 했다
         4ba0585  **잡이 없다**
         ae043a5  job 02:48:35 → 02:50:02  success   ← 앞 잡 종료 **2초 뒤**. 직렬이다

       고친 뒤 (group = … && github.ref || github.sha)
         96ee3ac  job 03:38:50 → 03:40:29  success
         e374339  job 03:39:07 → 03:40:38  success   ← 앞 잡이 **아직 달리는 중**에 시작

   두 머지는 17초 간격이었고 잡은 겹쳐서 돌았다. 옛 설정이었다면 둘째 잡은
   03:40:29 이전에 시작할 수 없다. **GitHub 이 이 표현식을 의도대로 해석한다는
   것이 관측됐다.**

   ⚠️ 그리고 `8c33bc3`·`4ba0585` 에 **잡 자체가 없다**는 것이 이 결함의 모양을
   가장 정확히 말한다. 「실패한 검증」이 아니라 **「일어나지 않은 검증」**이다.
2. **모노레포 사본.** 이 두 워크플로가 모노레포에도 같은 형태로 있는지 이 레인은
   답하지 못한다. 있으면 같은 결함이고, `frontend-qa-evidence.yml` 의 주석이
   2026-08-07 자라는 것은 그쪽에서 왔을 가능성을 시사한다 — **확인하지 않았다.**
3. **연속 머지 습관.** 설정이 고쳐져도 사람 쪽 대처는 남는다: PR 을 연달아 머지할
   때 각 런이 자리를 잡을 시간을 주면 이 결함이 없어도 관측이 쉬워진다.
