## 3. 다섯 축 진단

### 3.1 워크플로우 — 이 레포에서 가장 강한 축

| 장치 | 내용 |
|---|---|
| `commit-msg` 훅 | **17항목 자기감사** 필수. 사유 없는 행 거부. 값 축은 `B-3`·`B-4` 를 실제 산출물과 대조 |
| `pre-commit` 훅 | **work-claim 브랜치 가드** — 다중 세션이 한 체크아웃을 공유할 때 남의 브랜치에 커밋이 얹히는 사고를 막는다 |
| explicit-files commit | `git add <명시파일>` + `git commit -F <msg> -- <files>`. `-A`/`.` **영구 금지** |

⚠️ **이 규율이 리팩토링 설계를 직접 제약한다.** 대량 자동수정(ruff `--fix` 등)이
만드는 광범위 diff 는 explicit-files 규율·다중 세션 워크트리와 **정면 충돌**한다.
따라서 이 문서의 모든 대량 변경은 **디렉터리 단위 분할**을 전제로 한다.

### 3.2 성능 — 이미 2축 예산이 있다

`bundle-budget.json` 은 **서로 다른 두 메트릭**에 각각 예산을 건다.

| 메트릭 | 측정 | 예산 | headroom |
|---|---:|---:|---:|
| 총 gzip | 318,274 B | 381,929 B | 1.2 |
| **초기 로드 경로 JS** | 161,064 B | 177,171 B | **1.1** |

두 번째 메트릭이 존재하는 이유가 문서에 적혀 있다 — *"총량은 청크가 **언제**
받아지는지에 눈이 멀다. 이 웨이브가 114,561 B 를 초기 경로에서 뺐는데 총량은
거의 안 움직였다. 총량만 보는 예산은 이 개선과 그 정확한 회귀를 **둘 다 '변화
없음'으로 채점**한다 — 그래서 잡아야 했던 결함이 두 달을 살아남았다."*

headroom 10% 의 근거도 파생이다 — *"이번에 제거한 가장 작은 청크(tracing,
36,414 B)보다 작게 두어, 어느 SDK 든 다시 붙으면 즉시 게이트가 걸리게."*

> 성능 축은 **추가할 것이 없다.** 이 문서가 제안하는 모든 변경은 이 두 예산을
> 통과해야 하는 **제약**으로 다룬다.

#### 🔑 결박 구조 — 분할은 함수 하나로 가능하다

```python
ROOT       = Path(__file__).resolve().parents[1]     # :74
WEB_SRC    = ROOT / "apps" / "web" / "src"           # :75
GLOBAL_CSS = WEB_SRC / "styles" / "global.css"       # :76  ← 단일 정의

def _read_css() -> str:                              # :93
    return GLOBAL_CSS.read_text(encoding="utf-8")    # :94  ← 유일한 읽기 지점
```

**71개 검사 전부가 `_read_css()` 를 경유한다.** 직접 읽는 곳은 존재 확인
1곳(`:153`)뿐이다. 따라서:

```python
def _read_css() -> str:
    return "\n".join(p.read_text(encoding="utf-8")
                     for p in sorted(STYLES_DIR.rglob("*.css")))
```

**이 한 함수를 바꾸면 CSS 분할이 열리고 71개 검사는 그대로 살아남는다.**
검사가 count-zero/symmetry 라 파일이 나뉘어도 명제가 유지되기 때문이다.

⚠️ 소비 측(`WEB_SRC.rglob("*.tsx")`)은 전체 스캔이라 분할에 강건하다.
다만 `(WEB_UI / "DataTable.tsx")` 처럼 **파일명을 직접 잡는 검사**가 있어
컴포넌트를 옮기면 그 검사는 함께 고쳐야 한다.

## 4. 업계 표준 대비 — 공식 문서 근거

### 4.1 디자인 토큰 — `createThemeContract`

vanilla-extract 공식 문서:

> *"Each theme must implement the contract **in its entirety**"*

```ts
// tokens.css.ts — 계약만 정의한다. CSS 를 만들지 않는다.
export const vars = createThemeContract({
  surface: { bg: null, bgAlt: null, border: null },
  status:  { pass: null, fail: null, warn: null, na: null },
});

// theme.dark.css.ts — 하나라도 빠지면 컴파일 실패
export const dark = createTheme(vars, { ... });
```

**이것이 `both_dark_channels_declare_the_same_tokens` 와 `no_dark_only_token`
을 런타임 테스트에서 컴파일 타임으로 올린다.** 검사가 더 좋아지는 것이 아니라
**위반 상태가 만들어지지 않는다.**

#### 71개 검사 중 무엇이 대체되고 무엇이 남는가

| pytest 검사 | 대체 | 근거 |
|---|---|---|
| `both_dark_channels_declare_the_same_tokens` | ✅ **컴파일 에러** | contract 전체 구현 강제 |
| `no_dark_only_token` | ✅ **구조적으로 불가능** | 계약에 없는 토큰은 존재 못 함 |
| `every_defined_workbench_class_is_referenced` | ✅ **죽은 CSS 불가** | 스코프 격리 |
| `no_border_radius_literal` | ✅ **stylelint** | `declaration-property-value-allowed-list` |
| `no_font_weight_literal` · `no_letter_spacing_literal` | ✅ stylelint | 동일 |
| `no_raw_colour_in_box_shadow` | ✅ stylelint | 동일 |
| `radius_scale_is_capped_at_prd_maximum` | ✅ `Literal` union 타입 | 스케일이 타입이 된다 |
| **`h1_outranks_body_by_the_contracted_ratio`** | ❌ **유지** | 제품 규칙 — 도구가 PRD 를 모른다 |
| **`reduced_motion_still_neutralises_every_duration_token`** | ❌ **유지** | 접근성 정책 — 도구 밖 |

> 대체되는 것은 **검사가 좋아져서가 아니라 위반 상태가 만들어지지 않기 때문**이다.
> 남는 것은 도구가 표현할 수 없는 **제품 규칙**이다. 이 구분이 S8 의 범위다.

⚠️ Tailwind v4 도 기존 변수를 살릴 길이 있다 — `@theme inline` 이 `var()` 를
받는다:
```css
:root { --acme-canvas-color: oklch(0.967 0.003 264.542); }
@theme inline { --color-canvas: var(--acme-canvas-color); }
```
그러나 **Tailwind 는 「모든 테마가 계약 전체를 구현했는가」를 강제하지 못한다.**
지금 pytest 가 잡는 바로 그 축이다. 그리고 유틸리티 클래스가 JSX 에 흩어지면
explicit-files 규율(§3.1)에서 컴포넌트 파일 자체가 충돌 지점이 된다.

### 4.2 접근성 — Radix `asChild`

공식 문서의 조건: **props 를 spread 하고 ref 를 forward 할 것.**

```jsx
const Button = React.forwardRef((props, ref) => <button {...props} ref={ref} />);

<Dialog.Trigger asChild>
  <Button>열기</Button>      {/* 마크업·시각 결과 동일, 동작만 주입 */}
</Dialog.Trigger>
```

**26개 컴포넌트를 버리지 않는다.** `DataTable` · `ProjectPicker` ·
`DensityToggle` 이 포커스 트랩 · 키보드 내비게이션 · WAI-ARIA 를 얻는다.
지금 그 비용은 `axe` 사후 검출 + 손으로 지불되고 있다.

### 4.3 작업 큐 — PostgreSQL 만으로

`taskiq-pg` 공식 문서:

> *"utilizes PostgreSQL's native LISTEN/NOTIFY mechanism ... **eliminating the
> need for external message brokers like Redis or RabbitMQ**"*

```python
broker = AsyncpgBroker(
    dsn=...,
    channel_name="taskiq",
    table_name="taskiq_messages",
    max_retry_attempts=5,
).with_result_backend(AsyncpgResultBackend(dsn=..., table_name="taskiq_results"))
```

**이 시스템에 Redis 보다 나은 이유 셋:**

1. **인프라 증가 0** — 온프레미스 폐쇄망에서 컨테이너·보안 승인 포트·백업 대상이
   늘지 않는다. 그리고 큐가 같은 PostgreSQL 에 있으므로 이미 CI 로 도는
   `backup-restore-rehearsal` 에 **자동으로 포함**된다.
2. **운영자가 SQL 로 큐를 본다** — 이 레포의 증적(evidence) 문화와 같은 결이다.
   ```sql
   SELECT task_id, convert_from(result,'UTF8')::jsonb FROM taskiq_results;
   SELECT id, task_name, created_at FROM taskiq_messages ORDER BY created_at DESC;
   ```
3. **트랜잭션 경계 공유** — 결과를 쓰는 트랜잭션과 후속 작업 등록이 같은 DB 다.
   「저장은 됐는데 작업이 안 걸린」 상태가 구조적으로 줄어든다.

지연 실행도 라벨 하나다: `kiq_with_meta(labels={"delay": 30}, ...)`.

### 4.4 마이그레이션 — `stamp` 가 진입로

Alembic 공식 API:

> **`alembic.command.stamp`** — *"'stamp' the revision table with the given
> revision; **don't run any migrations**"*

기존 10개 SQL 을 **재실행하지 않고** "여기까지 적용됨"만 표시한 뒤 011번부터
Alembic 으로 간다. 운영 DB 를 건드리지 않는다.

그리고 이 프로젝트에 특히 맞는 둘:

```python
# 오프라인 모드 — DB 접근 없이 SQL 생성. 운영자가 먼저 검토한다
def run_migrations_offline():
    context.configure(url=..., target_metadata=...)
```

```python
# autogenerate 가 외부 테이블을 drop 하지 못하게
def include_object(object, name, type_, reflected, compare_to):
    if type_ == "table" and reflected and compare_to is None:
        return False
    return True
```
Keycloak · `taskiq_*` 테이블이 같은 DB 에 있어도 안전하다.

### 4.5 관측성 — 표준은 이미 충족돼 있다

§3.6 이 실측한 대로 W3C Trace Context · Prometheus 형식 메트릭 · 구조화 로깅이
전부 자체 구현으로 존재한다. **업계 표준과의 격차는 「구현 유무」가 아니라
「수집기 호환」 하나다.**

ADR-0006 이 이미 그 축을 다룬다 — *"backend 의 `structured.jsonl`(OBS-0)가
Loki / Datadog / ELK / OTel collector 호환"*. 즉 설계 의도가 이미 수집기 중립이다.

남는 선택지는 하나뿐이다: **OTLP exporter 를 옵션 의존으로 추가**해 기존
`ApiMetricsRegistry` 의 출력을 표준 수집기로 내보낼 것인가. contracts 의 P0 를
지키려면 `[otlp]` extra 로만 들어와야 한다.

⚠️ `opentelemetry-instrumentation-fastapi` 같은 **자동 계측 패키지는 도입하지
않는다.** 이미 있는 미들웨어와 이중 계측이 되고, contracts 가 서드파티를 하드
의존하게 된다.

## 6. 상세 설계 — 착수 순서대로

### S1 — mypy `domain/*` strict · **오늘 켤 수 있다**

54파일에 오류 **4건**, 전부 `no-untyped-def`. **실제 타입 불일치 0건.**

```toml
[tool.mypy]
python_version = "3.11"
ignore_missing_imports = true
follow_imports = "silent"
disallow_untyped_defs = false

[[tool.mypy.overrides]]
module = "fcc_test_platform.domain.*"
disallow_untyped_defs = true
```

4건을 고치고 CI 에 붙이면 도메인 타입 규율이 그날부터 기계 강제다.
**이 문서 전체에서 비용 대비 효과가 가장 크다.**

### S2 — import-linter

```ini
[importlinter]
include_external_packages = True     # ⚠️ 없으면 실행 자체가 거부된다
root_packages = fcc_test_platform

[importlinter:contract:layers]
type = layers
layers =
    fcc_test_platform.api
    fcc_test_platform.infrastructure
    fcc_test_platform.application
    fcc_test_platform.domain

[importlinter:contract:purity]
type = forbidden
source_modules = fcc_test_platform.domain
forbidden_modules = fastapi, psycopg, sqlalchemy, pandas, openpyxl

[importlinter:contract:app-no-db]
type = forbidden
source_modules = fcc_test_platform.application
forbidden_modules = psycopg, sqlalchemy
```

실행에 `PYTHONPATH` 로 형제 레인이 필요하다:
`.:../fcc-test-contracts:../fcc-test-contracts/packages/fcc-test-kernel`.
CI 는 이미 그 둘을 설치하므로 추가 배선이 없다.
세 번째 계약의 2건을 baseline 에 등재하고 한 방향으로만 줄인다.

### S3 — DB 어댑터 이전

`central_project_reference_adapter` → `infrastructure/adapters/driven/`.
그 디렉터리가 이미 있으므로 새 구조를 만들지 않는다.

간접 경로(`runtime_config → central_db_config → psycopg`)는 루트 모듈이 설정과
드라이버를 함께 들고 있어 생긴다. **설정 읽기와 연결 생성을 분리**하면
`runtime_config` 는 설정만 본다.

⚠️ S2 의 세 번째 계약이 먼저 들어가야 이 작업의 완료를 **기계가 판정**한다.

### S7 — CSS 분할 (§3.3 결박 구조 참조)

```python
# tests/test_frontend_visual_language.py
STYLES_DIR = WEB_SRC / "styles"

def _read_css() -> str:
    return "\n".join(p.read_text(encoding="utf-8")
                     for p in sorted(STYLES_DIR.rglob("*.css")))
```

**이 한 함수가 71개 검사를 전부 살린다.** 함께 고칠 것은

그래야 다중 세션 충돌이 실제로 줄어든다.

### S8 — vanilla-extract (S7 이후)

## 8. contract-as-data 는 유지한다

`platform_routes.py` 의 dict 계약 + 동적 라우트 등록은 유지한다.

**기각 근거 정정** (독립 리뷰 — 이 계약 표면을 실제로 개정한 세션):
fail-closed 를 지키는 것은 `_operation` 이 아니라 **소비 지점**이다.
`access_policy.py:201` 의 `.get()` 이 부재를 차단으로 읽으므로 데코레이터로
바꿔도 그 성질은 유지된다.

**진짜 근거는 소비자가 둘이라는 사실이다:**

| 소비자 | 위치 |
|---|---|
| 런타임 인가 | `platform_routes.py:548` |
| OpenAPI 생성 | `api_schema.py:657,693` |

데코레이터는 런타임 함수 객체에 붙으므로 문서 생성기가 앱을 import 해야 하고,
**계약 → 앱으로 의존 방향이 뒤집힌다.**

### 유지한 채 타입 안전성 얻기

```python
class OperationSpec(TypedDict):
    request: Required[Optional[str]]
    response: Required[str]
    permission: Required[str]
    error_responses: NotRequired[dict]
    allowed_during_password_change: NotRequired[Literal[True]]

OPERATIONS: dict[str, OperationSpec]
```

`Literal[True]` 가 「키가 있으면 반드시 True」를 타입으로 못 박아,
`_operation` 주석이 걱정하던 *"모든 항목에 `False` 를 적어 두면 다음 사람이
기본값을 뒤집는다"* 가 **타입 수준에서 불가능**해진다.

⚠️ 이 이득은 **S1 이 켜져 있어야** 실현된다. 검사기 없는 TypedDict 는 주석과
같은 효력이다.

## 부록 A. EMS 대비 — 같은 조직의 형제 시스템

`equipment_management_system`(EMS)은 같은 중앙 PC에서 나란히 도는 형제
시스템이다(EMS `:8090` · FCC `:8080`/`:8081`). 코드는 공유하지 않지만 **운영
관행과 보안 파라미터를 물려받았다**(`bcrypt cost 12 — EMS parity`).

### A.1 스택 대비

| 영역 | EMS | platform |
|---|---|---|
| 프레임워크 | Next.js 16 (App Router) · **React 19** | React **18.3.1** + Vite 5 |
| UI 프리미티브 | **Radix UI 13종** + shadcn/ui | 자체 26개 |
| 스타일링 | **Tailwind 4** + CVA + tailwind-merge | 단일 `global.css` |
| 폼 | react-hook-form + zod resolver | 자체 |
| 아이콘 | lucide-react | — |
| 백엔드 | **NestJS 11** (TypeScript) | **FastAPI** (Python) |
| ORM | **Drizzle** (타입 안전) | psycopg raw + SQLAlchemy |
| 마이그레이션 | **drizzle-kit** | 손번호 SQL |
| 작업 큐 | **BullMQ + ioredis** | 없음 |
| 캐시 | **Redis 7.4** | 없음 |
| 로깅 | **Winston** + daily-rotate | 표준 logging |
| 메트릭 | **prom-client** → Grafana | 1파일 |
| 에러 추적 | **Sentry**(서버+클라) | 클라만 |
| 인증 | NextAuth 5 + Azure AD | Keycloak 25 OIDC |
| 오브젝트 스토리지 | RustFS (S3 호환) | 파일서버 |

### A.2 무엇을 물려받고 무엇을 물려받지 않는가

**물려받을 것**
- **Grafana 합류** — EMS 가 이미 Prometheus + Grafana 를 운영한다. S4 의 메트릭은
  새 스택을 세우지 말고 **그 Grafana 에 붙인다**.
- **CI 게이트 밀도** — EMS 는 워크플로 12개(CodeQL · supply-chain-gate ·
  e2e-nightly · perf/a11y/bundle audit). platform 의 백엔드 CI 는 `lane-check`
  하나뿐이다. 프론트(10 게이트)의 밀도를 백엔드로 옮기는 것이 로드맵의 방향이다.
- **Radix** — EMS 가 이미 13종을 쓴다. 사내에 운용 경험이 있다는 뜻이고, S6 의
  학습 비용이 그만큼 낮다.

**물려받지 않을 것**
- **Redis + BullMQ** — EMS 는 컨테이너를 세울 수 있는 환경이지만, FCC 중앙은
  온프레미스 폐쇄망이고 포트마다 보안 승인이 필요하다. **taskiq-pg 로 인프라
  증가 0**이 이 제약에서 더 낫다(§4.3).
- **Tailwind** — EMS 의 선택은 옳지만, platform 은 이미 CSS 규율 검사 71개와
  토큰 334개를 가졌고 Tailwind 는 **계약 전체 구현을 강제하지 못한다**(§4.1).
- **Drizzle 상당물** — TypeScript 생태계의 선택이다. Python 쪽 대응은
  SQLAlchemy 2.0 Core 이고 §3.5 ①에 두었다.

⚠️ **두 시스템은 성격이 다르다.** EMS 는 CRUD 업무앱(장비 대장·승인 워크플로),
platform 은 계측 워크벤치(챔버·세션·측정·성적서)다. 스택을 맹목적으로 맞추면
platform 이 이미 잘하는 축(계약 파생 · 번들 예산 2축 · CSS 규율)을 잃는다.
**물려받을 것은 스택이 아니라 운영 인프라와 게이트 밀도다.**
