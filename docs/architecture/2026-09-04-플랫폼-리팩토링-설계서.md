## 1. 대상 정의 — 무엇을 리팩토링하는가

**리팩토링은 납품 레포에서 수행될 수 없다.**

| 트리 | 경로 | 성격 |
|---|---|---|
| 원본 모노레포 | `~/FCC_mobile_test_automation` (main, 커밋 5,138) | **유일한 작업 대상** |
| 납품 상자 (platform) | `fcc-delivery-final/fcc-test-platform` | 읽기 전용 생성물 |
| 납품 상자 (contracts) | `fcc-delivery-final/fcc-test-contracts` | 읽기 전용 생성물 |

납품 파일을 고치면 배송이 그 파일을 이름으로 대며 거부하고, 누군가 편집을
원본으로 옮길 때까지 **모두의 배송이 멈춘다**. 따라서 이 문서의 모든 변경은
원본 기준으로 기술한다.

⚠️ **이 문서의 초기 진단은 납품 상자(원본의 29%)만 보고 작성되었다가 전면
철회되었다.** 3장이 그 기록이다.

## 3. 기각된 진단 — 재론 금지 목록

초기 분석은 납품 상자만 보고 다음을 "부채"로 지목했다. **전부 오진이었다.**

| # | 초기 진단 | 기각 근거 | 판정 |
|---|---|---|---|
| 1 | 계약을 사람이 손으로 관리 → 자동 생성 필요 | 이미 코드에서 파생 + CI 드리프트 게이트 | ❌ 기각 |
| 2 | 껍데기 헥사고날 / anemic domain | `Protocol` 113개, 도메인 import 오염 0 | ❌ 기각 |
| 3 | 리포지토리 패턴 부재, SQL 전역 산재 | `*_store.py` 76파일 | ❌ 기각 |
| 4 | 3,670줄 단일 라우터 분해 필요 | 원본은 표면별 8파일로 이미 분해 | ❌ 기각 |
| 5 | dict 라우팅은 FastAPI 장점 포기 | contract-as-data 의도적 설계 (아래) | ⏳ 리뷰 대기 |

### 3.1 왜 오진했는가 — 방법론적 교훈

납품 상자는 원본의 29%이고, 추출 매니페스트는 **표면별로 분해된 계약을
단일 파일로 조립**해 싣는다. 즉 납품 상자에서 관측된 "3,670줄 단일 파일"과
"빈약한 domain"은 **원본의 구조가 아니라 포장의 형태**였다.

> 생성물을 원본으로 착각하고 내린 진단은 전부 무효다. 이 프로젝트에는
> 생성물인데 생성물처럼 보이지 않는 파일이 여럿 있다.

### 3.2 5번 항목 — contract-as-data를 함부로 건드리면 안 되는 이유

```python
def _operation(*, request, response, permission,
               error_responses=None, response_media_type=None,
               allowed_during_password_change=False) -> dict:
```

- 권한(`permission`)이 **계약에 결합** → 라우트별 권한이 SSOT
- `allowed_during_password_change`는 **키의 부재가 곧 차단(fail closed)**.
  주석: "모든 항목에 False를 적어 두면" (안티패턴) — 새 operation은 누군가
  의도적으로 옵트인하기 전까지 거부된다.
- Pydantic 데코레이터 방식으로 옮기면 이 성질을 **잃는다**.

→ 최종 판정은 리뷰 C(설계 의도) Q1 결과에 따른다.

## 4. 살아남은 결함

납품 상자와 원본 **양쪽에서** 확인된 것만 남긴다.

### 4.1 정적 분석 도구 부재 — 최우선

원본 루트에 mypy·ruff·pyright·flake8 설정이 **하나도 없다**
(`pyproject.toml`에 `[tool.pytest.ini_options]` 하나뿐).

이것이 왜 가장 중요한가:

> 도메인 순수성을 **각 파일 docstring에 자연어로 선언**하고,
> 345,560줄 테스트로 **감시**하는데, 그것을 **강제할 도구는 한 줄도 없다.**

`import-linter` 계약 20줄이 대체할 수 있는 일에 수천 줄의 pytest가 쓰이고 있다
(정확한 대체 가능 범위는 리뷰 A Q1 결과 대기).

### 4.2 서버 측 관측성 부재

- OpenTelemetry: `src/` 전체에서 **0파일**
- 메트릭: 1파일
- 반면 프론트엔드는 OTel 완비(`sdk-trace-web`, `instrumentation-fetch`, OTLP)

→ 브라우저에서 시작된 trace가 API 도달 즉시 끊긴다.

### 4.3 Python lockfile 부재

`git+https://…@tag` 직접 참조로만 고정. 이연 사유는 "배포물을 담을 인덱스가
없다"(pyproject 주석). → 사설 인덱스 하나가 이 이연을 해소한다.

### 4.4 테스트 마커 형해화

`pyproject.toml`이 6종 선언(unit/integration/hardware/database/gui/invariant)
하지만 실사용은:

| 마커 | 사용 |
|---|---:|
| `parametrize` | 81 |
| `bench` | 58 |
| `integration` | **1** |
| `unit`/`hardware`/`database`/`gui`/`invariant` | 0 |

→ 345K줄 테스트를 목적별로 선택 실행할 수 없다. CI 시간과 직결.

## 5. 교차검증 — 방법과 그 한계

### 5.1 무엇을 했는가

초기 진단을 그대로 문서화하면 편향이 굳는다. 그래서 서로 다른 각도의
적대적 리뷰어 3인을 병렬로 붙였다: **실증 반박자**(수치 재측정),
**아키텍처 적대자**(제안의 실패 모드), **설계 변호인**(현 구조의 의도 복원).

### 5.2 실제로 무슨 일이 일어났는가 — 정직한 기록

**리뷰어 3인은 2시간 이상 응답하지 않았고, 최종 판정은 작성자 자신의
자기반박으로 수행되었다.** 범위를 좁혀 재조준하고 마감을 통보했으나
결과를 받지 못했다.

⚠️ 따라서 이 문서의 검증은 **독립적이지 않다.** 같은 사람이 진단하고
같은 사람이 반박했다. 다만 반박의 근거는 전부 **원본 트리에 대한 직접
재측정**이며, 인용된 수치는 누구나 재현할 수 있다. 5.3의 기각 판정들은
의견이 아니라 측정이다.

이 한계를 감추지 않는 이유: 이 문서 자체가 "생성물을 원본으로 착각한
진단은 무효"라고 말하고 있다. 검증 절차의 결함을 숨기면 같은 오류를
문서가 반복하는 것이다.

### 5.3 자기반박 결과 — 초기 진단 12건의 최종 판정

| # | 초기 진단 | 판정 | 근거 |
|---|---|---|---|
| 1 | 계약을 손으로 관리 → 자동 생성 필요 | ❌ 기각 | 이미 코드에서 파생 + `api-schema-drift.yml` 게이트 |
| 2 | 껍데기 헥사고날 / anemic domain | ❌ 기각 | `Protocol` 113개, 도메인 import 오염 0 |
| 3 | 리포지토리 패턴 부재 | ❌ 기각 | `*_store.py` 76파일 |
| 4 | 3,670줄 단일 라우터 분해 | ❌ 기각 | 원본은 표면별 8파일 |
| 5 | dict 라우팅 → Pydantic 전환 | ❌ 기각 | fail-closed 권한 모델 상실 (5.4) |
| 6 | 아키텍처 순응 테스트를 도구로 대체 | ❌ **기각** | 메타테스트 구조 (5.5) |

| 8 | 배송 모델 A/B 양자택일 | ⏸ 보류 | 분리 목적이 IP 공개범위 |
| 9 | provider 플러그인화 · 멀티테넌시 | ⏸ 보류 | 요구사항 근거 미확인 (8장) |
| 10 | **정적 분석 도구 부재** | ✅ **유지** | 원본에도 mypy/ruff 0 |
| 11 | **서버 관측성 부재** | ✅ **유지** | OTel 0파일, 메트릭 1파일 |

**12건 중 6건 기각, 3건 보류/축소, 3건만 생존.** 생존한 것은 전부
"없는 것을 더하는" 항목이고, 기각된 것은 전부 "있는 것을 바꾸는" 항목이다.
이 비대칭이 이 문서의 결론이다.

### 5.4 왜 contract-as-data를 건드리지 않는가

```python
def _operation(*, request, response, permission,
               error_responses=None, response_media_type=None,
               allowed_during_password_change=False) -> dict:
```

- 권한이 **계약에 결합** → 라우트별 권한 SSOT
- `allowed_during_password_change`: **키의 부재가 곧 차단(fail closed)**.
  새 operation은 누군가 의도적으로 옵트인하기 전까지 거부된다
- Pydantic 데코레이터로 옮기면 이 성질을 잃는다 — 새 라우트가 **조용히
  열리는** 사고가 구조적으로 가능해진다

> 타입 안전성을 얻자고 권한 안전성을 내주는 거래다. 받아들일 수 없다.

### 5.5 왜 순응 테스트를 삭제하지 않는가 — 가장 중요한 반전

`test_frontend_architecture_conformance.py` = 9,774줄 / **테스트 함수 344개
/ 클래스 64개**. 초기 진단은 이것을 "pytest로 만든 커스텀 린터"라 불렀다.
실제로 읽어보니 두 종류가 섞여 있었다:

**(가) 도구로 대체 가능 (소수)**
`test_no_inline_hex_color` · `test_no_raw_backend_access_outside_typed_client`
· `test_no_local_percent_formatting_outside_the_allowlist`
→ ESLint/stylelint/dependency-cruiser 규칙으로 표현 가능

**(나) 도구로 대체 불가능한 도메인 불변식 (다수)**
`test_only_a_fresh_result_can_block_publish` ·
`test_bulk_import_stays_a_single_atomic_put` ·
`test_the_row_component_owns_no_mutation` ·
`test_no_report_number_prefix_construction` ·
`test_both_locales_carry_every_stream_label_leaf`
→ 이건 코드 스타일이 아니라 **제품 규칙**이다. 린터에 그런 개념이 없다

**(다) 메타테스트 — 결정적 발견**
`test_patterns_actually_detect_the_original_defect` ·
`test_the_scan_actually_detects_the_defect` ·
`test_the_virtualization_test_cannot_pass_vacuously` ·
`test_ssot_consumption_check_is_not_satisfied_by_comments` ·
`test_allowlist_does_not_grow` · `test_entries_still_exist_and_still_offend`
(tests/ 전체에 **19개**)

> 이 테스트들은 **자기 자신이 공허하게 통과하지 않는지 검사한다.**
> "이 스캔이 원래 결함을 실제로 잡는가", "예외 등재 항목이 아직도
> 예외를 필요로 하는가", "allowlist가 자라지 않는가".
>
> 범용 린터는 이걸 하지 않는다. 린터 규칙은 자기가 유효한지 스스로
> 묻지 않는다. **이건 부채가 아니라 이 팀이 도달한 성숙도다.**

따라서 (가)만 도구로 이관하고 (나)·(다)는 **보존**한다.
"73K → 30K 감축"은 폐기한다.

### 5.6 evidence 모듈 — 분리가 아니라 수명 관리

13개 모듈 전부 `"""Validate ... evidence metadata."""` 형태이며 docstring이
**"네트워크 호출·DB 연결·파일 쓰기를 하지 않는다"**를 명시한다. dataclass
기반 순수 검증기다.

성격은 배송 거버넌스도 제품 런타임도 아닌 **운영 전환(cutover) 검증 도구**:
db_migration · frontend_deployment · idp_deployment · hardware_smoke ·
rbac_assignment · report_reconstruction · artifact_sync.

순수 함수이고 의존성이 없어 해악이 없다. 분리 비용 > 이득.
→ **전환 완료 후 수명이 다한 것만 폐기**하는 정책만 세운다.

## 7. 상세 설계

### S1. import-linter — 최우선, 즉시 착수 가능

**근거 실측**

| 방향 | 건수 |
|---|---:|
| domain → application/infrastructure | **0** |
| application → infrastructure | **11** (모듈레벨 3 + 함수내 지연 8) |
| infrastructure → domain | 166 (정상) |

순수성을 docstring 자연어로 선언한다("stdlib 만 import"). 그 선언을
**기계가 강제**하게 만드는 것이 S1의 본질이다. 사람이 지불하던 비용을
CI로 넘긴다.

**baseline 운용**: 위반 11건을 등재하고 한 방향으로만 감소시킨다 —
이 조직이 `delivered_test_run_baseline` 에서 이미 쓰는 철학과 동일하므로
새 개념 학습이 필요 없다.

**CI**: `.github/workflows/backend-invariants.yml` 에 한 스텝 추가
(`lint-imports`). 새 워크플로를 만들지 않는다.

### S6. 테스트 마커 재건

현재 선언 6종 대비 실사용:

| 마커 | 사용 |
|---|---:|
| `parametrize` | 81 |
| `bench` | 58 |
| `integration` | **1** |
| `unit`/`hardware`/`database`/`gui`/`invariant` | **0** |

345K줄 테스트를 목적별로 선택 실행할 수 없다는 뜻이다.

**설계**: 파일명 규칙에서 마커를 자동 부착한다 — 납품 상자 `conftest.py`
가 이미 쓰는 `_INVARIANT_FILENAME_TOKENS` 패턴을 확장. 862개 파일에 손으로
마커를 다는 일은 하지 않는다.

```python
# conftest.py
_MARKER_TOKENS = {
    "conformance": "invariant", "invariant": "invariant",
    "parity": "invariant", "bench": "bench",
    "hardware": "hardware", "gui": "gui",
}
def pytest_collection_modifyitems(config, items):
    for item in items:
        name = item.fspath.basename
        for token, marker in _MARKER_TOKENS.items():
            if token in name:
                item.add_marker(getattr(pytest.mark, marker))
```

**CI 레인 분리**: `-m invariant`(빠름, 모든 PR) / `-m "not invariant and
not bench and not hardware"`(단위) / `-m bench`(야간) / `-m hardware`(수동).

### S7. uv + 사설 인덱스

이연 사유(pyproject 주석): *"두 배포물을 담을 인덱스가 아직 없어 해석기가
비교할 대상이 없다"*. → 인덱스 하나가 이 이연을 해소한다.

1. 사설 인덱스 구축 (Gitea Package Registry 또는 Artifactory)
2. `fcc-test-contracts` · `fcc-test-kernel` · `fcc-test-platform` 를
   `uv publish` 로 버전 배포
3. `git+https://…@tag` 직접 참조 → 일반 버전 제약으로 교체
4. `uv.lock` 커밋, CI는 `uv sync --frozen`

**효과**: 배송 상자가 "설치되는가"를 CI가 갓 클론한 러너에서 판정할 수
있게 된다. 지금은 `jsonschema`·`PyJWT` 누락이 로컬에서 안 잡히고 CI에서만
드러난 전례가 pyproject 주석에 기록돼 있다.

## 8. 미해결 — 판정 불가로 남은 것

| 항목 | 왜 판정할 수 없었나 | 판정에 필요한 것 |
|---|---|---|
| **상품화 요구가 실재하는가** | provider 플러그인화·멀티테넌시는 초기 분석자의 추정이었고, 요구사항 문서를 확인하지 못했다 | 이 시스템의 배포 대상이 단일 조직인지 다수 고객인지에 대한 사업 측 확인 |
| **배송 모델 재편** | 분리 목적이 IP 공개범위임은 확인했으나, 사설 인덱스 도입 후에도 추출 매니페스트가 필요한지는 미판정 | S7 완료 후 재평가 |
| **Alembic 전환** | 기존 손번호 SQL 체계의 설계 근거를 확인하지 못했다 | `infrastructure/database/migrations/` 실사 |
| **평문 HTTP / TLS** | platform-api 이중 인스턴스는 인증서 확보 시 되돌리기로 이미 결정돼 있음 | 사내 인증서 발급 일정 |
| **프론트 통합** | `web/platform-shell` 과 `apps/web` 의 역할 분담 근거 미확인 | 두 표면의 사용자·목적 확인 |

## 9. 이 문서가 남기는 한 문장

> FCC는 **구조가 아픈 시스템이 아니라, 규율을 사람이 손으로 지불하고 있는
> 시스템**이다. 640K LOC에서 도메인 레이어 위반이 0건이고 서드파티 오염이
> 0건인 것은 도구가 막아서가 아니라 **팀이 매번 지켜서**다.
>
> 따라서 할 일은 그 규율을 바꾸는 것이 아니라, **기계에게 넘겨주는 것**이다.
> import-linter 계약 20줄이 344개 순응 테스트를 대체하지는 못하지만,
> 344개가 감시하지 않는 레이어 경계를 무료로 지켜준다.
