## 1. 0단계 — 당신 레포에 «환경» 부터 세우십시오

코드를 만지기 전에, 당신 레포의 에이전트가 **매 세션 규칙을 받도록** 만듭니다.
이것을 건너뛰면 나머지 전부가 「한 번은 지켜지고 다음엔 안 지켜지는」 상태가 됩니다.

### 왜 이것이 먼저인가 — 실측된 실패

> `fcc-test-platform` 은 2026-09-07 이전까지 **매 세션 로드되는 규칙이 0개**였습니다.
> `.claude/rules/` 에 파일 셋이 있었지만 전부 `paths:` 조건부여서, **그 경로를 만지지
> 않는 세션에는 한 글자도 로드되지 않았습니다.** 그 자리를 개인 auto memory 98개가
> 메우고 있었고, **auto memory 는 기계-로컬이라 동료 PC 로 하나도 가지 않습니다.**

**규칙이 있는 것과 규칙이 «도달하는» 것은 다른 명제입니다.**

### 📋 복붙 ① — 환경 세우기

```
이 레포를 FCC 중앙 플랫폼의 provider 레인으로 만들려고 한다.
docs/PROVIDER-KICKOFF.md 를 읽었다.

먼저 «환경» 부터 세워줘. 다음 넷을 만든다:

1. 루트에 CLAUDE.md — 200줄 이하. 이 레포가 무엇인지, 이 레포가 지켜야 하는 경계,
   그리고 「매 세션 참인 것」만 넣는다. 특정 경로에서만 참인 것은 넣지 마라.
   ⚠️ 반드시 포함할 것:
     - 이 레포는 provider 레인이고, 분야 지식(측정·시험계약)의 «주인» 이다
     - 중앙 플랫폼(fcc-test-platform)에 우리 소스를 두지 않는다. 이미지로만 간다
     - 계약 아티팩트는 «여기서» 발행한다. 중앙 트리에 복사하지 않는다
     - provider_id 는 계약 SSOT 에서 «읽어서» 쓴다. 문자열로 박지 않는다

2. .claude/rules/ — 경로별 규칙. 각 파일 맨 위에 paths: frontmatter 를 둔다.
   ⚠️ 모든 세션에 참인 것을 여기 쓰지 마라 — 조건부라서 필요한 순간에 도달하지 않는다.

3. intent/ — 기능 개발의 앞문. 아래 §2 의 서식을 쓴다.

4. .claude/skills/ — 반복 절차. 예: 「계약 검사 돌리기」, 「이미지 빌드·이관」.
   skills 는 필요할 때만 로드되므로 절차를 여기 두면 CLAUDE.md 가 짧아진다.

각 파일을 만들기 전에 «무엇을 왜 그 위치에 두는지» 를 한 줄로 설명하고,
내가 승인하면 쓴다. 한 번에 다 쓰지 마라.
```

### 무엇을 어디에 두는가 — 판단 규칙

| 이 사실은… | 어디에 | 이유 |
|---|---|---|
| 모든 세션에 참 + 팀이 알아야 함 | **`CLAUDE.md`** | source control 로 공유된다 |
| 특정 경로에서만 참 | **`.claude/rules/` + `paths:`** | 그 파일을 읽을 때 로드 |
| 여러 단계의 절차 | **`.claude/skills/`** | 필요할 때만 로드 → 컨텍스트 절약 |
| **막아야** 하는 것 | **hook** | `CLAUDE.md` 는 강제 계층이 «아니다» |

⚠️ 공식 문서 원문 — *"Claude treats them as context, **not enforced configuration**.
To block an action regardless of what Claude decides, use a PreToolUse hook instead."*

## 2. intent / spec / plan — 기능 개발의 앞문

중앙 플랫폼은 2026-09-07 부터 이 흐름을 씁니다. **당신 레포에도 같은 것을 세우면
두 트랙에서 같은 습관을 쓸 수 있습니다.**

| 파일 | 답하는 질문 | 초안 | 승인 |
|---|---|---|---|
| `intent.md` | **왜** 이걸 하나 | 에이전트 | 동료 1인 (작성자 제외) |
| `spec.md` | **무엇을** 어떤 설계로 | 에이전트 | 동료 1인 |
| `plan.md` | **어떻게** — 어느 파일을 어떤 순서로 | 에이전트 (plan mode) | 개발 담당자 |

> **초안은 전부 에이전트가 쓰고, 사람은 승인만 합니다.**
> 사람이 초안을 쓰면 속도의 이득이 사라지고, 사람이 승인을 안 하면 책임이 사라집니다.

**규칙 본문의 SSOT 는 `fcc-test-platform:intent/README.md` 입니다.** 서식은
`intent/_templates/` 에 있습니다 — 베껴 오되, **승인 모델은 당신 팀의 인원에 맞게
다시 정하십시오.** 그것은 플랫폼의 결정이지 보편 규칙이 아닙니다.

### 📋 복붙 ② — intent 흐름 가져오기

```
중앙 플랫폼 레포(https://github.com/junnv93/fcc-test-platform)의
intent/README.md 와 intent/_templates/ 를 읽고, 이 레포용으로 옮겨줘.

⚠️ 그대로 베끼지 마라. 다음을 우리 상황에 맞게 «다시» 정해야 한다:
  - 승인자가 누구인가 (우리 팀 인원이 몇 명인가에 달렸다)
  - 「방아쇠」 다섯 중 우리에게 해당하는 것은 무엇인가
  - 우리 레포에서 «되돌릴 수 없는 경로» 는 어디인가

그리고 각 항목에 대해, «오늘 그것을 강제하는 것이 있는가» 를 실측해서 적어줘.
없으면 「기록이지 게이트가 아니다」라고 명시해라 — 없는 강제를 있다고 적으면
다음 사람이 그것을 믿는다.
```

⚠️ **적용하지 않는 것**: 오탈자 · 명백한 버그 한 줄 · 이미 승인된 spec 안의 후속 수정.
**전부에 요구하면 형식이 되고, 형식이 되면 아무도 안 읽습니다.**

## 3. ① 계약 적합성 — 검사는 «당신 레포에서» 돕니다

### 운영자 판정 (2026-08-31)

> **아티팩트는 발행처에 머문다.** provider 가 자기 레포에서 자기 계약을 검사하고,
> 중앙은 **그 결과만** 받는다.

기각된 둘: **URL 발행**(검사가 네트워크에 의존 → 오프라인·재현성이 깨짐),
**중앙 트리로 복사**(→ `90-known-traps.md` §1 — **가장 쉽고 가장 나쁜 길**).

### 📋 복붙 ③ — 계약 적합성 시작

```
FCC 계약 커널을 설치하고, 우리 headless API 가 계약을 만족하는지 검사하는
파이프라인을 세워줘.

  pip install "fcc-test-contracts @ git+https://github.com/junnv93/fcc-test-contracts@<태그>"

⚠️ 두 레인은 public 이므로 토큰이 필요 없다. 태그는 브랜치가 아니라 «태그» 로 핀해라.

1. 설치된 패키지 안의 fcc_test_contracts/artifacts/provider_onboarding.md 를
   «읽어서» 절차를 따라라. 이 문서에 요약된 것을 믿지 말고 원문을 읽어라.

2. ⚠️ 스키마가 아니라 «예시 계약» 에서 출발해라 —
   fcc_test_contracts/artifacts/*_headless_api_contract.example.json

3. 검사를 우리 CI 에 붙여라. 로컬에서만 도는 검사는 잊혀진다.

4. ⚠️ 검사를 만든 뒤, «일부러 깨진 입력을 주입해서» 빨개지는지 확인해라.
   빨개지지 않으면 그 검사는 없는 것과 같다. 주입이 «착지했는지» 부터 확인해라 —
   공허한 주입은 성공한 주입과 같은 모양이다.

5. 우리 계약 아티팩트를 이 레포에서 export 하는 진입점을 만들어라.
   ⚠️ 그것을 중앙 레포에 복사하지 마라. 중앙 레지스트리가 «가리킬» 뿐이다.
```

### 중앙 레지스트리에 등재하기

당신 아티팩트가 준비되면 `fcc-test-platform:config/headless_provider_registry.json` 에
한 줄이 추가됩니다:

```json
{
  "provider_id": "<자연키>",
  "product_line": "<제품군>",
  "contract_family": "<계약 패밀리>",
  "contract_artifact": "<당신 아티팩트의 위치>"
}
```

⚠️ **`contract_artifact` 가 가리키는 파일이 해소되지 않으면 레지스트리 «전체» 가
로드에 실패합니다**(`providers: []`). 증상은 *「내 provider 만 안 보인다」* 가 아니라
*「전부 안 보인다」* 입니다.

⚠️ **`provider_id` 는 «자연키» 입니다. UUID 가 아닙니다.** 이것을 UUID 로 착각한
회귀가 2026-08 에 실제로 있었습니다 → `90-known-traps.md` §2.

## 4. ② headless API — 당신 분야의 «시험 지식» 서비스

### 왜 당신이 만들어야 하나

중앙에서 **provider 저장소를 실제로 필요로 하는 서비스는 이것 하나**입니다.
실측(중앙 compose 주석, 도는 컨테이너 안에서, 2026-09-03):

```
sys.path 에서 /app/src 를 빼면
  platform-api   → 휠만으로 조립된다 (OpenAPI 경로 동일)
  headless-api   → ModuleNotFoundError
```

그리고 그 표면이 무엇인지 보면 이유가 드러납니다 — 실측 **36 경로**
(`docs/api/headless-api.openapi.json`, Unlicensed 기준):

| 무엇 | 개수 | 왜 분야 지식인가 |
|---|---|---|
| 시험계획 저작 | 16 | *유효한 시험계획 행이란 무엇인가* — 분야마다 완전히 다르다 |
| 성적서 | 7 | *성적서에 무엇이 들어가는가* |
| 세션 결과 조회 | 5 | |
| 자기 선언 | 4 | `capabilities` · `ui-descriptor` · `api-contract` · `status` |
| 작업(job) | 3 | |
| 헬스체크 | 1 | |

⚠️ **`ui-descriptor` 를 주목하십시오.** 웹 화면이 *당신 분야에 대해* 무엇을 보여줘야
하는지를 **당신이 선언**합니다. 그래서 프런트엔드가 플랫폼에 있으면서도 분야 중립일 수
있습니다. 플랫폼은 당신 분야를 알 수 없고, **알아서도 안 됩니다** — 알게 되면
provider 가 늘 때마다 플랫폼을 고쳐야 합니다.

### 이미지로만 건너갑니다

중앙 compose 실측:

```yaml
headless-api:
  image: ${FCC_HEADLESS_IMAGE:-fcc-unlicensed-headless-api:latest}
  #  ⚠️ build: 스탠자가 «없다»
```

`build:` 가 있으면 중앙 PC 에 당신의 소스 트리가 있어야 하고, 그러면 경계가 무너집니다.

### 📋 복붙 ④ — headless 이미지

```
우리 headless API 를 중앙에 넣을 이미지로 만들어줘.

만족해야 하는 성질 (참고할 실물은 비공개라 «성질» 로만 주어졌다):
  - 진입점이 «하나» 다.  uvicorn --factory <우리 모듈>:create_app --host 0.0.0.0 --port 8001
    ⚠️ 플랫폼 진입점까지 담으면 경계가 이미지 «안에서» 무너진다.
  - 플랫폼 소유 자산(마이그레이션 러너 등)을 «포함하지 않는다».
  - 헬스체크는 표준 라이브러리로 짠다 — slim 이미지에 curl 이 없다.
  - org.opencontainers.image.revision 라벨을 «반드시» 넣는다:
        --build-arg GIT_REVISION="$(git rev-parse HEAD)"

⚠️ 「headless 전용」은 «진입점» 을 뜻하지 «의존 폐포» 를 뜻하지 않는다.
   실물도 fcc-test-platform 휠을 «설치한다» — headless 표면이 그것을 모듈 레벨로
   import 하기 때문이다. 의존을 줄이려다 이미지를 깨뜨리지 마라.

⚠️ 의존성 설치는 «분리» 해라 — 서드파티는 정상 resolve, git+ 레인만 --no-deps.
   한 번에 resolve 하면 두 레인이 서로를 핀해서 ResolutionImpossible 이 난다.
   ⚠️ 그리고 그 규칙이 Dockerfile «안에만» 있으면, Dockerfile 이 없는 레인
   (챔버 PC 등)은 그것을 받지 못한다. 어디에 쓸지 같이 정해라.

이관:
   docker save <이미지>:latest -o headless-api.tar     # 개발 PC
   docker load -i headless-api.tar                     # 중앙 PC
   ⚠️ docker compose up -d 만으로는 새 이미지가 안 붙을 수 있다 — 같은 태그면
      캐시가 조용히 재사용된다. 컨테이너를 «재생성» 하고 리비전 라벨로 확인해라.
```

### 🔴 `:latest` 는 「재빌드했는가」에 답하지 않습니다

폐쇄망에는 레지스트리가 없어 `docker save`/`load` 로 옮기고, 그러면 낡은 것도 새것도
**같은 태그**입니다. 실측(2026-09-04): `:latest` 가 하루 전 코드였고 의존성도 낡았는데
**컨테이너는 `healthy` 였습니다** — 낡은 코드와 낡은 의존성이 서로 정합했기 때문입니다.
**아무것도 실패하지 않습니다.**

```bash
docker inspect <이미지> --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
```

## 5. ③ 챔버 노드 — 계측기를 잡는 쪽

### 계약은 **6 경로**입니다 (`docs/api/session-api.openapi.json`)

```
GET   /session/info          API 버전 + 오퍼레이션 카탈로그
GET   /session/is-running    지금 측정 중인가
GET   /session/progress      진행률
POST  /session/start         측정 시작
POST  /session/stop          측정 중지
POST  /session/workbook      .xlsx 업로드 → «불투명 핸들» 반환
```

⚠️ **`/session/workbook` 의 설계를 그대로 따르십시오.** 계약 원문 —
*"노드가 바이트를 어디에 둘지 정한다. 핸들이 `start_session` 이 받는 유일한 것이고,
따라서 **클라이언트가 파일시스템 경로를 이름으로 부르는 일이 없다.**"*
경로를 주고받게 만들면 중앙이 챔버의 디스크 구조를 알게 되고, 분야 중립성이 깨집니다.

### 📋 복붙 ⑤ — 챔버 노드

```
우리 측정 프로그램을 챔버 노드로 만들어줘. 중앙이 부를 HTTP 표면 6개를 붙인다.

⚠️ 경로를 하드코딩하지 마라. 계약(session-api.openapi.json)에서 «파생» 해라.
   중앙 쪽 어댑터(chamber_proxy_adapter.py)도 그렇게 하고 있고, 두 쪽이 같은 SSOT 를
   봐야 함께 움직인다.

⚠️ /session/workbook 은 «불투명 핸들» 을 돌려준다. 파일 경로를 돌려주지 마라.

⚠️ provider_id 는 계약 패키지에서 «읽어서» 쓴다. 문자열 리터럴로 박지 마라.
   그리고 값이 «있으면» 통과시키지 말고 계약 SSOT 와 «대조» 해라 —
   틀린 값이 실장비에서 통과한 사고가 있다.
   ⚠️ 계약 패키지를 못 읽으면 «통과» 가 아니라 «검증하지 못했다» 로 말해라.

Windows 에서 돌 것이므로:
  - 설정 파일을 읽을 때 -Encoding UTF8 을 «명시» 해라 (BOM 없는 UTF-8 이 ANSI 로
    읽히면 한글이 깨지고, 최악의 경우 «키 하나가 통째로 사라진다»)
  - 콘솔 QuickEdit 를 끄거나 서비스로 돌려라 (창을 «클릭» 하면 프로세스가 얼고,
    밖에서 보면 「죽지 않았는데 죽은 것」이 된다)
```

### 챔버는 «분야 중립» 입니다

`chamber_nodes` 표의 최종 컬럼 **11개**에 **시험 종류를 적는 칸이 없습니다**(실측).
한 챔버에서 여러 분야를 할 수 있고, 챔버 자격증명은 하나입니다.
분야는 `FCC_CENTRAL_PROVIDER_ID` 라는 **다른 칸**에 있습니다.

### 자격증명은 «파생» 됩니다

```
chamber_client_id(chamber_id) = "fcc-chamber-" + chamber_id
```

⚠️ **`chamber_id` 를 client id 로 그대로 쓰지 마십시오.** 실장비에서 그렇게 됐고,
노드가 **존재하지 않는 이름으로** 토큰을 요청했습니다. 증상 `invalid_client` 는
**「client 없음」과 「secret 회전」에 같은 답**이라 사후에 원인을 못 가리고,
화면에는 그저 **Offline** 으로 보입니다.

⚠️ **프로비저닝을 두 번 돌리지 마십시오** — secret 이 회전해 배포된 값이 죽습니다.

### `jwks_uri` 를 중앙에서 물어서 가져오지 마십시오

`KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` 라서 **중앙에서 물으면 `localhost` 가 나옵니다.**
그 값을 챔버에 넣으면 노드가 **자기 자신에게** JWKS 를 요청합니다.
**설정은 형식상 완전하고 값도 그럴듯하며, 런타임에만 틀립니다.**

챔버가 쓸 값: `http://<중앙 IP>:<keycloak 포트>/realms/<realm>/protocol/openid-connect/certs`

## 6. 검증 순서 — 되돌리기 어려운 것 «앞» 에 공짜인 것을 두십시오

```
 ① 계약 검사        당신 CI      아무것도 안 건드림
 ② 이미지 빌드      당신 PC      로컬
 ③ 이미지 load      중앙        되돌릴 수 있음 (태그 보존)
 ④ compose up       중앙        컨테이너만
 ⑤ 챔버 프로비저닝   챔버 PC     ⚠️ 파일·방화벽·ACL 변경 — 되돌리기 비싸다
 ⑥ 노드 기동        챔버 PC
 ⑦ 연결 확인        양쪽
```

⚠️ **⑤ 는 반드시 `-ValidateOnly` 를 먼저 돌리십시오.** 실측(2026-09-04): 그 단계가
**여섯 개의 결함을 아무것도 안 건드린 상태에서** 하나씩 드러냈습니다. 그냥 설치했다면
파일이 깔리고 방화벽이 열린 뒤에 실패해, **반쯤 설치된 상태에서** 원인을 찾아야 했습니다.

### 각 단계의 판정

```
③ docker images <태그>                          + 리비전 «라벨» 대조 (태그로는 판정 불가)
④ docker ps                                     Up 인가
⑥ curl http://<챔버 IP>:<포트>/session/health    {"status":"ok",...}
⑦ chamber_nodes 행 + heartbeat 신선도
```

⚠️ **⑥ 은 반드시 «네트워크 주소» 로 재십시오.** `127.0.0.1` 로만 재면
**「떠 있다」와 「밖에서 쓸 수 있다」를 구분하지 못합니다.**

⚠️ **포트는 방화벽 «승인 집합» 안에서 고르십시오.** 승인은 PC 마다 따로 납니다.
밖의 포트를 고르면 노드는 정상 기동하고 heartbeat 도 가는데 **중앙→노드 forward 만**
막힙니다 → 「살아 있는데 조용함」.

⚠️ **`base_url` 도 같은 증상을 만듭니다.** heartbeat 는 챔버→중앙이라 **성공**하고
중앙→챔버만 막힙니다.

## 7. 보고할 때 — 「관측 못 함」을 「없음」으로 쓰지 마십시오

같은 이름의 컨테이너가 여러 기계에서 돌므로 `docker ps` 출력이 **완전히 같은 모양**
입니다. **2026-09-04 라운드에서 세 세션이 각자 다른 기계를 재고 같은 이름으로
보고했습니다.**

**보고에 측정 기계 주소를 명시하십시오.** 그리고 WSL 의 `hostname -I` 는 NAT 때문에
거짓을 말할 수 있습니다.

## 8. 아직 답이 없는 것들 — 당신이 부딪힐 수 있습니다

| 무엇 | 상태 |
|---|---|
| 이미지 태그 규약 | **미정.** Unlicensed 는 `:latest` + 리비전 라벨로 간다 |
| 적합성 증거 채널 | 2026-09-04 착지. 최신은 `config/provider_conformance_evidence/` |
| 챔버 노드 서비스화 | 지금은 포그라운드 콘솔. 옮기려면 「계측기 락이 서비스 계정과 시험원 계정 사이에서 성립하는가」가 선행 |
| 접두사 중립화 (`fcc-chamber-`) | 알려진 부채. **다른 provider 가 붙기 전이 유일하게 싼 시점** |
| 외부 provider 아티팩트 해소 규칙 | 판정은 났으나(§3) **구현 미착수** — 당신이 첫 사례가 됩니다 |

⚠️ **마지막 줄이 중요합니다.** 오늘 등재된 provider 셋은 전부 **우리가 발행한 것**
(실물 1 + 예시 2)이라 검사가 **구조적으로 통과할 수밖에 없습니다.**
**당신이 붙는 날 그 전제가 사라집니다.** 초록을 봤다고 안심하지 마십시오 —
그 초록이 무엇에 대한 것인지 물으십시오.
