# 트랙 B — 플랫폼 공동개발

> 대상: `fcc-test-platform` 에 PR 을 내게 될 사람.
> **트랙 A 와 규율이 다릅니다.** 여기서 당신은 *분야 지식의 주인*이 아니라
> *분야 중립 규율의 준수자*입니다.

---

## 1. 이 레인에서 무엇이 참인가

**여기에 측정 코드는 없습니다.** 스펙트럼 분석기 제어 · EUT 제어 · Excel 시험계획 ·
GUI 는 전부 provider 비공개 레포에 남습니다. 이 레포가 아는 것은
*어느 분야인지 무관하게 참인 것* — 프로젝트 · 챔버 · 세션 · 결과 · 성적서 — 뿐입니다.

**무엇을 어디에 둘지 헷갈릴 때 물어야 하는 질문은 하나입니다:**

> **이것은 분야 지식인가, 아니면 분야와 무관하게 참인 것인가?**

분야 지식이면 여기 두지 마십시오. 두면 provider 가 늘 때마다 이 레포를 고쳐야 합니다.

## 3. 기능 작업은 `intent/` 에서 시작합니다 (2026-09-07~)

새 기능 · 동작 변경 · 외부에 보이는 변화는 **코드보다 먼저**
`intent/<slug>/intent.md` 를 만들고 **사람의 승인(PR 머지)** 을 받습니다.

```
intent/<슬러그>/
   ├── intent.md      왜        →  브랜치 intent/<슬러그>   동료 1인 승인
   ├── spec.md        무엇을     →  브랜치 spec/<슬러그>     동료 1인 승인
   └── plan.md        어떻게     →  브랜치 feature/<슬러그>  개발 담당자
```

**규칙 본문 SSOT → `intent/README.md`.** 서식 → `intent/_templates/`.
이 문서와 어긋나면 **그 파일이 맞습니다.**

### 승인은 «예외 승인» 입니다

기본은 **동료 1인**(작성자 제외)이고, **리드는 상시 승인자가 아니라 예외 판단자**입니다.
기계가 판정하는 **방아쇠 다섯**이 걸릴 때만 사람의 결정이 요구됩니다:

| # | 걸리는 조건 | 초록이 되는 조건 |
|---|---|---|
| T1 | `migrations/` · `infra/` · 커널 핀 · 인증/RBAC · **게이트 자신**을 건드림 | `CODEOWNERS` — ⚠️ 오늘 «기록»이지 게이트가 아님 |
| T2 | 기준선에 **실패 이름 추가** (= 부채 등재) | `Debt-Accepted-By: <이름> — <사유>` |
| T3 | `spec.md` 에 **답 없는 열린 질문** | `→ 답(<이름>): <내용>` |
| T4 | `plan.md` 표에 **없는 파일**이 diff 에 있음 | 표에 추가 또는 `Scope-Extended-By:` |
| T5 | 변경 파일 수가 선언의 **2배 초과** | T4 와 같음 |

⚠️ **방아쇠는 «알림» 이 아닙니다.** 알림은 무시할 수 있고, 무시된 알림은 **없는 알림과
같은 모양**입니다. 그래서 이 축은 **아티팩트 안에 이름 붙은 결정이 적히기 전까지
검사가 초록이 되지 않는** 형태입니다.

### ⚠️ 적용하지 «않는» 것

오탈자 · 명백한 버그 한 줄 · 이미 승인된 `spec.md` 안의 후속 수정.
**전부에 요구하면 형식이 되고, 형식이 되면 아무도 안 읽습니다.**

### 📋 복붙 ② — 의도 만들기

```
intent/_templates/intent.md 서식으로 새 intent 를 만들어줘.
문제는: (겪은 문제를 «그냥 말로» 쓰세요)

⚠️ 해결책을 문제로 쓰지 마라. 「배지를 추가해야 한다」는 문제가 아니라 이미 정해진
   해결책이고, 그 문장으로는 다 만든 뒤에 됐는지 «판정할 수 없다».
   「누가 · 무엇을 못 해서 · 어떤 비용이 나는지」를 써라.

⚠️ Open questions 를 「없음」으로 비우지 마라.
   열린 질문이 하나도 없는 의도는 대개 «덜 생각한» 의도다.

⚠️ 이 레포는 PUBLIC 이다. 고객·의뢰자를 실명이나 연락처가 아니라 «역할» 로 써라.
```

⚠️ 커밋 규율:

## 4. 게이트 — 무엇이 «진짜» 막나

| 층 | 어디서 | 무엇을 막나 | 우회 |
|---|---|---|---|
| L0 | `CLAUDE.md` | (막지 않음) 규칙을 **도달**시킴 | — |
| L1 | Claude Code 훅 | 세션 안의 편집 | 설정 삭제 |
| L2 | `githooks/pre-commit` | 브랜치·claim 바인딩 | `--no-verify` |
| L3 | `githooks/pre-push` → `lane_check.py` | 형식·짝·상태 위반 | `FCC_SKIP_LANE_CHECK=1` |
| **L4** | **서버 branch protection** | **승인 없는 `main` 착지 · `lane-check` red** | **불가능** |

⚠️ **L1~L3 은 실수 방지층이지 방어층이 아닙니다.** 셋 다 우회할 수 있습니다 —
로컬 PC 에서 도는 것은 그 PC 의 주인이 끌 수 있기 때문입니다.

**실제로 강제되는 것은 L4 하나뿐입니다.** 실측(2026-09-07):

```
required_status_checks.contexts   = ["lane-check"]
enforce_admins                    = true      ← 관리자도 우회 못 한다
required_approving_review_count   = 0         ← ⚠️ 승인 없이 머지된다
require_code_owner_reviews        = false     ← CODEOWNERS 는 «막지 않는다»
```

⚠️ **그래서 「동료 1인 승인」은 오늘 사람이 지키는 규율이지 기계가 막는 게이트가
아닙니다.** 그 사실을 알고 지키십시오. 「검사가 통과했으니 승인된 것」이 아닙니다.

### 그러면 L0~L3 은 왜 만드나

**막기 위해서가 아니라, 우회할 이유가 없게 만들기 위해서**입니다.
올바른 길이 가장 쉬운 길이면 아무도 벗어나지 않습니다. 게이트가 오탐을 내거나
짜증나면 사람들은 `--no-verify` 를 배우고, **그날부터 그 게이트는 0층이 됩니다.**

### `lane_check` 은 «이름 집합» 으로 판정합니다

```bash
python3 scripts/lane_check.py --root .
```

「전부 통과」가 아니라 **관측된 실패 «이름 집합» == 선언**을 봅니다.

* **개수가 아니라 이름입니다** — 하나 고치고 하나 깨뜨리면 개수는 같습니다.
* 이 레인의 선언된 실패는 **0** 입니다 (`delivered_test_run_baseline.json`).
  실패를 보면 그것은 **당신 환경 문제이거나 새로 깨진 것**입니다.
* ⚠️ **새 실패를 기준선에 추가하지 마십시오.** 추가는 **부채 등재**이고 별도 승인
  사항입니다(T2).

## 5. 커밋 위생 — 셋 다 차단형이고 서로 독립입니다

### 5-1. Explicit-files commit

```bash
git add <파일...>          # ✅
git add -A                 # ❌ 금지
git add .                  # ❌ 금지
```

여러 세션이 한 저장소를 만지므로 **bulk staging 은 다른 세션의 파일을 실어 나릅니다.**

### 5-2. No-squash merge

```bash
gh pr merge <N> --merge    # ✅
gh pr merge <N> --squash   # ❌ 금지
```

`--squash` 는 커밋 본문을 PR 설명으로 **대체**해, 각 커밋에 실린 17항목 자가점검이
**착지 커밋에서 사라집니다.** 푸시 뒤에는 고칠 수 없습니다.

### 5-3. Merge base 신선도

```bash
python3 scripts/merge_readiness_guard.py merge <PR번호> --update
```

판정식은 `git log <base> --not <head> --no-merges` 가 **0줄**이고, `--is-ancestor` 가
**아닙니다.**

⚠️ **`CLEAN` 은 «그때의 base» 에 대한 진술입니다.** CI 는 머지 ref 를 보지만
base 가 움직여도 다시 돌지 않습니다. **머지 직전에 다시 물으십시오.**

### 5-4. 17항목 자가점검

커밋 메시지에 `^[A-D]-[1-5]:\s+(PASS|SKIP|N/A)` **물리 17줄** + 끝에
`Self-Audit: 17-items` 트레일러. **상태 뒤에 «사유» 가 없으면 거부됩니다.**

⚠️ **SKIP 도 «주장» 입니다.** 관성으로 채웠다가 틀린 사례가 있습니다.
판정 SSOT → `scripts/self_audit_message.py` · 정의 → `.claude/contracts/sprint-self-audit-checklist.md`.

## 6. 공유 체크아웃 — 「미커밋 파일」이 당신 것이 아닐 수 있습니다

```bash
git worktree list                       # 지금 누가 무엇을 하는가 «먼저»
git fetch origin
git diff origin/main --stat             # ⚠️ git status 만 보지 마라
git push origin HEAD:refs/heads/<이름>   # ⚠️ 브랜치를 «바꾸지» 마라
```

`git status` 는 **어느 참조점에 대해** 묻는지 말해 주지 않습니다.
낡은 `HEAD` 는 **이미 착지한 남의 파일**을 「내 미커밋 변경」으로 보이게 합니다.

⚠️ **워크트리는 `.git/config` 를 공유합니다.** 한 세션이 훅을 끄면 **모든 세션에서
꺼집니다.** 훅이 사라졌다면 옆 세션일 수 있습니다.

⚠️ **판정을 내렸으면 그 파일을 소유한 세션에도 직접 알리십시오.**

## 7. 새 검사를 붙일 때

### 반드시 «테스트 파일» 로 붙이십시오

이 레인의 실질 게이트는 `githooks/pre-push` → `lane_check.py` → **pytest** 입니다.
**워크플로 스텝에만 넣으면 로컬 push 를 막지 못합니다.**

### 그리고 «이빨» 을 확인하십시오

```
새 검사를 만들었으면, 일부러 깨진 입력을 «주입» 해서 빨개지는지 확인해라.
⚠️ 그 주입이 «착지했는지» 부터 확인해라 — 한 세션에서 주입이 세 번 공허했던 기록이
   있다. 공허한 주입은 성공한 주입과 «같은 모양» 이다.
```

### 검사기가 못 보는 것들

| 방식 | 못 보는 것 |
|---|---|
| 줄 단위 정규식 | **여러 줄로 쪼개진 표현.** 「없다」와 「못 봤다」의 출력이 같다 → **AST 로** |
| 문자열 존재 검사 | **산문을 코드로 센다.** 주석·문서가 통과시킨다 → 호출·인자는 **AST 로** |
| 존재 축 봉인 | 도구가 «출력하는» 문자열은 못 본다 |
| 접두사 매치 | 무엇을 셌는지 말하지 않는다 (「84」가 실은 24였던 사례) |
| 스칼라 장부 | **범위 확대를 회귀처럼 보이게 한다** → 집합으로 두어라 |

⚠️ **집합은 «선언에서 파생» 하십시오.** 손으로 열거한 목록은 반드시 하나를 놓치고,
놓친 그것이 사고가 됩니다. 「무엇이」는 파생하고 「어디」만 적어 두면
**이사한 날 조용해지지 않습니다.**

## 8. 커널을 만질 때 — 2-레포 작업입니다

```
① fcc-test-contracts 에서 고친다
② 태그를 «낸다»                    ← ⚠️ 사람의 승인이 필요한 지점
③ fcc-test-platform 의 핀을 올린다
④ platform 에서 소비를 확인한다
```

⚠️ **핀은 «태그» 입니다. 브랜치가 아닙니다.** 태그를 안 내면 platform 은 그 변경을
**보지 못합니다.**

⚠️ **태그를 내기 전에 «핀만으로 만든 venv» 에서 재십시오.** `.pth` 기법은 editable
설치 앞에서 무력하고, `.pth` 꼬리는 `pip` 를 **조용히 no-op** 시킵니다.

⚠️ **어떤 결함은 «소비 레인에서만» 보입니다.** 커널 레인 전량이 초록이어도
platform 에서 깨질 수 있고, 그 갈라짐은 **양방향**입니다.

⚠️ **형제 세션이 버전 번호를 먼저 가져갈 수 있습니다.** 같은 줄이라 git 이 조용히
병합합니다. **이미 나간 태그를 옮기지 마십시오.**

## 9. 판정하기 전에 — 이 레포가 반복해 틀린 방식

| 하려는 판정 | ❌ 틀린 방법 | ✅ 맞는 방법 |
|---|---|---|
| 「이 파일이 어디서 왔나」 | 문서의 이사 기록을 읽는다 | **저쪽 이름으로 실제 확인** — 세 문서가 원을 그린 사례가 있다 |
| 「이 진입점이 무엇을 읽나」 | grep | **실행해 본다** |
| 「이 태그에 무엇이 실렸나」 | 그래프·트리를 본다 | **설치해 본다** — 그래프는 거짓 음성, 트리는 `version` 줄을 놓친다 |
| 「이 핀들이 해석되나」 | 선언을 읽는다 | **설치를 돌린다** — 서로를 배제해도 선언만 보면 안 보인다 |
| 「이것이 없다」 | `is_dir` · 이름으로 판단 | **내 도구가 어디까지 봤는지 함께 적는다** |
| 「이 red 가 내 탓인가」 | 바로 결론 | **다른 rig 로 다시 잰다** — 같은 커밋이 61·1·0 을 냈다 |
| 「A 를 고쳤더니 B 가 좋아졌다」 | 둘 다 움직인 채로 잰다 | **하나를 고정한다.** 기준선은 merge-base 로 |
