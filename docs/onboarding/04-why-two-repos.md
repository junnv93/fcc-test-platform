# 왜 저장소가 나뉘어 있나 — 각각의 성격과 역할

> **「저장소가 왜 이렇게 여러 개인가」는 신규 합류자가 가장 자주 하는 질문입니다.**
> 그리고 이 답을 모르면 **무엇을 어디에 넣을지 매번 틀립니다.**
>
> 비유를 쓰지 않고, **결정문 원문과 실측값**으로 씁니다.

## 2. 「운영 분리」와 「저장소 분리」는 **다른 결정**입니다

여기가 이 구조를 이해하는 열쇠이고, 대부분의 사람이 처음에 섞습니다.

결정문(ADR-0018 D-1) 원문:

> **런타임/운영 분리**(provider·platform 이 별도 프로세스/컨테이너/DB 로 가동)는
> **이미 달성**됐다. … **소스 레포 분리**는 배포가 아니라 **팀 협업·접근권한·독립
> 릴리스 주기**를 위한 **별개** 결정이다. **monorepo 도 N 개 독립 서비스를 배포할 수
> 있다.** 따라서 레포 분리는 "운영 필요" 가 아니라 **"독립 개발 필요"** 가 트리거다.

| | 무엇을 나누나 | 왜 |
|---|---|---|
| **운영 분리** | 프로세스 · 컨테이너 · DB | 하나가 죽어도 나머지가 산다. 따로 배포한다 |
| **저장소 분리** | 소스 코드가 사는 곳 | **서로 다른 팀이 서로를 기다리지 않고 일한다** |

**한 저장소 안에서도 컨테이너 7개를 띄울 수 있습니다.** 실제로 예전에 그랬습니다.
그러므로 「따로 배포하니까 저장소도 나눠야 한다」는 **틀린 추론**입니다.

---

## 3. 그러면 왜 나눴나 — provider 가 «여럿»이 되기 때문입니다

```
   오늘                                    앞으로
   ────                                    ──────
   provider 1개 (Unlicensed)               provider 여럿 (KC · mmWave · licensed …)
   = 우리 팀 하나                            = 팀이 여럿
                                            = 각자 «비공개» 저장소를 갖는다
```

각 provider 팀은 **자기 측정 코드를 남에게 보여주지 않습니다.** 그런데
**같은 웹 플랫폼**을 씁니다. 그러면 세 가지가 필요합니다:

1. **공유하는 약속** — 「이렇게 요청하면 이렇게 답한다」 → `fcc-test-contracts`
2. **공유하는 플랫폼** — 화면·DB·인증·성적서 → `fcc-test-platform`
3. **각자의 비공개 코드** — 측정·시험계획·성적서 내용 → 각 provider 저장소

**셋을 한 저장소에 두면, 남의 팀 코드를 보지 않고는 일할 수 없게 됩니다.**

---

## 4. ⚠️ 그런데 「빨리 나누는 것」이 «해롭다»고 결정문은 말합니다

이것이 이 프로젝트에서 배울 만한 판단입니다. ADR-0018 D-2 원문:

> 분리의 목적은 mmWave/licensed 팀의 **독립 개발**이다. provider 가 Unlicensed
> 하나뿐인 지금 전부 쪼개면, 크로스-레포 버전 동기화·publish·레포별 CI 비용은 모두
> 치르고 **독립 개발 이득은 없다**(YAGNI).
>
> **더 큰 위험**: 계약이 **단일 provider 가정으로 레포 경계에 굳는다.** 계약이 아직
> 흔들리는 중일 때 쪼개면 **2번째 provider 개발자가 매 변경마다 깨진다** —
> **빨리 쪼개는 것이 오히려 방해가 된다.**

**요약하면 — 나누는 것 자체는 이득이 아닙니다.** 나누면 비용이 먼저 생기고
(버전 맞추기 · 태그 내기 · CI 두 벌), 이득(팀이 서로를 안 기다림)은
**팀이 둘 이상일 때만** 생깁니다.

그래서 3단계로 나눠서, **약속이 안정된 뒤에** 실제로 쪼갰습니다.

## 5. `fcc-test-contracts` — 「약속」의 성격

### 5-1. 무엇이 들어 있나 (실측)

| 폴더 | 파일 수 | 무엇 |
|---|---|---|
| `fcc_test_contracts/common/` | 47 | 신원 · 접근 정책 · 로깅 · 인증 설정 등 **분야 무관 공통** |
| `fcc_test_contracts/headless/` | 20 | provider 서비스가 지켜야 하는 계약과 **검사기** |
| `fcc_test_contracts/artifacts/` | 15 | **계약 파일 자체** — OpenAPI · 예시 계약 · provider 온보딩 문서 |
| `fcc_test_contracts/web/` | 2 | 화면 쪽 계약 |
| `packages/fcc-test-kernel/` | — | **도메인 모델과 공유 로직**(파이썬 패키지, 따로 태그) |
| `packages/api-artifacts/` | — | 프런트엔드가 쓰는 **같은 계약의 JS/TS 판** |

### 5-2. 성격 — **의존성이 0개입니다**

```
dependencies = []
```

이것이 「커널」이라는 말의 뜻입니다. **아무것도 끌어오지 않습니다.**

⚠️ **왜 중요한가.** provider 팀이 이 패키지를 설치할 때 **딸려 오는 것이 없습니다.**
만약 여기가 웹 프레임워크나 DB 드라이버에 의존하면, 계약만 확인하고 싶은 사람도
그것들을 전부 설치해야 합니다. 그러면 **약속을 확인하는 비용이 약속을 지키는 비용보다
커집니다.**

### 5-3. 역할 — **양쪽이 같은 것을 보게 만드는 것**

```
provider 저장소  ──┐
                   ├──▶  fcc-test-contracts  (같은 파일을 «둘 다» 본다)
fcc-test-platform ─┘
```

**같은 파일을 보지 않으면, 각자 「맞다」고 믿으면서 서로 다른 것을 만듭니다.**
그리고 그 어긋남은 **실장비에서만** 드러납니다.

## 6. `fcc-test-platform` — 「플랫폼」의 성격

### 6-1. 무엇이 들어 있나

중앙 DB · 백엔드 API(65 경로) · 인증/RBAC · 프런트엔드(51 라우트) ·
provider 레지스트리 · 배포 조합 · 성적서/아티팩트 열람.

### 6-2. 성격 — **여기에 측정 코드는 없습니다**

스펙트럼 분석기 제어 · EUT 제어 · Excel 시험계획 · GUI 는 전부 provider 저장소에 남습니다.
**이 저장소가 아는 것은 「어느 분야인지 무관하게 참인 것」뿐입니다** —
프로젝트 · 챔버 · 세션 · 결과 · 성적서.

⚠️ **판단 규칙 하나로 줄이면:**

> **이것은 분야 지식인가, 아니면 분야와 무관하게 참인 것인가?**

분야 지식이면 여기 두지 않습니다. 두면 **provider 가 늘 때마다 이 저장소를 고쳐야
하는 구조**가 되고, 그것이 이 설계가 막으려는 바로 그것입니다.

### 6-3. 역할 — 실제로 얼마나 커널에 기대나 (실측)

```
platform 의 파이썬 215 파일 중
   fcc_test_contracts 를 import 하는 파일   135
   fcc_test_kernel 을 import 하는 파일       109
```

가장 많이 쓰는 것들:

```
13×  fcc_test_kernel.application.central_contract.envelope_helpers
11×  fcc_test_contracts.common.tree_artifacts
10×  fcc_test_kernel.application.central_contract.pagination
 8×  fcc_test_contracts.common.identity
 7×  fcc_test_kernel.domain.models.chamber_node
```

**즉 platform 은 커널 «위에» 서 있습니다.** 커널이 흔들리면 platform 이 흔들립니다 —
그래서 §7 의 순서가 필요합니다.

## 7. 의존은 **한 방향**입니다 — 그리고 그것이 일상에 영향을 줍니다

```
   fcc-test-platform  ───────▶  fcc-test-contracts
                       의존

   ✗ 반대 방향은 «없습니다»
```

`fcc-test-contracts` 는 platform 을 **모릅니다.** 알면 순환이 생기고,
순환이 생기면 **어느 쪽을 먼저 고쳐야 하는지 아무도 답할 수 없게 됩니다.**

### 그래서 커널을 고치는 것은 **2-레포 작업**이고 **순서가 있습니다**

```
① fcc-test-contracts 에서 고친다
② 태그를 «낸다»                      ← ⚠️ 사람의 승인이 필요한 지점
③ fcc-test-platform 의 «핀»을 올린다
④ platform 에서 소비를 확인한다
```

**핀은 「태그」입니다. 브랜치가 아닙니다.** platform 의 실제 선언:

```
fcc-test-contracts @ git+https://github.com/junnv93/fcc-test-contracts@v0.1.26
fcc-test-kernel    @ git+…@kernel-v0.5.4#subdirectory=packages/fcc-test-kernel
                        └─────────── 태그 ───────────┘
```

⚠️ **커널에서 고쳤는데 platform 에서 안 보인다면, 대개 ②를 안 한 것입니다.**
platform 은 **태그에 담긴 것만** 봅니다.

⚠️ **`fcc-test-kernel` 은 같은 저장소 안에 있지만 «다른 태그»를 씁니다**
(`kernel-v0.5.4`). 한 저장소가 두 개의 배포물을 내보내고, 각자 판번호가 따로 움직입니다.

## 8. 오늘 이 구조가 일상에 미치는 영향

| 상황 | 결과 |
|---|---|
| 화면 문구를 고친다 | platform 만. 1-레포 작업 |
| API 경로를 추가한다 | platform 만 (그 경로가 provider 계약이 아니라면) |
| **시료 도메인에 필드 하나 추가** | ⚠️ **2-레포.** 커널 태그가 «먼저» |
| provider 계약 형태를 바꾼다 | ⚠️ **2-레포 + 모든 provider 팀에 영향** |
| 측정 알고리즘을 고친다 | **provider 저장소만.** platform 무관 |

⚠️ **가장 자주 하는 실수: 커널에 있어야 할 것을 platform 에 두는 것.**
당장은 되고, **두 번째 provider 가 붙는 날 그것이 드러납니다** —
그때는 이미 platform 이 그 위에 쌓여 있습니다.

⚠️ **반대 실수도 있습니다: 분야 지식을 커널에 두는 것.**
커널은 **모두가** 씁니다. 거기에 한 분야의 가정이 들어가면 **다른 분야가 그것을
따라야 합니다.**

## 9. 왜 «다시 합치지» 않나

「나누니까 복잡해졌다」는 관찰은 맞습니다. 그런데 합치면:

| 합쳤을 때 | 결과 |
|---|---|
| provider 팀이 서로의 측정 코드를 본다 | 🔴 **비공개 전제가 깨진다** — 다른 provider 저장소는 비공개다(ADR-0018 D-5) |
| 한 팀의 커밋이 다른 팀 CI 를 깨뜨린다 | 🔴 서로를 기다리게 된다 — 분리의 목적이 사라진다 |
| 계약이 「지금 코드가 하는 것」이 된다 | 🔴 **약속이 사라진다.** 계약은 코드와 «따로» 있어야 검사할 수 있다 |

⚠️ **그리고 되돌릴 수 없는 사실이 하나 더 있습니다** —
**배송 기계는 2026-08-31 에 퇴역했습니다.** 예전에는 모노레포가 두 레인을 «만들어»
내보냈지만, 지금은 **방향이 역전돼 모노레포가 두 패키지를 pip 로 «소비»합니다.**

```bash
ls FCC_mobile_test_automation/packaging/                    # No such file or directory
ls FCC_mobile_test_automation/scripts/stage_extraction_package.py   # No such file or directory
```

**재배송이 물리적으로 불가능합니다.** 두 레인은 이제 **스스로 사는 저장소**입니다.

## 10. 한 장 요약

```
fcc-test-contracts        «약속»        의존성 0.  양쪽이 같은 것을 보게 만든다
        ▲
        │ 태그로 소비 (단방향)
        │
fcc-test-platform         «플랫폼»      분야 중립. 측정 코드 없음
        ▲
        │ 태그로 소비 · 이미지로 배포
        │
당신의 provider 저장소     «분야 지식»    비공개. 측정·시험계획·성적서 내용
```

**세 문장으로:**

1. **`contracts` 는 약속을 담고, 아무것에도 의존하지 않습니다.**
   그래야 누구나 싸게 확인할 수 있습니다.
2. **`platform` 은 분야를 모릅니다.**
   그래야 provider 가 늘어도 고칠 필요가 없습니다.
3. **당신의 저장소는 분야를 압니다.**
   그래야 당신의 시험 지식이 남의 저장소로 새지 않습니다.
