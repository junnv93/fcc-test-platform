## 1. 🔴 계약 아티팩트를 «옆에 복사» 하는 것 — 가장 쉽고 가장 나쁜 길

### 무슨 일이 일어나나

두 번째 provider 가 붙으면, `config/headless_provider_registry.json` 의
`contract_artifact` 가 **이 트리에 없는 파일**을 가리켜야 합니다. 그때 가장 손에
잡히는 해법이 「그 파일을 여기로 복사해 오는 것」입니다.

**그렇게 하면 코드를 한 줄도 안 고치고 검사가 초록이 됩니다.** 실측
(`fcc_test_contracts/headless/provider_registry.py:272`):

```python
def _resolve_artifact_path(registry_path, project_root, artifact):
    path = Path(artifact)
    if path.is_absolute():
        return path
    candidate = project_root / path
    if candidate.exists():
        return candidate
    return registry_path.parent / path      # ← 레지스트리 «옆» 을 본다
```

### 왜 나쁜가

그 초록은 **provider 의 코드가 계약을 만족한다**는 보고가 아니라
**우리가 둔 사본이 계약을 만족한다**는 보고입니다. 그리고 사본은 갈라집니다.

⚠️ **이미 일어났습니다.** 모노레포 커밋 `aaac18ab` 본문 —
레지스트리 사본이 갈라졌고, *"모노레포 체커를 돌리면 3 provider 전부
`schema_mismatch` 였고, **그것을 돌리는 게이트가 없어 아무도 못 봤다.**"*

### 운영자 판정 (2026-08-31)

> **아티팩트는 발행처에 머문다.** provider 가 자기 레포에서 자기 계약을 검사하고,
> 중앙은 **그 결과만** 받는다.

기각된 둘: **URL 발행**(검사가 네트워크에 의존 → 오프라인·재현성이 깨짐),
**이 트리로 복사**(위 이유).

> ### 🧭 스스로 묻는 질문
> **「이 초록은 «남의 코드» 에 대한 것인가, 아니면 «내가 둔 사본» 에 대한 것인가?」**

## 2. 🔴 `provider_id` — 같은 뜻의 값이 최소 넷 있었습니다

### 무슨 일이 일어났나

계약 SSOT 의 값은 `fcc-unlicensed-conducted` 입니다. 그런데 실장비에서 발견된 값들:

| 어디 | 값 | 결과 |
|---|---|---|
| 계약 SSOT · 중앙 DB · 중앙 컨테이너 | `fcc-unlicensed-conducted` | ✅ |
| 챔버 PC 의 옛 env | `unlicensed` | 중앙이 **404** 로 거절 |
| 노드 런처 | `providers.id` (UUID) | 인입 배치가 통째로 거절 |
| `infra/chamber/session-node.env.example:55` | `unlicensed` | ⚠️ **측정 PC 설정 시 복사하는 파일** |

### 왜 반복됐나 — 검사가 **키만** 봤기 때문입니다

모노레포 `ac715741` 본문 — *"형제 검사는 **키가 있는가**만 묻기 때문에 그 축에서는
`unlicensed` 와 `fcc-unlicensed-conducted` 가 **같은 값**이다."*

그리고 `89b1df0e` 본문 — 봉인이 사본 **둘을 손으로 열거**해 묶었는데, **네 번째 사본**
(챔버 env 예시)이 그 목록에 없었습니다. 해법은 목록을 늘리는 것이 아니라 **축을 바꾸는
것**이었습니다: *"운영자 대면 경로에서 그 env 대입을 **전수 발견**해 계약 SSOT 와 대조한다."*

### 증상이 원인을 가립니다

```
틀린 provider_id  →  중앙이 404  →  운영자에게는 「노드가 안 뜬다」로 보인다
```

그리고 인입 시점의 거절은 **인증 두 층(챔버 토큰 · 기계 신분증)을 통과한 뒤**에
오므로 **인증 문제처럼 읽힙니다.**

### 오늘의 방어

`scripts/check_central_provider_id_pairing.py` 가 중앙 env 짝을 봅니다.

> ### 🧭 스스로 묻는 질문
> **「내 검사는 «키가 있는가» 를 묻나, «값이 맞는가» 를 묻나?」**
> 그리고 — **「이 값의 사본이 몇 개인지 내가 «세어» 봤나, 아니면 «기억» 했나?」**
> 손으로 열거한 목록은 반드시 하나를 놓칩니다. **선언에서 파생하십시오.**

## 3. `:latest` 는 「재빌드했는가」에 답하지 않습니다

폐쇄망에는 이미지 레지스트리가 없어 `docker save`/`load` 로 옮깁니다.
그러면 낡은 이미지도 새 이미지도 **같은 태그**입니다.

⚠️ **실측(2026-09-04)**: 개발 PC 의 `:latest` 가 하루 전 코드였고 그 안의 의존성도
낡아 있었는데 — **컨테이너는 `healthy` 였습니다.** 낡은 코드와 낡은 의존성이 서로
정합했기 때문입니다. **아무것도 실패하지 않습니다.**

### 방어

```bash
docker build … --build-arg GIT_REVISION="$(git rev-parse HEAD)" -t <이미지>:latest .
docker inspect <이미지> --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
```

⚠️ 그리고 `docker load` 후 `docker compose up -d` **만으로는 새 이미지가 안 붙을 수
있습니다** — 같은 태그면 캐시가 조용히 재사용됩니다. 컨테이너를 **재생성**하십시오.

### 자매 함정 — 버전 번호도 답하지 않을 수 있습니다

`fcc-test-platform 0.1.8` 이 커널 이관 **전/후 양쪽**에 붙어 있었습니다.
**버전이 안 올랐으므로 버전으로 판정할 수 없습니다.** 설치된 패키지의 **내용**을 보십시오.

> ### 🧭 스스로 묻는 질문
> **「이 축에서 «서로 다른 두 상태» 가 «같은 값» 을 갖는가?」**
> 이 질문은 이 레포가 규칙 파일로 갖고 있습니다 —
> `.claude/rules/check-axis-blindness.md`.

## 4. 챔버 자격증명 — `chamber_id` 를 client id 로 쓰지 마십시오

id 는 **파생**됩니다:

```
chamber_client_id(chamber_id) = "fcc-chamber-" + chamber_id
```

⚠️ 실장비에서 노드가 **존재하지 않는 이름으로** 토큰을 요청했습니다.
증상은 `invalid_client` 인데, 그 코드는 **「client 없음」과 「secret 회전」에 같은 답**
이라 사후에 원인을 가릴 수 없습니다. 화면에는 그저 **Offline** 으로 보입니다.

⚠️ **client 프로비저닝을 두 번 돌리지 마십시오** — secret 이 회전해 이미 배포된 값이
죽습니다. 이미 있으면 admin API 로 **현재 값을 읽으십시오.**

### 이름이 사실과 반대로 생겼습니다

접두사 `fcc-chamber-` 의 `fcc` 는 **시스템 이름**이지 시험 종류가 아닙니다
(realm `fcc-dev`, 웹 audience `fcc-platform-frontend` 도 같은 접두사).
**챔버는 분야 중립**이고 `chamber_nodes` 에 시험 종류 칸이 없습니다(실측 11 컬럼).
알려진 부채이며, 바꾼다면 **다른 provider 가 붙기 전이 유일하게 싼 시점**입니다.

## 5. `.well-known` 의 `jwks_uri` 는 「물어본 주소의 메아리」입니다

`KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` 이므로 **중앙에서 물으면 `localhost` 가 나옵니다.**
그 값을 챔버에 넣으면 노드가 **자기 자신에게** JWKS 를 요청합니다.

⚠️ **설정은 형식상 완전하고 값도 그럴듯하며, 런타임에만 틀립니다.**

챔버가 쓸 값은 중앙의 **공개 주소**입니다:
`http://<중앙 IP>:<keycloak 포트>/realms/<realm>/protocol/openid-connect/certs`

## 6. 포트는 «승인 집합» 안에서 고르십시오

회사 방화벽 승인이 **PC 마다 따로** 납니다. 승인 밖 포트를 고르면 —
노드는 **정상 기동**하고 heartbeat 도 **갑니다**. 막히는 것은 **중앙→노드 forward** 뿐입니다.
증상은 §00-project-map §4 와 같습니다: **「살아 있는데 조용함」**.

## 7. Windows 두 가지 — 개발 PC 에서는 «보이지 않습니다»

### 7-a. BOM 없는 UTF-8 이 ANSI 로 읽힙니다

PowerShell 5.1 의 `Get-Content` 는 BOM 없는 파일을 **ANSI 코드페이지**로 읽습니다.
한글 값이 깨지고 — ⚠️ **그것으로 끝이 아닙니다.** CP949 의 lead 바이트가 뒤 바이트를
trail 로 삼키므로, **멀티바이트 길이가 홀수면 줄바꿈까지 삼켜** 다음 줄과 병합되고
**키 하나가 통째로 사라집니다.**

읽는 쪽에 **`-Encoding UTF8` 을 명시**하십시오.

### 7-b. 콘솔 창을 «클릭» 하면 프로세스가 얼어붙습니다

포그라운드 콘솔로 서비스를 돌리면 QuickEdit 기본값 때문에 **창을 클릭하는 것만으로**
프로세스가 멈춥니다:

```
TCP 연결   받는다 (OS 가 backlog 에 넣는다)
응답       없다
로그       한 줄도 안 늘어난다
```

밖에서 보면 **「죽지 않았는데 죽은 것」**이고, 중앙은 살아 있는 챔버를 로테이션에서 뺍니다.
QuickEdit 를 끄거나 **서비스로 돌리십시오.**

## 8. 「판정하지 못했다」를 「통과」로 쓰지 마십시오

검사기가 대상을 **읽지 못했을 때** 통과시키면, 그 초록은
**「검사했고 괜찮다」와 구별되지 않습니다.**

모노레포 `ac715741` 이 이 축을 명시적으로 상환했습니다 —
*"계약 패키지를 **못 읽으면 통과가 아니라 「검증하지 못했다」**로 말한다."*

그리고 `e4667289` — *"판정 불가가 「어긋남」으로 위장하던 한 줄을 고친다."*
**판정 불가는 통과도 실패도 아닌 «세 번째 상태»** 이고, 그것을 앞의 둘 중 하나로
접으면 반드시 거짓말이 됩니다.

> ### 🧭 스스로 묻는 질문
> **「이 검사가 초록일 수 있는 «경우의 수» 가 몇 가지인가?」**
> 「대상이 정상이다」 말고 다른 답이 있으면, 그 답을 별도 상태로 분리하십시오.

## 9. 「관측하지 못했다」를 「없다」의 증거로 쓰지 마십시오

같은 이름의 컨테이너가 **여러 기계에서** 돕니다. 개발 PC 와 중앙 PC 가
`docker ps` 출력이 **완전히 같은 모양**입니다.

⚠️ **2026-09-04 라운드에서 세 세션이 각자 다른 기계를 재고 같은 이름으로 보고했습니다.**

**보고에는 측정 기계 주소를 명시하십시오.** 그리고 WSL 의 `hostname -I` 는 NAT 때문에
거짓을 말할 수 있으므로, 중앙 PC 신원 판정에 그것을 쓰지 마십시오.

### 일반형 — 부재는 «내 도구가 어디까지 봤나» 와 함께 적으십시오

「이 레포에 없다」와 「없다」는 **다른 명제**입니다.
그리고 이름·경로·깊이 세 겹으로 틀릴 수 있습니다.

> ### 🧭 스스로 묻는 질문
> **「내가 «없다» 고 말할 때, 내 도구는 어디까지 봤나?」**
> 답을 못 하면 그 문장은 **「내 도구가 못 찾았다」**로 고쳐 쓰십시오.

## 10. 두 레인이 서로를 핀하고, 그 핀이 뒤처집니다

```
fcc-test-platform 0.1.8   →  fcc-test-contracts 0.1.11 을 요구
requirements 는           →  fcc-test-contracts 0.1.12 를 선언
한 번에 resolve 하면       →  ResolutionImpossible
```

해법은 **분리 설치**입니다 — 서드파티는 정상 resolve, `git+` 레인만 `--no-deps`.
중앙 `Dockerfile.api` 가 그렇게 합니다.

⚠️ **그 규칙이 Dockerfile 안에만 있으면, Dockerfile 이 없는 레인(챔버 PC 등)은
그것을 받지 못합니다.** 규칙이 한 파일 안에만 살면 그 파일이 없는 곳에서는 없습니다.

⚠️ 그리고 **핀 둘이 서로를 배제해도, 「설치를 실제로 돌려 보기 전」에는 어느 레포에서도
보이지 않습니다.** 해석 가능성은 **설치 단계만** 답할 수 있습니다.

## 11. 「검사를 만들었다」와 「그 검사에 이빨이 있다」는 다른 명제입니다

이 프로젝트에서 **가장 자주 재발한 유형**입니다. 공허한 검사는 **초록과 똑같이 생겼고**,
그래서 아무도 알아채지 못합니다.

### 공허한 통과의 두 모양

| 모양 | 어떻게 생겼나 | 왜 안 잡히나 |
|---|---|---|
| **집합이 빈다** | 검사할 대상이 0개 | 「비어 있지 않은가」 단언으로 잡을 수 있다 |
| **집합이 «틀리다»** | 대상은 있는데 **엉뚱한 것**을 세고 있다 | ⚠️ **성실히 보고하며 통과**한다. 비어있음 단언으로 못 잡는다 |

### 방어 — 새 검사에는 «주입» 을 함께 넣으십시오

`CLAUDE.md` §P0-4:
> 새 검사에는 **일부러 깨진 입력을 주입해 빨개지는지** 확인하는 케이스를 함께 넣어라.

⚠️ **그리고 그 주입이 «착지했는지» 부터 확인하십시오.** 한 세션에서 주입이 세 번
공허했던 기록이 있습니다 — **공허한 주입은 성공한 주입과 같은 모양입니다.**

### 자매 함정 — 검사기가 «못 보는» 것들

| 검사 방식 | 못 보는 것 |
|---|---|
| 줄 단위 정규식 스캔 | **여러 줄로 쪼개진 표현.** 「없다」와 「못 봤다」의 출력이 같다 → 참조 조사는 **AST 로** |
| 문자열 존재 검사 | **산문을 코드로 셉니다.** 주석·문서의 문자열이 통과시킨다 → 호출·인자는 **AST 로** |
| 존재 축 봉인 | **도구가 «출력하는» 문자열.** 진입점을 37개 세워도 도구가 내놓는 건 옛 경로일 수 있다 |
| 접두사 매치 | **무엇을 셌는지 말하지 않는다.** 「84」가 실은 24였던 사례가 있다 |

> ### 🧭 스스로 묻는 질문
> **「이 검사를 빨갛게 만들려면 무엇을 해야 하나? 그것을 «실제로» 해 봤나?」**

## 11-a. 「검사가 X 를 안 지운다」를 결함이라 부르기 «전»에

2026-09-07 에 실제로 겪은 것입니다. 게이트가 이 이름으로 막았습니다:

```
test_git_hooks_are_wired_here.py::TestTheCheckWouldSeeAnUnwiredCheckout
    ::test_an_unset_checkout_reads_as_empty
```

그 테스트의 환경 격리 헬퍼가 `GIT_DIR` 류 **위치** 변수만 지우고
`GIT_CONFIG_PARAMETERS`(**설정**)는 안 지웁니다. **「빠뜨렸다」로 읽혔고,
그 판정은 틀렸습니다.**

### 실제로는 그 red 가 «정확한 경보» 였습니다

```bash
T=$(mktemp -d); git init -q "$T"                  # 훅 «미설정» 저장소
git -C "$T" config core.hooksPath                  # → ''         본 검사가 미설정을 «본다» ✅
GIT_CONFIG_PARAMETERS="'core.hooksPath=githooks'" \
  git -C "$T" config core.hooksPath                # → 'githooks'  🔴 미설정인데 설정된 것처럼
```

본 검사는 `git config core.hooksPath` **전체 해소**를 읽습니다. 그래서 그 오염 아래에서는
**훅이 하나도 안 걸린 체크아웃도 통과합니다** — 게이트가 이빨을 잃습니다.
그 테스트는 정확히 그것을 지키는 자리이고, **빨개진 것은 그 사실의 보고**였습니다.

⚠️ **`GIT_CONFIG_*` 를 지웠다면 시험이 조용해지고 그 사실이 가려졌을 것입니다.**

### 근거는 «처음부터 코드에 있었습니다» — 제가 안 봤습니다

원저자가 다섯 줄 위 상수 주석에 적어 두었습니다:

> `⚠️ 전부 지우지 않는다 — GIT_AUTHOR_* 나 GIT_CONFIG_* 는 위치와 무관하고,`
> `넓게 지우면 이 헬퍼가 「위치를 격리한다」가 아니라 「git 을 다르게 만든다」가 된다.`

**함수 «본문»만 보고 단정했습니다.** 그리고 같은 파일을 본 형제 세션은
`docstring` 만 보고 「근거가 유실됐다」고 판단했습니다 —
**두 세션이 각자 다른 절반만 보고 각자 틀렸습니다.**

> ### 🧭 스스로 묻는 질문
> **「이것을 «결함»이라 부르기 전에, 그 파일의 상수·주석·도입 커밋 메시지를 읽었나?」**
> 그리고 — **「내 시선이 어디까지 갔나?」** §9 의 「내 도구가 어디까지 봤나」는
> 도구만의 이야기가 아닙니다.

⚠️ **실무 규칙 하나로 줄이면**: 훅을 `git -c core.hooksPath=…` 로 임시로 켜지 마십시오.
`core.hooksPath` 는 대개 **이미 설정돼 있습니다.** 그냥 `git push` 하십시오.

### 🧭 더 넓은 규칙 — 「훅 컨텍스트에서 난 red 는 «컨텍스트»를 먼저 의심하라」

훅 안은 **당신의 셸이 아닙니다.** git 이 환경변수를 넣고, stdin 이 이미 소비돼 있고,
`PATH` 와 인터프리터가 다를 수 있습니다. 같은 커밋이 셸에서는 초록이고 훅에서는
빨간 사례가 2026-09-07 하루에 **둘** 나왔습니다:

| 무엇 | 셸에서 | 훅에서 | 원인 |
|---|---|---|---|
| `test_an_unset_checkout_reads_as_empty` | 통과 | **실패** | `git -c` 가 넘긴 `GIT_CONFIG_PARAMETERS` |
| `fcc-test-contracts` 의 **삭제 전용** push | — | **막힘** | 시스템 `python3` 에 `pytest` 가 없다 |

**둘 다 트리(코드)와 무관합니다.** 그러므로 훅이 막았을 때 물어야 하는 순서는:

```
① 컨텍스트가 다른가?   훅이 넣은 env · 인터프리터 · stdin · PATH
② 설치본이 다른가?     .pth 가 어느 트리를 가리키나 (§14)
③ 내가 깨뜨렸나?       대조군과 «이름 집합»을 비교했나
```

⚠️ **③ 을 먼저 물으면, 고칠 것이 없는데 무언가를 고치게 됩니다** —
그리고 이 절이 기록하는 것이 정확히 그 사례입니다.

## 12. 「사본이 있다」가 진짜 의존을 가립니다

폐포(closure) 검사가 **사본을 보면** 초록이 거짓말을 합니다.
사본을 철수한 뒤 빨개지면, 물어야 할 질문은 **「봉인이 틀렸나」가 아니라
「내 전제가 죽었나」** 입니다.

그리고 반대 방향 — **설치 잔재(`egg-info` 등)가 봉인을 «통과» 시킵니다.**
빨간 것만 잔재를 의심하지 마십시오.

⚠️ **`.pth` 꼬리는 `pip` 를 조용히 no-op 시킵니다.** 「선언대로 설치했다」가 껍데기만
되고, namespace 패키지는 낡은 사본과 병합됩니다.

## 16. 공유 트리 — 「미커밋 파일」이 당신 것이 아닐 수 있습니다

`git status` 는 **어느 참조점에 대해** 묻는지 말해 주지 않습니다.
낡은 `HEAD` 는 **이미 착지한 남의 파일**을 「내 미커밋 변경」처럼 보이게 합니다.

```bash
git fetch origin && git diff origin/main --stat     # git status 만 보지 마라
git worktree list                                   # 지금 누가 무엇을 하는가
git push origin HEAD:refs/heads/<이름>               # 브랜치를 «바꾸지» 마라
```

⚠️ 그리고 **워크트리는 `.git/config` 를 공유합니다.** 한 세션이 훅을 끄면
**모든 세션에서 꺼집니다.** 훅이 사라졌다면 당신이 아니라 옆 세션일 수 있습니다.

⚠️ **판정을 내렸으면 그 파일을 소유한 세션에도 직접 알리십시오.**

## 17. 마지막 — 「고치라는 말」이 틀릴 수 있습니다

이 프로젝트에는 **정정 커밋이 많습니다.** 그것은 결함이 아니라 규율입니다.
근거로 인용된 문장을 **뒤집기 전에 그 근거의 진위부터 재십시오** — 근거가
**「거짓 사실」**일 수 있고, 그 문장이 쓰인 커밋 시점에도 거짓이었을 수 있습니다.

그리고 형제 세션이 알려 준 **줄 번호는 그쪽 커밋의 것**입니다.
당신 트리에서 확인하면 「무접촉」이라 답하고, 실은 이미 고쳐진 뒤일 수 있습니다.
