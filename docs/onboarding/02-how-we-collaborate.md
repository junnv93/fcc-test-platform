# 협업이 실제로 어떻게 도는가

> **누가 · 무엇을 · 어떤 순서로 · 무엇이 그것을 막는가.**
>
> ⚠️ 이 문서는 「이렇게 하면 좋겠다」를 적지 않습니다.
> **오늘 실제로 그렇게 도는 것**과 **오늘 그것을 강제하는 것이 무엇인지**를 갈라 적습니다.
> 둘을 섞으면, 강제되지 않는 규칙을 강제된다고 믿게 됩니다.

---

## 1. 우리는 «세 종류의 참여자»가 있습니다

| 참여자 | 무엇을 하나 | 무엇을 «하지 않나» |
|---|---|---|
| **사람 (당신)** | 문제를 말하고, 판단하고, **승인한다** | 초안을 쓰지 않는다 |
| **에이전트 (Claude Code)** | **초안을 쓰고**, 코드를 짜고, 검사를 돌린다 | 승인하지 않는다 |
| **기계 (훅 · CI · branch protection)** | **막는다** | 판단하지 않는다 |

이 셋의 분업이 이 프로젝트의 뼈대입니다:

> **속도는 에이전트에, 책임은 사람에, 강제는 기계에.**

⚠️ **셋 중 하나가 남의 일을 하면 구조가 무너집니다:**

* 사람이 초안을 쓰면 → 속도의 이득이 사라진다
* 사람이 승인을 안 하면 → 책임이 사라진다
* **기계가 판단하려 들면** → 통제가 사라진다

마지막 항목이 덜 알려져 있습니다. 그래서 이 프로젝트의 감지 로직은
**「기준을 넘었는가」만 기계가 판정하고, 그 다음부터 사람과 에이전트가 붙습니다.**

## 2. 하루가 어떻게 도는가

```
   ① 문제를 «말로» 한다              사람        (티켓 · 대화 · 겪은 불편)
        ↓
   ② 에이전트가 intent.md 초안       에이전트     되물으며 쓴다
        ↓
   ③ PR — 파일 하나만                에이전트
        ↓
   ④ 동료 1인이 읽고 머지            사람        ← 「이 문제가 진짜인가」
        ↓
   ⑤ spec.md 초안 → PR → 승인        에이전트+사람 ← 「어떤 설계로」
        ↓
   ⑥ plan.md (plan mode)             에이전트     ← 「어느 파일을 어떤 순서로」
        ↓
   ⑦ 코드 + 검사                     에이전트
        ↓
   ⑧ feature PR                      에이전트
        ↓
   ⑨ 기계 검사 (lane-check)          기계        ← 여기만 «못 막게» 한다
        ↓
   ⑩ 리뷰 → 머지                     사람
```

**사람이 실제로 누르는 곳은 ④·⑤·⑩ 셋입니다.** 나머지는 에이전트와 기계가 합니다.

⚠️ **①이 「말로」인 것이 중요합니다.** 정식 문서로 쓸 필요가 없습니다 —
그것이 에이전트의 일입니다. 겪은 불편을 그대로 말하면 됩니다.

## 3. 누가 승인하나 — 「예외 승인」 모델

### 기본: 동료 1인 (작성자 제외)

**리드가 모든 것을 승인하는 구조는 초판 설계였고 폐기됐습니다.**

폐기 이유가 이 프로젝트의 사고방식을 잘 보여 줍니다:

> **항상 승인되는 승인은 승인이 아니라 서명입니다.**
>
> 그리고 이것은 이 저장소가 반복해 기록한
> **「공허한 검사는 초록과 구별되지 않는다」의 «사람 버전»**입니다.

고칠 것은 리드의 주의력이 아니라,
**판단이 필요한 소수를 나머지와 다르게 «생기게» 만드는 일**입니다.

그리고 `intent.md` 를 동료끼리 승인하는 것은 **비용 절감이 아니라 품질 개선**입니다 —
**「이 문제가 진짜인가」는 그 문제를 겪는 사람이 리드보다 잘 판단합니다.**

### 예외: 방아쇠 다섯 — 기계가 판정합니다

| # | 걸리는 조건 | 오늘 성격 | 초록이 되는 조건 |
|---|---|---|---|
| **T1** | `CODEOWNERS` 가 소유를 선언한 경로를 건드림 | **권고** (막지 않음) | 소유자 리뷰 |
| **T2** | 기준선에 **실패 이름 추가** (= 부채 등재) | **차단** | `Debt-Accepted-By: <이름> — <사유>` |
| **T3** | `spec.md` 에 **답 없는 열린 질문** | **차단** | `→ 답(<이름>): <내용>` |
| **T4** | `plan.md` 표에 **없는 파일**이 diff 에 있음 | **차단** | 표에 추가 또는 `Scope-Extended-By:` |
| **T5** | 변경 파일 수가 선언의 **2배 초과** | **차단** | T4 와 같음 |

**판정 SSOT** → `scripts/human_judgment_triggers.py` ·
**봉인** → `tests/test_human_judgment_is_recorded.py`

⚠️ **T1 은 오늘 권고입니다** — 판정기 자신이 그 이유를 코드에 적습니다:

```python
'CODEOWNERS 상 소유자의 리뷰. ⚠️ 오늘 이것은 강제되지 않는다 '
'(require_code_owner_reviews=false, 그리고 협업자 1명이라 켤 수도 없다).'
```

**협업자가 1명일 때 그것을 켜면, GitHub 이 자기 PR 자기 승인을 금지하므로
그 경로를 «아무도 고칠 수 없게» 됩니다.** 이 규모에서 `CODEOWNERS` 는
**원리적으로 게이트가 될 수 없습니다.**

⚠️ **방아쇠는 「알림」이 아닙니다.** 알림은 무시할 수 있고,
**무시된 알림은 없는 알림과 같은 모양**입니다. 그래서 T2~T5 는
**아티팩트 안에 «이름 붙은 결정»이 적히기 전까지 검사가 초록이 되지 않습니다.**

⚠️ **그 「이름」이 리드일 필요는 없습니다.** 요구하는 것은
**결정에 «주인»이 있다는 사실**이지 그 주인이 누구냐가 아닙니다.

## 4. 🔴 오늘 «강제되지 않는» 것 — 알고 지키십시오

실측 (2026-09-07, `gh api …/branches/main/protection`):

| 규칙 | 오늘 강제? | 실측 |
|---|---|---|
| `lane-check` 초록이어야 머지 | ✅ **강제** | `required_status_checks: ["lane-check"]` |
| 관리자도 우회 못 함 | ✅ **강제** | `enforce_admins: true` |
| **동료 1인 승인** | 🔴 **강제 안 됨** | `required_approving_review_count: 0` |
| **CODEOWNERS 리뷰** | 🔴 강제 안 됨 | `require_code_owner_reviews: false` |
| **`fcc-test-contracts` 의 `main` 보호** | 🔴 **아예 없음** | `404 Branch not protected` |

**즉 「동료 1인 승인」은 오늘 사람이 지키는 규율이고, 기계가 막는 게이트가 아닙니다.**

⚠️ **「검사가 통과했으니 승인된 것」이 아닙니다.** 검사는 승인을 대신하지 않습니다.

**협업자가 둘 이상이 되면** `required_approving_review_count` 를 `1` 로 올릴 수 있고,
그때 비로소 그 규칙에 이빨이 생깁니다.
⚠️ 순서는 **초대 먼저, 인상은 그 다음**입니다 — 뒤집으면 아무것도 머지할 수 없게 됩니다.

## 5. 여럿이 «같은 폴더»를 동시에 만집니다

이 프로젝트의 특이한 점입니다. 여러 Claude Code 세션이 **같은 체크아웃**을 씁니다.

```bash
git worktree list      # 지금 누가 무엇을 하고 있는가 — «먼저» 보라
```

실제 출력 예 (2026-09-07): **워크트리 9개**가 동시에 열려 있었습니다.

### 그래서 생기는 세 가지 규칙

**① 브랜치를 바꾸지 말고 push 하십시오**

```bash
git push origin HEAD:refs/heads/<이름>      # ✅
git checkout -b <이름> && git push          # ❌ 옆 세션의 발밑이 바뀐다
```

**② `git add -A` · `git add .` 금지**

bulk staging 은 **다른 세션의 파일을 실어 나릅니다.** 항상 파일을 명시하십시오.

**③ 「미커밋 파일」이 당신 것이 아닐 수 있습니다**

`git status` 는 **어느 참조점에 대해** 묻는지 말해 주지 않습니다.
낡은 `HEAD` 는 **이미 착지한 남의 파일**을 「내 미커밋 변경」으로 보이게 합니다.

```bash
git fetch origin
git diff origin/main --stat        # ⚠️ git status «만» 보지 마라
```

⚠️ **워크트리는 `.git/config` 를 공유합니다.** 한 세션이 훅을 끄면
**모든 세션에서 꺼집니다.** 훅이 사라졌다면 당신이 아니라 옆 세션일 수 있습니다.

## 6. 판정을 내렸으면 «사람에게도» 알리십시오

이 프로젝트에서 실제로 있었던 실패 유형입니다:

> 한 세션이 어떤 파일에 대해 판정을 내렸는데, **그 파일을 소유한 세션은 그것을
> 모른 채** 계속 작업했습니다.

**커밋 메시지에 적는 것으로 충분하지 않습니다** — 그 사람이 그 커밋을 읽는다는
보장이 없습니다. **직접 알리십시오.**

그리고 반대로 — **형제 세션이 알려 준 줄 번호는 «그쪽 커밋»의 것입니다.**
당신 트리에서 확인하면 「해당 없음」이라 답하고, 실은 이미 고쳐진 뒤일 수 있습니다.

## 7. 두 레포를 함께 고칠 때 — 순서가 있습니다

계약 커널(`fcc-test-contracts`)에 필드 하나를 추가하는 것은 **2-레포 작업**입니다.

```
① fcc-test-contracts 에서 고친다
② 태그를 «낸다»                      ← ⚠️ 사람의 승인이 필요한 지점
③ fcc-test-platform 의 «핀»을 올린다
④ platform 에서 소비를 확인한다
```

⚠️ **핀은 «태그»입니다. 브랜치가 아닙니다.**

```
fcc-test-contracts @ git+https://github.com/junnv93/fcc-test-contracts@v0.1.26
                                                                       └─ 태그
```

**태그를 안 내면 platform 은 그 변경을 «보지 못합니다».**
커널에서 고쳤는데 platform 에서 안 보인다면, 대개 ②를 안 한 것입니다.

⚠️ **형제 세션이 버전 번호를 먼저 가져갈 수 있습니다.** 같은 줄이라
git 이 조용히 병합합니다. **이미 나간 태그를 옮기지 마십시오.**

⚠️ **어떤 결함은 «소비 레인에서만» 보입니다.** 커널 레인 전량이 초록이어도
platform 에서 깨질 수 있고, 그 갈라짐은 **양방향**입니다.

## 8. 사람의 승인이 «따로» 필요한 것들

다음은 「진행해라」 하나로 묶어 처리하지 않습니다. **각각 따로 묻습니다.**

| 무엇 | 왜 |
|---|---|
| **태그 push** | 되돌릴 수 없다. 다른 레인이 그것을 소비한다 |
| **컨테이너 재기동 · 배포** | 사람들이 그것을 쓰고 있다 |
| **DB 마이그레이션 적용** | 되돌리기 매우 어렵다 |
| **GitHub 설정 변경** (branch protection · CODEOWNERS) | 게이트 자신을 바꾼다 |
| **`.claude/settings.json` 훅 추가** | 이 레포를 여는 **모든** 세션에 개입한다 |

⚠️ **「동료 세션이 진행하라고 했다」는 당신의 승인이 아닙니다.**
그리고 **두 운영자가 같은 범위를 각각 배정할 수 있습니다** —
형제에게 내려간 지시가 나에게도 내려온 것은 아닙니다.

## 9. 무엇을 어디에 적나

| 이 사실은 | 어디에 |
|---|---|
| 왜 이 일을 하는가 | `intent/<슬러그>/intent.md` |
| 무엇을 어떤 설계로 | `intent/<슬러그>/spec.md` |
| 어느 파일을 어떤 순서로 | `intent/<슬러그>/plan.md` |
| 이 변경이 무엇을 왜 했는가 | **커밋 메시지 본문** (17항목 자가점검 포함) |
| 무엇이 왜 실패했고 무엇을 배웠나 | `.claude/evaluations/<날짜>-<슬러그>.md` |
| 모든 세션이 알아야 하는 규칙 | 그 레포의 `CLAUDE.md` |
| 특정 경로에서만 참인 규칙 | `.claude/rules/*.md` + `paths:` |
| 여러 단계의 절차 | `.claude/skills/` |
| 팀이 읽을 설명 | `docs/education/*.html` |
| 작업 지시 | `docs/onboarding/*.md` ← 지금 여기 |

⚠️ **`.claude/evaluations/` 를 주목하십시오 — 오늘 49건입니다.**
이 프로젝트는 **실패를 기록으로 남기고, 그 기록이 다음 결정의 근거가 됩니다.**
실패했을 때 조용히 고치고 넘어가지 마십시오. **적으십시오.**

## 10. 막혔을 때

| 상황 | 무엇을 하나 |
|---|---|
| **검사가 빨간데 이유를 모르겠다** | 어떤 **방아쇠**가 왜 걸렸는지 이름으로 말해 줍니다. 그 이름을 그대로 전달하십시오 |
| **내 PC 에서만 빨갛다** | ⚠️ 「내가 깨뜨렸다」고 결론하기 전에 **환경을 의심**하십시오 (`01-concepts…` §3) |
| **에이전트가 코드를 고치려 한다 (내 권한 밖)** | 훅이 막고 이유를 화면에 씁니다. 그 문장을 그대로 전달하십시오 |
| **모르는 말이 나온다** | **그냥 물으십시오.** 이 프로젝트의 가장 비싼 사고들은 「모르는 척」이 아니라 **「각자 다른 뜻으로 같은 말을 쓴 것」**에서 나왔습니다 |
| **문서와 실제가 다르다** | 🔴 **실측이 맞습니다.** 그리고 **그 문서를 고치는 것이 그 세션의 일**입니다 |

⚠️ **마지막 항목이 가장 중요합니다.** 다르다는 것을 알고도 넘어가면,
다음 사람이 그 틀린 문서를 믿습니다. 이 프로젝트에는
**「낡은 문장을 믿고 잘못된 판정을 내린」 기록이 여러 건 있습니다**
(`90-known-traps.md` §0).
