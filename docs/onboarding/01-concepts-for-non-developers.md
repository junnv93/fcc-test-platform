# 개념 사전 — 개발을 안 해 본 사람을 위해

> 이 문서는 **비유를 쓰지 않습니다.** 「~같은 것」은 처음에는 이해가 빠르지만,
> 실제로 명령을 칠 때는 아무 도움이 안 되고 때로는 틀린 판단을 만듭니다.
> 대신 **정확한 정의 + 이 프로젝트의 실제 예시**로 씁니다.
>
> 모든 예시와 수치는 **2026-09-07 에 이 저장소에서 직접 확인한 것**입니다.

---

## 1. 먼저 — 기계가 세 종류입니다

이 프로젝트에서 「PC」라고 하면 셋 중 하나이고, **셋은 하는 일이 완전히 다릅니다.**
어느 기계 이야기인지 헷갈리면 대화가 통째로 어긋납니다.

| 기계 | 몇 대 | 무엇을 하나 | 누가 만지나 |
|---|---|---|---|
| **개발 PC** | 사람마다 1대 | 코드를 쓴다. 이미지를 만든다 | 당신 |
| **중앙 PC** | **1대** | 웹 화면·DB·인증을 돌린다. 모두가 접속한다 | 운영자 |
| **챔버 PC** | 챔버마다 1대 | 계측기를 잡고 **실제 시험을 수행**한다 | 시험원 |

⚠️ **「내 PC 에서는 됐는데」가 이 프로젝트에서 특히 위험한 이유가 여기 있습니다.**
개발 PC 에는 파이썬도, 라이브러리도, 당신이 몇 달 전에 설치한 무언가도 있습니다.
중앙 PC 에는 **없습니다.** 챔버 PC 는 **Windows** 이고 인터넷도 막혀 있습니다.

실제로 일어난 예 — 챔버 PC 에서만 나타난 것들:

* PowerShell 이 한글 설정 파일을 다르게 읽어 **설정 키 하나가 통째로 사라졌습니다.**
* 콘솔 창을 **마우스로 클릭했더니** 프로그램이 얼어붙었습니다. 밖에서 보면
  「죽지 않았는데 응답이 없는」 상태였습니다.

**둘 다 개발 PC 에서는 재현되지 않습니다.**

## 2. 저장소 · 커밋 · 브랜치 · PR — ⚠️ 여기는 «다른 문서»가 소유합니다

이 낱말들은 이미 정의돼 있습니다:

> **`docs/education/2026-09-06-시스템-연결-구조-시험원-교육자료.html` §00**
> — 저장소 · 커밋 · 브랜치 · 태그 · PR · 머지 · 워크트리 · 패키지 · 휠 · pip ·
> 가상환경 · 핀 · API · 경로 · 스키마 · OpenAPI · 코드 생성 · CI

**그 문서를 먼저 읽으십시오.** 여기서 다시 정의하면 두 곳이 생기고,
**두 곳은 반드시 갈라집니다** — 그리고 갈라진 쪽을 읽은 사람이 틀린 것을 믿게 됩니다.

이 문서가 채우는 것은 그 문서에 **없는 것**입니다 (실측으로 확인):

| 주제 | 그 문서 | 이 문서 |
|---|---|---|
| 저장소 · 커밋 · PR · 패키지 · API | ✅ §00 | — (가리킬 뿐) |
| 저장소 셋의 연결 구조 · 판올림 | ✅ §01~§05 | — |
| **CI 가 실제로 «무엇을» 하나** | 낱말 정의 1줄 | ✅ **§3** |
| **컨테이너 · 이미지 · 빌드** | **0건** | ✅ **§5** |
| **배포 · 이미지 이관** | 3줄 | ✅ **§4 · §6** |
| **provider 화** | **0건** | ✅ `10-provider-lane-kickoff.md` |
| **협업 방식** | **0건** | ✅ `02-how-we-collaborate.md` |

### 다만 이 프로젝트에만 있는 두 가지는 여기서 적습니다

**① 커밋에는 17줄짜리 «자가점검»이 붙습니다.**

```
A-1: PASS — MEMORY.md topic + index 갱신
A-2: SKIP — CLAUDE.md 무변경
...
Self-Audit: 17-items
```

⚠️ **「PASS」만 쓰고 사유를 안 적으면 «거부됩니다».** 사유가 없으면 아무 생각 없이
채울 수 있고, **아무 생각 없이 채운 점검은 점검하지 않은 것과 같은 모양**이기 때문입니다.

**② 브랜치를 «바꾸지» 않고 push 합니다.**

```bash
git push origin HEAD:refs/heads/<이름>
```

여러 세션이 같은 폴더를 동시에 쓰기 때문입니다 — 브랜치를 바꾸면
옆에서 일하던 사람의 발밑이 바뀝니다.

## 3. CI — 「기계가 대신 검사한다」

### 정의

**CI (Continuous Integration, 지속적 통합)** 는
**코드가 바뀔 때마다 «다른 기계»가 자동으로 검사를 돌리는 것**입니다.

여기서 중요한 것은 **「다른 기계」**입니다. 당신 PC 가 아니라
**아무것도 설치돼 있지 않은 깨끗한 기계**에서 처음부터 설치하고 검사합니다.
그래서 「내 PC 에서는 됐는데」를 잡아냅니다.

### GitHub Actions — 우리가 쓰는 CI

GitHub 이 제공하는 CI 입니다. **저장소 안의 `.github/workflows/` 폴더에 있는
YAML 파일**이 「무엇을, 언제, 어떤 순서로」를 적습니다.

우리 저장소에는 **워크플로 6개**가 있습니다 (실측 2026-09-07):

| 파일 | 언제 도나 | 무엇을 하나 |
|---|---|---|
| `checks.yml` | **모든 PR + `main` push** | ⭐ 레인 게이트 — 파이썬 검사 전체 |
| `frontend.yml` | 웹 화면 파일이 바뀐 PR | 빌드 · e2e · 접근성 · 성능 · 인증 적합성 (**4잡 43스텝**) |
| `dependency-audit.yml` | **매주 월요일 06:00** + 관련 PR | 쓰는 라이브러리에 알려진 취약점이 있나 |
| `frontend-qa-evidence.yml` | 웹 파일이 `main` 에 들어갈 때 | QA 증거 기록 |
| `renovate-config.yml` | `renovate.json` 이 바뀔 때 | 그 설정 파일 자체가 유효한가 |
| `frontend-deploy.yml` | **사람이 직접 누를 때만** | 프런트엔드 배포 |

### ⭐ `checks.yml` 이 실제로 하는 일 — 다섯 단계

이것이 **`main` 에 들어가려면 반드시 초록이어야 하는** 유일한 검사입니다.

```yaml
1. actions/checkout@v4        # 깨끗한 기계에 저장소를 받아온다
2. actions/setup-python@v5    # 파이썬을 설치한다
3. pip install -e '.[test]'   # ⚠️ 이 저장소를 «상자로서» 설치한다
4. rm -rf build               # 설치가 남긴 찌꺼기를 치운다
5. python scripts/lane_check.py   # 선언된 실패 집합과 대조한다
```

⚠️ **3번의 `-e` 가 중요합니다.** `-e` 는 editable(수정 가능) 설치이고,
주석이 그 이유를 적습니다 — *"비-editable 은 `build/` 를 남겨 실패 집합을 오염시킨다."*

⚠️ **그리고 이것이 「내 PC 에서 빨간데 CI 는 초록」의 흔한 원인입니다.**
이 문서를 쓰는 동안 실제로 그 일이 있었고, **원인을 끝까지 갈랐습니다:**

```
내 작업 폴더에서 검사       → 실패 61건
전용 환경에 «그 폴더»를 설치하고 다시 검사 → 3359 통과, 실패 0
```

**원인은 「설치를 안 해서」가 아니라 「설치가 «다른 폴더»를 가리켜서」였습니다:**

```
공유 환경의 설치 기록  →  «원본 체크아웃» 을 가리킨다
내 작업 폴더           →  다른 커밋이다

즉 검사는 «내 폴더의 시험 파일» 을 읽고,
   실제 코드는 «원본 폴더» 에서 가져왔다.  둘이 다르면 빨개진다.
```

⚠️ **CI 는 이 문제를 겪지 않습니다** — 깨끗한 기계에서 설치하므로
**검사하는 폴더와 설치된 폴더가 항상 같습니다.**

**빨간 것을 보면 「내가 깨뜨렸다」고 결론하기 전에 «환경이 다른가»를 먼저 물으십시오.**

### `lane_check` — 「개수」가 아니라 「이름 집합」

5번 단계가 하는 판정이 이 프로젝트의 특징입니다.

보통의 검사는 **「실패가 0건인가」**를 묻습니다. 우리는 **「실패한 «이름»들의 집합이
선언과 같은가」**를 묻습니다.

```
선언 (delivered_test_run_baseline.json):  {"lane": "fcc-test-platform", "baseline": []}
                                                                        ↑ 선언된 실패 «0건»
```

⚠️ **왜 개수가 아니라 이름인가.** 하나를 고치고 다른 하나를 깨뜨리면
**개수는 그대로**입니다. 이름 집합으로 보면 그 교체가 드러납니다.

## 4. 배포 — 「개발」과 무엇이 다른가

### 정의

| | 개발 | 배포 |
|---|---|---|
| 무엇을 하나 | 코드를 **바꾼다** | 바뀐 코드를 **실제로 돌아가는 곳에 올린다** |
| 어디서 | 개발 PC | 중앙 PC · 챔버 PC |
| 되돌리기 | 쉽다 (커밋 되돌리기) | **어렵다** — 이미 사람들이 그것을 쓰고 있다 |
| 실패하면 | 나만 막힌다 | **모두가 막힌다** |

⚠️ **이 프로젝트에서 배포가 특히 어려운 이유:** 중앙 PC 와 챔버 PC 는
**폐쇄망**에 있습니다. 인터넷으로 코드를 내려받을 수 없습니다.
그래서 **파일을 손으로 옮겨야 합니다** — 그것이 §5 의 이미지 이야기입니다.

## 5. 컨테이너 이미지 — 이것이 무엇인지가 핵심입니다

여기가 팀원이 **직접 하게 될 작업**이므로 자세히 씁니다.

### 5-1. 문제부터

당신이 측정 프로그램을 만들었다고 합시다. 예를 들어:

```
measure.py              당신이 쓴 코드
requirements.txt        이 코드가 필요로 하는 라이브러리 목록 (fastapi, numpy, pyvisa …)
config.json             설정
```

이것을 중앙 PC 에서 돌리려면 그 PC 에 다음이 **전부** 있어야 합니다:

* 파이썬 — **어느 버전?** 3.11 에서 되던 게 3.13 에서 안 될 수 있습니다
* 라이브러리 전부 — **어느 버전?** 그리고 그 라이브러리가 의존하는 다른 라이브러리들
* 시스템 도구 — 예: 인증서, 폰트, C 라이브러리
* 환경변수 · 폴더 구조 · 권한

**폐쇄망이라 `pip install` 이 안 됩니다.** 인터넷에 못 나가니까요.

### 5-2. 컨테이너 이미지의 정의

**컨테이너 이미지(container image)는 「프로그램 + 그것이 돌기 위해 필요한 모든 것」을
하나로 묶어 놓은 파일**입니다. 여기서 「모든 것」은 리터럴입니다 —
운영체제의 파일들, 파이썬 인터프리터, 라이브러리, 당신의 코드, 설정까지.

**그래서 그 파일을 옮긴 PC 에 파이썬이 없어도 똑같이 돕니다.**
필요한 파이썬이 이미 그 안에 들어 있기 때문입니다.

**컨테이너(container)** 는 그 이미지를 **실제로 실행한 상태**입니다.
이미지는 파일이고, 컨테이너는 돌고 있는 프로세스입니다. 이미지 하나로 컨테이너를
여러 개 띄울 수 있습니다.

### 5-3. Dockerfile — 「무엇을 어떻게 담을지」의 설명서

이미지는 손으로 만들지 않습니다. **`Dockerfile` 이라는 파일에 조립 순서를 적고,
`docker build` 가 그것을 읽어 이미지를 만듭니다.**

우리 저장소의 실제 `Dockerfile.api` 에서 가져온 예 (주석 제거):

```dockerfile
FROM python:3.11-slim AS runtime          # ① 파이썬 3.11 이 든 바탕에서 시작한다
ENV PYTHONUNBUFFERED=1                    # ② 환경변수를 정한다
WORKDIR /app                              # ③ 작업 폴더를 정한다
COPY requirements-central.txt ./          # ④ 의존 목록을 이미지 «안»으로 복사한다
RUN pip install -r /tmp/req-third-party.txt   # ⑤ 그 목록대로 설치한다
COPY fcc_test_platform/ ./fcc_test_platform/  # ⑥ 실제 코드를 복사한다
RUN pip install --no-deps .               # ⑦ 코드를 «상자로서» 설치한다
USER appuser                              # ⑧ root 가 아닌 사용자로 돌린다
```

⚠️ **`COPY` 가 하는 일을 정확히 이해하십시오** — 당신 PC 의 파일을
**이미지 «안으로» 복사**하는 것입니다. 복사되지 않은 파일은 이미지에 **없습니다.**

실제로 그것 때문에 빌드가 죽은 기록이 이 저장소에 있습니다:

> 파일 하나가 다른 곳으로 이사했는데 `COPY logger_config.py` 줄을 안 지워서
> 빌드가 실패했습니다 — `failed to compute cache key … "/logger_config.py": not found`.
>
> ⚠️ **그리고 그 실패를 «게이트 어느 것도 잡지 못했습니다».** 파이썬 검사에서는
> 파일이 사라진 것이 **정상**이었고(그게 이사의 목적이니까), **빌드 축에서만**
> 결함이었기 때문입니다.

### 5-4. 태그 — 이미지의 이름표

```
fcc-unlicensed-headless-api:latest
└────────── 이름 ──────────┘ └태그┘
```

⚠️ **태그는 «이름표»일 뿐이고, 내용물을 보장하지 않습니다.**
같은 `:latest` 가 어제 만든 것을 가리킬 수도, 방금 만든 것을 가리킬 수도 있습니다.

**실제로 일어난 일 (2026-09-04):**

```
개발 PC 의 :latest    → 하루 전 코드였다
그 안의 라이브러리     → 낡아 있었다
컨테이너 상태          → healthy   ← ⚠️ 아무것도 실패하지 않았다
```

**낡은 코드와 낡은 라이브러리가 서로 정합했기 때문**입니다.
**태그만으로는 「다시 만들었는가」에 답할 수 없습니다.**

### 5-5. 리비전 라벨 — 그 답을 만드는 방법

빌드할 때 **어느 커밋으로 만들었는지를 이미지 안에 새겨 넣습니다.**

```bash
docker build ... --build-arg GIT_REVISION="$(git rev-parse HEAD)" ...
```

그리고 나중에 **읽어서 확인**합니다:

```bash
docker inspect <이미지> --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
# → a1b2c3d4...   이 커밋으로 만든 이미지다
```

⚠️ **비워 두면 «비어 있음»이 나오고, 우리 검사는 그것을 «통과»가 아니라 «UNKNOWN»
으로 보고합니다.** 저장소 주석이 그 이유를 적습니다 —
*"「unknown」 같은 기본값을 넣는 것은 같은 침묵을 예쁘게 쓴 것이고,
그럴듯한 값을 넣는 것은 «거짓말»이다."*

## 6. 이미지를 중앙으로 옮기기 — 「압축 폴더로 푼다」의 정확한 내용

이것이 **팀원이 실제로 하게 될 절차**입니다. 전 과정은
**`15-image-handoff-walkthrough.md`** 에 명령 단위로 있고, 여기서는 **개념**만 봅니다.

```
[개발 PC]                          [옮기기]              [중앙 PC]
                                                        
소스 코드                                                
   │ docker build                                        
   ▼                                                     
이미지 (도커 안에 있음)                                    
   │ docker save                                         
   ▼                                                     
headless-api.tar  ──── USB · 공유폴더 · scp ────▶  headless-api.tar
   (파일 하나)                                            │ docker load
                                                         ▼
                                                   이미지 (도커 안에 있음)
                                                         │ docker compose up -d
                                                         ▼
                                                      컨테이너 (돌고 있음)
```

### 각 명령이 하는 일

| 명령 | 하는 일 |
|---|---|
| `docker build` | Dockerfile 을 읽어 **이미지를 만든다** |
| `docker save` | 도커 안의 이미지를 **`.tar` 파일 하나로 뽑아낸다** |
| `docker load` | `.tar` 파일을 읽어 **그 PC 의 도커 안에 이미지를 되돌린다** |
| `docker compose up -d` | 이미지로 **컨테이너를 띄운다** |

⚠️ **`.tar` 는 「압축 폴더」와 «같은 종류의 것»이지만 그 안에 든 것은 폴더가 아니라
이미지의 층(layer)들과 메타데이터입니다.** 그래서 압축 프로그램으로 풀지 않고
**`docker load` 로 풉니다.** 손으로 풀면 도커가 그것을 이미지로 인식하지 못합니다.

### ⚠️ 여기서 반드시 밟는 함정

**`docker load` 만 하고 `docker compose up -d` 를 하면, 새 이미지가 안 붙을 수
있습니다.** 태그가 같으면 이미 돌고 있는 컨테이너가 **그대로 유지**되기 때문입니다.

**컨테이너를 «재생성»하고, §5-5 의 리비전 라벨로 확인하십시오.**
「명령이 성공했다」와 「새 코드가 돌고 있다」는 다른 명제입니다.

## 7. 왜 우리 코드는 이미지로만 중앙에 가나

**중앙 PC 에 provider 저장소를 두지 않기 위해서**입니다.

실측으로 확인된 것 (2026-09-03, 도는 컨테이너 안에서):

```
파이썬이 코드를 찾는 경로에서 /app/src 를 빼면
   platform-api   → 여전히 돈다 (설치된 것만으로 조립된다)
   headless-api   → ModuleNotFoundError  ← provider 소스가 필요했다
```

**중앙 7개 서비스 중 provider 저장소를 실제로 필요로 한 것은 그 하나뿐**이었고,
그 하나 때문에 중앙 PC 가 provider 저장소 전체를 갖고 있어야 했습니다.

그 하나를 이미지로 떼어내자 중앙은 `fcc-test-platform` 하나만 두면 됩니다.
그래서 중앙 compose 의 `headless-api` 에는 **`build:` 줄이 없습니다**:

```yaml
headless-api:
  image: ${FCC_HEADLESS_IMAGE:-fcc-unlicensed-headless-api:latest}
  # build: 가 «없다» — 있으면 중앙에 소스 트리가 있어야 한다
```

⚠️ **provider 가 늘어도 중앙은 그대로 platform 하나입니다.**
provider 마다 이미지가 하나씩 붙을 뿐이고, **그것이 이 설계가 지키려는 성질**입니다.

## 8. 그 밖에 자주 나오는 말들

| 말 | 정확한 뜻 | 이 프로젝트의 예 |
|---|---|---|
| **API** | 프로그램끼리 주고받는 약속된 창구 | `POST /session/start` — 중앙이 챔버에게 「측정 시작해라」 |
| **엔드포인트 / 경로** | API 창구 하나 | 챔버 노드는 **6개**를 만든다 |
| **계약 (contract)** | 「이 API 는 이렇게 생겨야 한다」를 기계가 읽을 수 있게 적은 파일 | `headless_api_contract.v1.json` |
| **스키마** | 데이터가 어떤 모양이어야 하는지의 정의 | `central_db_schema.v1.json` |
| **마이그레이션** | DB 표 구조를 바꾸는 «순서 있는» 파일들 | `migrations/` **35개** |
| **컨테이너 오케스트레이션** | 여러 컨테이너를 함께 띄우고 관리 | `docker compose` |
| **compose 파일** | 「어떤 컨테이너를 어떤 설정으로 함께 띄울지」 | `infra/docker-compose.central.yml` — **7개 서비스** |
| **헬스체크** | 그 컨테이너가 살아 있는지 주기적으로 묻는 것 | headless-api 는 15초마다 `/headless/metrics` 를 부른다 |
| **환경변수** | 프로그램 밖에서 넣어 주는 설정값 | `FCC_CENTRAL_PROVIDER_ID` |
| **heartbeat** | 「나 살아 있다」를 주기적으로 보내는 신호 | 챔버 → 중앙 |
| **OIDC / 토큰** | 「이 요청이 누구 것인지」를 증명하는 표준과 그 증명서 | Keycloak 이 발급 |
| **폐쇄망** | 인터넷에 연결되지 않은 네트워크 | 중앙·챔버 PC |
