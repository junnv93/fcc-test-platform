# 로컬 프로그램을 headless 로 바꾸기 — 먼저 간 사람의 기록

**대상 독자**: 이미 돌아가는 **자기 분야의 로컬 측정 프로그램**(GUI + 계측기 제어 +
결과 기록)을 갖고 있고, 그것을 이 중앙 플랫폼에 붙이려는 개발자.

**이 문서의 성격**: 처방이 아니라 **먼저 간 사람의 기록**입니다. Unlicensed provider 가
PySide6 GUI 프로그램 하나에서 출발해 `headless API` · `세션 노드` · `GUI` 셋이 **같은
코어를 공유**하는 형태에 도달했고, 그 과정에서 무엇이 실제로 문제였는지를 적습니다.

> ⚠️ **소스는 못 보여드립니다.** provider 저장소는 비공개입니다(ADR-0018 D-5).
> 그래서 코드가 아니라 **구조와 그 구조를 고른 이유**를 적습니다. 인용된 수치는 전부
> 실측입니다.

**같이 읽을 것**: `docs/operations/provider-integration-guide.md` — 이 문서가 *「무엇을
어떻게 나누는가」* 라면 그쪽은 *「나눈 뒤 어떻게 배포하는가」* 입니다.

---

## 0. 먼저 — 무엇을 만드는 것인지

「headless 화」는 GUI 를 지우는 것이 아닙니다. **하나의 코어를 여러 껍데기가 공유하게
만드는 것**입니다.

```
                    ┌──────────────────────┐
   GUI 창  ────────▶│                      │
   HTTP API ───────▶│    측정 코어          │──────▶ 계측기 · DUT
   세션 노드 ───────▶│  (프레임워크 무지)     │──────▶ 결과 저장
                    └──────────────────────┘
```

⚠️ **GUI 는 남습니다.** 승인이 나지 않은 챔버 PC 는 계속 로컬 프로그램으로 돕니다
(운영자 판정 2026-08-16: PC 단위 순차 전환). 즉 **둘 다 돌아가는 기간이 길고**, 그
기간에 두 껍데기가 **다른 코드를 돌면** 두 결과가 갈립니다.

**그것이 「코어를 공유한다」가 편의가 아니라 요구인 이유입니다.**

---

## 1. 실제로 어떻게 생겼나 — Unlicensed 의 실측

```
공유 코어         _TestRunnerCore              295 줄
  ├─ GUI 껍데기   TestRunner(QThread, 코어)
  └─ headless     HeadlessTestRunner(threading.Thread, 코어)   210 줄

진입점 넷
  main_entry.py        279 줄   GUI 프로세스
  session_api_app.py    74 줄   챔버 노드가 서빙하는 ASGI 앱
  session_node_entry.py 363 줄  챔버 PC 에서 도는 실행 파일
  headless_api_app.py  131 줄   중앙에서 도는 ASGI 앱
```

**껍데기가 얇습니다.** 74~363 줄이고, 그 안에 측정 로직이 **없습니다.**

핵심은 이 두 줄입니다:

```python
class TestRunner(QThread,               _TestRunnerCore):  ...   # GUI
class HeadlessTestRunner(threading.Thread, _TestRunnerCore):  ...  # headless
```

**스레드 백엔드만 다르고 비즈니스는 같은 객체입니다.**

## 2. 첫 번째 관문 — 코어가 GUI 를 모르게 만들기

### 2-1. 문제의 모양

로컬 프로그램은 보통 이렇게 생겼습니다:

```python
def run_measurement(self):
    self.progress_bar.setValue(0)          # ← GUI 위젯
    for row in rows:
        value = self.analyzer.query(...)
        self.log_box.append(f'{value}')    # ← GUI 위젯
        self.progress_bar.setValue(i)
    QMessageBox.information(self, '완료')   # ← GUI 위젯
```

측정 로직과 화면 갱신이 **같은 함수 안에 섞여** 있습니다. 이 상태로는 HTTP 요청이
그것을 부를 수 없습니다 — 위젯이 없으니까요.

### 2-2. 고른 해법 — 콜백 이음매

발신 지점을 **함수 인자**로 바꿉니다. 코어는 누가 받는지 모릅니다.

```python
def _core_init(self, ..., on_log=None, on_progress=None, on_error=None, ...):
```

Unlicensed 의 실측 개수는 **10개**입니다:

```
on_log · on_completion · on_total · on_progress · on_error
on_notification · on_cells_updated · on_test_plan_updated
on_saving_progress · on_user_input_required
```

그리고 **기본값이 전부 `None` 이고 no-op 으로 떨어집니다** — 아무도 안 붙여도 코어가
돕니다. 그것이 「GUI 없이 도는가」를 시험할 수 있게 만드는 조건입니다.

| 껍데기 | 콜백을 무엇에 연결하나 |
|---|---|
| GUI | Qt Signal → 위젯 |
| headless | `SessionEventPort.publish()` → WebSocket · 로그 · 중앙 |

⚠️ **`on_user_input_required` 가 가장 어려운 하나입니다.** GUI 에서는 대화상자를 띄우고
사람을 기다리면 되지만 headless 에는 사람이 없습니다. **그 지점을 찾아내는 것이 이
작업의 절반**이고, 나머지 절반은 *「그때 무엇을 하기로 정할 것인가」* 라는 **운영
판정**입니다(자동 진행? 세션 실패? 중앙에 물어보기?). 개발자가 혼자 정할 수 없습니다.

### 2-3. 어떻게 지키나 — 선언이 아니라 검사로

「코어는 GUI 를 모른다」는 **지켜지지 않으면 조용히 무너집니다.** 누군가 편의로
`from PySide6...` 한 줄을 넣으면 headless 빌드가 그날부터 깨지는데, 그 사람은 GUI 에서
시험하므로 **모릅니다.**

Unlicensed 는 AST 검사로 못 박았습니다:

```
헤드리스 러너에 PySide6 / PyQt import  →  0건
도메인 계층에 GUI · pandas · 계측기 라이브러리 import  →  0건
```

**규칙을 문서에 적지 말고 검사로 만드십시오.** 문서는 어기는 순간을 못 봅니다.

## 3. 두 번째 관문 — 웹이 요구하는 표면은 작다

중앙이 당신의 코어에 요구하는 것은 **네 가지뿐**입니다:

```python
class TestSessionUseCase(Protocol):
    def start(...) -> ...
    def stop(self) -> None
    def is_running(self) -> bool
    def get_progress(self) -> dict
```

⚠️ **이것이 좋은 소식입니다.** 전부를 고칠 필요가 없습니다. 이 넷을 만족하는 객체
하나만 만들면 웹 어댑터가 그대로 붙습니다.

⚠️ **그리고 나쁜 소식이기도 합니다.** `is_running` 과 `get_progress` 는 **아무 때나
불릴 수 있어야** 합니다 — 측정 중에도요. 로컬 프로그램은 보통 그런 요구를 받은 적이
없어서, 측정 루프가 상태를 물어볼 틈을 안 줍니다.

---

## 4. 세 번째 관문 — 이벤트 루프를 막지 마십시오

**이것이 실장비에서 가장 비싼 실수입니다.**

HTTP 서버는 단일 이벤트 루프로 돕니다. 그 위에서 **동기 함수를 그대로 부르면** 그동안
서버가 **아무것도 서빙하지 못합니다** — 헬스체크도, 진행률도, 중앙 heartbeat 응답도.

Unlicensed 실측: 세션 합성 3.0초 동안 `/session/health` 가 **2.52초 대기**했습니다.

⚠️ **그리고 그 증상이 나쁩니다.** 중앙은 응답 없는 노드를 **죽은 것으로 읽고
로테이션에서 뺍니다.** 노드는 멀쩡히 측정 중인데요.

해법은 무거운 호출을 워커 스레드로 넘기는 것입니다:

```python
result = await run_in_threadpool(lambda: adapter.start(...))
```

⚠️ **그 전환에는 선행 조건이 있습니다** — 측정 슬롯 **상호배제**. 오프로드하면 두
요청이 각자 측정을 시작할 창이 넓어집니다. 배타가 없으면 오프로드가 그 위험을 키웁니다.

---

## 5. 네 번째 관문 — 계측기는 공유 자원입니다

GUI 와 headless 노드가 **같은 PC 에 둘 다 깔릴 수 있습니다**(전환기). 둘이 동시에
뜨면 같은 분석기에 SCPI 가 섞입니다.

⚠️ **실해는 측정 실패가 아니라 「조용히 틀린 값」입니다.** 두 프로세스가 서로의 명령을
받아 각자 그럴듯한 숫자를 냅니다.

Unlicensed 는 **PC 전역 파일 락**으로 막습니다 — 뜨는 쪽이 거부합니다.

```
instrument exclusion scope: ...\Temp\fcc-instrument-access.lock
```

⚠️ **락 키를 「챔버」나 「계측기 주소」로 잡지 마십시오** — 두 프로세스가 서로 다른
값을 볼 수 있고, 그러면 **락 파일이 둘 생기고 아무도 아무것도 막지 않는데 양쪽 다
잡았다고 믿습니다.** PC 전역이 옳습니다.

---

## 6. 다섯 번째 관문 — 결과는 나중에 보내집니다

로컬 프로그램은 결과를 파일에 씁니다. 중앙에 붙으면 **네트워크가 끊긴 동안 측정한
결과**를 어떻게 할지 정해야 합니다.

⚠️ **「보내고 잊는다」는 안 됩니다.** 측정은 되돌릴 수 없고, 중앙이 잠깐 죽었다고
그 데이터가 사라지면 시료를 다시 만들어야 합니다.

Unlicensed 는 **로컬 큐(outbox)** 를 둡니다 — 결과를 먼저 로컬에 확정하고, 별도
경로로 중앙에 밀어 넣고, 성공할 때까지 재시도합니다.

**즉 「측정 완료」와 「중앙 반영 완료」는 다른 사건이고, 둘을 구분해 기록해야 합니다.**

---

## 7. 여섯 번째 관문 — 참조값의 출처가 바뀝니다

로컬 프로그램은 참조값(케이블 손실 · 경로 매핑 · 한계값)을 **자기 파일**에서 읽습니다.
중앙에 붙으면 그 출처가 **중앙 카탈로그**로 옮겨갑니다.

⚠️ **이 전환이 이 작업에서 가장 조용한 위험입니다.**

```
참조값이 틀리면      측정은 정상 완료되고
                    판정도 나오고
                    숫자만 그 차이만큼 틀립니다
                    → 다운스트림에서 탐지 불가
```

세 가지를 지키십시오:

1. **프로젝트는 시작한 모드로 끝냅니다.** 한 프로젝트 도중에 출처를 바꾸지 마십시오.
2. **못 물어본 것과 안 정해진 것을 구분하십시오.** Unlicensed 의 어댑터는 둘 다
   *「로컬 값을 쓰라」* 로 접는데, 그것은 **의도된 설계이고 문서에 그렇게 적혀
   있습니다** — 구분은 호출자의 로그가 합니다. 당신도 그 선택을 **명시적으로** 하고
   기록하십시오. 안 하면 나중에 아무도 어느 값으로 쟀는지 모릅니다.
3. **전환 시 등가성을 확인하십시오.** 같은 시료를 양쪽 출처로 재서 대조합니다.

---

## 8. 그리고 배포에서 만날 것들 — 미리 알고 가십시오

아래는 Unlicensed 가 **첫 실장비 배포 하루에 실제로 만난 11개**입니다. 전부 **개발
PC 에서는 구조적으로 안 보이는 것들**입니다. 상세와 처방은
`docs/operations/provider-integration-guide.md` §8 에 있습니다.

| 계급 | 무엇 |
|---|---|
| **환경** | Store 파이썬으로는 빌드 링크가 실패한다 |
| | Windows PowerShell 이 BOM 없는 UTF-8 을 ANSI 로 읽는다 — 한글이 깨지고 **길이가 홀수면 줄바꿈까지 삼켜 설정 키가 사라진다** |
| | 배열 스플랫이 인자를 한 칸 민다(PowerShell) |
| **레포 분리** | 설치 목록 4개 중 1개만 분리를 따라갔다 |
| | 분리 설치 규칙이 Dockerfile 안에만 살아 있어 그 매체가 없는 레인에 안 닿았다 |
| | 권장 포트가 다른 저장소 문서에만 있었다 |
| **문서** | 런북이 도구가 **거부하는** 값을 가르쳤다 |
| | 코드가 바뀐 날 문서가 안 따라가 **오지 않을 신호**를 찾게 했다 |
| **운영** | 콘솔 창을 클릭하면 노드가 얼어붙는다 — TCP 는 붙고 응답만 없다 |
| | 첫 설치가 비밀 파일을 잠가 **두 번째 설치를 막았다** |
| | 검사가 옳게 막았는데 **무엇을 고칠지 말하지 않아** 왕복이 생겼다 |

⚠️ **마지막 계급을 특히 보십시오.** 셋 다 「실패했다」와 「정상이다」가 **화면에서
같은 모양**이었습니다.

## 9. 순서 — 무엇부터 하나

```
① 코어와 화면을 가른다              ← 가장 오래 걸린다. 나머지는 여기 의존한다
② GUI 없이 도는지 검사로 못 박는다   ← 선언 말고 AST 검사
③ 네 메서드 표면을 맞춘다            start / stop / is_running / get_progress
④ 이벤트 루프를 막지 않게 오프로드    ← 선행: 측정 슬롯 상호배제
⑤ 계측기 배타 락                    ← PC 전역 키
⑥ 결과 outbox                      ← 측정 완료 ≠ 중앙 반영 완료
⑦ 참조값 출처 전환 + 등가성 확인
⑧ 계약 적합성 · 이미지 · 챔버 노드    → provider-integration-guide.md
```

⚠️ **①을 건너뛰고 ③부터 하고 싶어집니다** — 껍데기만 씌우면 돌아 보이니까요. 그러면
GUI 판과 headless 판이 **다른 코드**가 되고, 두 판의 측정 결과가 갈리기 시작하는데
**그것을 발견하는 시점은 성적서가 나온 뒤**입니다.

---

## 10. 이 문서를 갱신하는 규칙

⚠️ **이 문서의 수치는 특정 시점의 실측입니다**(2026-09-04, Unlicensed provider).
콜백 10개 · 코어 295줄 · 포트 89개 같은 값은 **바뀝니다.**

숫자가 낡는 것은 괜찮습니다. **문제는 「그때는 이랬다」와 「지금도 이렇다」가 구분되지
않는 것**입니다. 그래서 인용에는 **날짜와 출처**를 함께 적었습니다.

⚠️ 그리고 이 문서는 **provider 저장소를 인용하지 않습니다.** 읽는 사람이 열 수 없는
파일을 「참고하라」고 적으면 그것은 안내가 아니라 막다른 길입니다 — 그 교훈 자체가
위 §8 「문서」 계급에서 나왔습니다.
