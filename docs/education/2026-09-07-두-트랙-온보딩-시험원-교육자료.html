두 트랙 온보딩

합류하는 분은 두 가지 일을 동시에 하게 됩니다 — 자기 계측 프로그램을 provider 로 만드는 일과 이 플랫폼을 함께 개발하는 일. 두 일은 레포가 다르고, 당신의 역할이 다르고, 규율이 다릅니다. 이 문서는 그 둘을 갈라 놓고, 개발을 안 해 본 분이 이미지 빌드부터 배포까지 직접 할 수 있도록 개념과 절차를 함께 적습니다.

한 문장으로 — 이 프로젝트가 지키려는 것

거의 모든 설계 결정이 이 문장 하나에서 나옵니다.

여러 시험 분야가 하나의 웹 플랫폼을 공유하고, 각 분야의 「시험 지식」은 그 분야가 소유한 서비스 안에만 있습니다.

무엇을 어디에 둘지 헷갈릴 때 물어야 하는 질문은 언제나 하나입니다 — 이것은 분야 지식인가, 아니면 분야와 무관하게 참인 것인가?

분야 지식(스펙트럼 분석기 제어 · 시험계획 규칙 · 성적서 양식)이면 플랫폼에 두지 않습니다. 두는 순간 provider 가 늘 때마다 플랫폼을 고쳐야 하는 구조가 되고, 그것이 이 설계가 막으려는 바로 그것입니다.

당신이 하는 두 가지 일

가장 위험한 실수는 한쪽 습관을 다른 쪽에 가져가는 것입니다.

구체적인 예 하나. 필요한 파일을 옆에 복사해 두는 것은 당신 레포에서는 자연스러운 동작입니다. 그런데 플랫폼에서 계약 아티팩트를 복사하는 것은 운영자가 2026-08-31 에 명시적으로 기각한 형태입니다.

이유는 아래 「가장 나쁜 길」 절에 있습니다. 여기서 요점은 — 같은 손동작이 한쪽에서는 정상이고 다른 쪽에서는 사고입니다.

기초

왜 저장소가 나뉘어 있나

신규 합류자가 가장 자주 하는 질문이고, 이 답을 모르면 무엇을 어디에 넣을지 매번 틀립니다.

먼저 — 「운영 분리」와 「저장소 분리」는 다른 결정입니다

⚠️ 그리고 결정문은 「빨리 나누는 것」이 «해롭다»고 적습니다. ADR-0018 D-2 — "provider 가 하나뿐인 지금 전부 쪼개면, 버전 동기화·publish· 레포별 CI 비용은 모두 치르고 독립 개발 이득은 없다."

더 큰 위험도 적습니다 — "계약이 «단일 provider 가정»으로 레포 경계에 굳는다. 계약이 아직 흔들리는 중일 때 쪼개면 2번째 provider 개발자가 매 변경마다 깨진다 — 빨리 쪼개는 것이 오히려 방해가 된다."

그래서 3단계로 나눠, 약속이 안정된 뒤에 실제로 쪼갰습니다.

세 저장소 — 각각의 성격

⚠️ contracts 의 의존성이 «0개»인 것이 설계입니다. provider 팀이 이것을 설치할 때 딸려 오는 것이 없습니다. 만약 여기가 웹 프레임워크나 DB 드라이버에 의존하면, 계약만 확인하고 싶은 사람도 그것들을 전부 설치해야 하고, 그러면 「약속을 확인하는 비용」이 「약속을 지키는 비용」보다 커집니다.

이것이 «일상»에 미치는 영향

가장 자주 하는 실수 둘.

① 커널에 있어야 할 것을 platform 에 두는 것. 당장은 됩니다. 그리고 두 번째 provider 가 붙는 날 드러납니다 — 그때는 이미 platform 이 그 위에 쌓여 있습니다.

② 분야 지식을 커널에 두는 것. 커널은 모두가 씁니다. 거기에 한 분야의 가정이 들어가면 다른 분야가 그것을 따라야 합니다.

왜 «다시 합치지» 않나

합쳤을 때결과
provider 팀이 서로의 측정 코드를 본다비공개 전제가 깨진다 (ADR-0018 D-5)
한 팀의 커밋이 다른 팀 CI 를 깨뜨린다서로를 기다리게 된다 — 분리의 목적이 사라진다
계약이 「지금 코드가 하는 것」이 된다약속이 사라진다. 계약은 코드와 «따로» 있어야 검사할 수 있다

그리고 되돌릴 수 없는 사실이 하나 더 있습니다 — 배송 기계는 2026-08-31 에 퇴역했습니다. 예전에는 모노레포가 두 레인을 «만들어» 내보냈지만, 지금은 방향이 역전돼 모노레포가 두 패키지를 pip 로 «소비»합니다. 재배송은 물리적으로 불가능합니다 — 그 스크립트도 폴더도 삭제됐습니다. 두 레인은 이제 «스스로 사는» 저장소입니다.

기초

먼저 — 기계가 세 종류입니다

「PC」라고 하면 셋 중 하나이고, 셋은 하는 일이 완전히 다릅니다. 어느 기계 이야기인지 헷갈리면 대화가 통째로 어긋납니다.

기계대수무엇을 하나거기 있는 것거기 «없는» 것
개발 PC사람마다 1 코드를 쓴다. 이미지를 만든다 파이썬 · 라이브러리 · 인터넷 —
중앙 PC1 웹 화면 · DB · 인증을 돌린다. 모두가 접속한다 Docker 만 인터넷 · 파이썬 · 당신의 소스

「내 PC 에서는 됐는데」가 이 프로젝트에서 특히 위험한 이유가 여기 있습니다. 개발 PC 에는 파이썬도, 라이브러리도, 당신이 몇 달 전에 설치한 무언가도 있습니다. 중앙 PC 에는 없습니다. 챔버 PC 는 Windows 이고 인터넷도 막혀 있습니다.

실제로 챔버 PC 에서만 나타난 것 둘 — PowerShell 이 한글 설정 파일을 다르게 읽어 설정 키 하나가 통째로 사라졌고, 콘솔 창을 마우스로 클릭했더니 프로그램이 얼어붙었습니다. 둘 다 개발 PC 에서는 재현되지 않습니다.

무엇이 어디서 도는가

★ 표시 둘만 provider 가 만듭니다. 나머지는 플랫폼이 소유합니다.

✅ 문서 세 곳이 「중앙 5개 서비스」라고 적고 있었고, 실측은 7개입니다 — 이 웨이브에서 «고쳤습니다». central-migrate(일회성)와 platform-api-node(브라우저와 노드의 인증 모드가 반대라 갈라놓은 두 번째 인스턴스)가 나중에 붙었고 문장이 따라오지 않았습니다.

⚠️ 그 문서들의 결론은 처음부터 참이었습니다 — provider 저장소를 실제로 필요로 하는 서비스는 headless-api 하나뿐입니다. 틀렸던 것은 분모이고, 결론이 맞다고 분모를 두면 다음 사람이 docker compose ps 에서 7줄을 보고 「뭔가 잘못됐다」고 판단합니다. 그래서 고쳤고, 각 자리에 정정 주석을 남겼습니다.

계측 프로그램은 중앙과 어떻게 말하나

연결은 두 방향이고, 그 비대칭이 진단을 어렵게 만듭니다.

방향무엇말하는 내용
챔버 → 중앙 POST /platform/chambers/heartbeat 「나 살아 있다 / 측정 중이다 / 진행률은 이만큼」
중앙은 이것이 끊기면 OFFLINE 을 «파생»한다 — 저장하지 않는다
중앙 → 챔버 POST http://<챔버 IP>:<포트>/session/start 「이 계획으로 측정해라」

이 비대칭이 만드는 특유의 증상을 기억하십시오. base_url 이 틀리거나 포트가 방화벽 승인 밖이면 — heartbeat 는 챔버→중앙 방향이라 성공하고, 중앙→챔버 forward 만 막힙니다.

화면에는 「연결 안 됨」이 아니라 「노드는 살아 있는데 아무것도 안 온다」 로 보입니다. 「살아 있는데 조용함」이 이 결함의 얼굴입니다.

챔버 노드가 구현하는 계약 — 6 경로뿐입니다

GET   /session/info          API 버전 + 오퍼레이션 카탈로그
GET   /session/is-running    지금 측정 중인가
GET   /session/progress      진행률
POST  /session/start         측정 시작
POST  /session/stop          측정 중지
POST  /session/workbook      .xlsx 업로드 → «불투명 핸들» 반환

⚠️ /session/workbook 이 파일 경로가 아니라 핸들을 돌려주는 것은 설계입니다. 계약 원문 — "노드가 바이트를 어디에 둘지 정한다. 핸들이 start_session 이 받는 유일한 것이고, 따라서 클라이언트가 파일시스템 경로를 이름으로 부르는 일이 없다."

경로를 주고받게 만들면 중앙이 챔버의 디스크 구조를 알게 되고, 분야 중립성이 깨집니다.

Track A · 기초

컨테이너 이미지 — 이것이 무엇인지가 핵심입니다

팀원이 직접 하게 될 작업이므로 개념부터 봅니다.

먼저 문제부터

당신이 측정 프로그램을 만들었다고 합시다. 예를 들어 measure.py, 필요한 라이브러리 목록 requirements.txt, 설정 config.json.

이것을 중앙 PC 에서 돌리려면 그 PC 에 파이썬이 어느 버전으로 있어야 하고, 라이브러리가 어느 버전으로 전부 있어야 하고, 그 라이브러리가 의존하는 다른 라이브러리들도 있어야 합니다. 그런데 폐쇄망이라 pip install 이 안 됩니다.

Dockerfile — 「무엇을 어떻게 담을지」의 설명서

이미지는 손으로 만들지 않습니다. Dockerfile 에 조립 순서를 적고, docker build 가 그것을 읽어 이미지를 만듭니다. 우리 저장소의 실제 파일에서 가져온 예입니다(주석 제거): 

FROM python:3.11-slim AS runtime          ① 파이썬 3.11 이 든 바탕에서 시작한다
ENV PYTHONUNBUFFERED=1                    ② 환경변수를 정한다
WORKDIR /app                              ③ 작업 폴더를 정한다
COPY requirements-central.txt ./          ④ 의존 목록을 이미지 «안»으로 복사
RUN pip install -r /tmp/req-third-party.txt   ⑤ 그 목록대로 설치
COPY fcc_test_platform/ ./fcc_test_platform/  ⑥ 실제 코드를 복사
RUN pip install --no-deps .               ⑦ 코드를 «상자로서» 설치
USER appuser                              ⑧ root 가 아닌 사용자로 돌린다

⚠️ COPY 가 하는 일을 정확히 이해하십시오 — 당신 PC 의 파일을 이미지 «안으로» 복사하는 것입니다. 복사되지 않은 파일은 이미지에 없습니다.

실제로 그것 때문에 빌드가 죽은 기록이 있습니다 — 파일 하나가 이사했는데 COPY 줄을 안 지워서 failed to compute cache key … not found. ⚠️ 그리고 그 실패를 파이썬 검사가 «잡지 못했습니다» — 파이썬 축에서는 파일이 사라진 것이 정상이었고 (그게 이사의 목적이니까), 빌드 축에서만 결함이었기 때문입니다.

Track A · 실무

이미지를 만들어 중앙에 넣기 — 전 과정

이것이 팀원이 새 코드를 반영할 때마다 반복하게 될 절차입니다. 한 번 하고 끝나는 설치가 아닙니다.

⚠️ .tar 를 압축 프로그램으로 «풀지» 마십시오. 안에 든 것은 폴더가 아니라 이미지의 층(layer)과 메타데이터이고, 손으로 풀면 도커가 그것을 이미지로 인식하지 못합니다. 반드시 docker load 로 풉니다.

왜 ⑦ 이 필요한가 — 「같은 이름표, 다른 내용물」

Track A · provider 화

가장 쉽고 가장 나쁜 길

이 절이 이 문서에서 가장 중요합니다. 코드를 한 줄도 안 고치고 검사가 초록이 되는 길이 열려 있습니다.

두 번째 provider 가 붙을 때, 손에 가장 잘 잡히는 해법은 「그 계약 파일을 여기로 복사해 오는 것」입니다. 그리고 그렇게 하면 통과합니다 — 해소기에 폴백이 있기 때문입니다. 

def _resolve_artifact_path(registry_path, project_root, artifact):
    ...
    candidate = project_root / path
    if candidate.exists():
        return candidate
    return registry_path.parent / path      ← 레지스트리 «옆» 을 본다

그 초록은 「provider 의 코드가 계약을 만족한다」는 보고가 아니라 「우리가 둔 사본이 계약을 만족한다」는 보고입니다.

⚠️ 이미 한 번 일어났습니다. 레지스트리 사본이 갈라졌고, 모노레포 체커를 돌려 보니 3 provider 전부 schema_mismatch 였습니다 — 그것을 돌리는 게이트가 없어 아무도 못 봤습니다.

운영자 판정 (2026-08-31): 아티팩트는 발행처에 머문다. provider 가 자기 레포에서 자기 계약을 검사하고, 중앙은 그 결과만 받는다.

Track B · 기초

CI — 「다른 기계가 대신 검사한다」

CI(Continuous Integration)는 코드가 바뀔 때마다 «다른 기계»가 자동으로 검사를 돌리는 것입니다.

여기서 중요한 것은 「다른 기계」입니다. 당신 PC 가 아니라 아무것도 설치돼 있지 않은 깨끗한 기계에서 처음부터 설치하고 검사합니다. 그래서 「내 PC 에서는 됐는데」를 잡아냅니다.

우리는 GitHub Actions 를 씁니다. 저장소 안의 .github/workflows/ 폴더에 있는 파일이 「무엇을, 언제, 어떤 순서로」를 적습니다. 실측 워크플로 6개:

파일언제 도나무엇을 하나
checks.yml모든 PR + main push⭐ 레인 게이트 — 파이썬 검사 전체
frontend.yml웹 화면 파일이 바뀐 PR빌드 · e2e · 접근성 · 성능 · 인증 적합성 (4잡 43스텝)
dependency-audit.yml매주 월요일 06:00쓰는 라이브러리에 알려진 취약점이 있나
frontend-qa-evidence.yml웹 파일이 main 에 들어갈 때QA 증거 기록
renovate-config.ymlrenovate.json 이 바뀔 때그 설정 파일 «자체»가 유효한가
frontend-deploy.yml사람이 직접 누를 때만프런트엔드 배포

⭐ checks.yml 이 실제로 하는 다섯 단계

⚠️ 원인은 「설치를 안 해서」가 아니라 「설치가 «다른 폴더»를 가리켜서」였습니다. 공유 환경의 설치 기록이 원본 체크아웃을 가리키고 있었고, 내 작업 폴더는 다른 커밋이었습니다. 검사는 내 폴더의 시험 파일을 읽고, 실제 코드는 원본 폴더에서 가져왔습니다.

⚠️ CI 는 이 문제를 겪지 않습니다 — 깨끗한 기계에서 설치하므로 검사하는 폴더와 설치된 폴더가 항상 같습니다.

⚠️ lane_check 은 「실패가 0건인가」를 묻지 않습니다. 「실패한 «이름»들의 집합이 선언과 같은가」를 묻습니다. 하나를 고치고 다른 하나를 깨뜨리면 개수는 그대로이지만, 이름 집합으로 보면 그 교체가 드러납니다.

「지키자」는 규칙이 아닙니다. 「못 하게 한다」가 규칙입니다.

층어디서무엇을 막나우회
L0CLAUDE.md(막지 않음) 규칙을 도달시킴—

L1~L3 은 실수 방지층이지 방어층이 아닙니다. 셋 다 우회할 수 있습니다 — 로컬 PC 에서 도는 것은 그 PC 의 주인이 끌 수 있기 때문입니다.

실제로 강제되는 것은 L4 하나뿐입니다. 실측(fcc-test-platform): enforce_admins: true — 관리자도 우회 못 합니다.

✅ 그리고 이것은 «두 레인 다» 참입니다. 계약 커널 fcc-test-contracts 도 enforce_admins: true 입니다(2026-09-07 13:4x 부터). 두 레인 모두 관리자가 L4 를 우회하지 못합니다.

🔄 정정 — 이 문단은 같은 날 «두 번» 바뀌었습니다. 12:08 판은 "이것은 «이 레인만» 참입니다. contracts 는 enforce_admins: false 이고 거기서는 L4 도 관리자가 우회할 수 있습니다 … 대가는 그 레인에서 「red 면 서버가 막는다」가 거짓이라는 것" 이었습니다. 13:4x 에 true 가 되어 그 대가가 사라졌습니다. 뒤집힌 이유는 근거가 틀려서가 아니라 근거의 «전제»(러너 할당량 미해소)가 해소돼서입니다 — 되돌리는 조건은 contracts/CLAUDE.md §enforce_admins 절에 적혀 있습니다.

🔴 그런데 required_approving_review_count: 0 입니다. 🔄 정정 — 「동료 1인 승인」은 2026-09-07 2차 개정으로 «폐기»됐습니다. 이 자료의 앞 판은 "즉 「동료 1인 승인」은 오늘 사람이 지키는 규율이지 기계가 막는 게이트가 아닙니다" 라고 적었습니다. 지금은 승인자가 아예 없습니다 — 개발 담당자가 Status: accepted 를 적고 직접 머지합니다. 폐기 사유는 「그 규칙이 가리킨 사람이 존재하지 않았다」 입니다(협업자 1명 + 자기 PR 자기 승인 금지). 그 자리를 순서 게이트(spec 이 있으면 intent 는 accepted 여야 한다)와 방아쇠 T2~T5 가 메웁니다 — 버튼이 아니라 «문장»을 요구하므로 혼자 일해도 공허해지지 않습니다. SSOT → intent/README.md

그러면 L0~L3 은 왜 만드나요? 막기 위해서가 아니라, 우회할 이유가 없게 만들기 위해서입니다. 올바른 길이 가장 쉬운 길이면 아무도 벗어나지 않습니다. 게이트가 오탐을 내거나 짜증나면 사람들은 --no-verify 를 배우고, 그날부터 그 게이트는 0층이 됩니다.

레인 게이트는 «개수»가 아니라 «이름 집합»으로 판정합니다

lane_check.py 는 「전부 통과」가 아니라 관측된 실패 이름 집합 == 선언을 봅니다. 하나 고치고 하나 깨뜨리면 개수는 같습니다. 이 레인의 선언된 실패는 0 이므로, 실패를 보면 그것은 당신 환경 문제이거나 새로 깨진 것입니다.

속도는 에이전트에, 책임은 사람에, 강제는 기계에.

⚠️ 셋 중 하나가 남의 일을 하면 구조가 무너집니다. 사람이 초안을 쓰면 속도의 이득이 사라지고, 사람이 승인을 안 하면 책임이 사라지고, 기계가 판단하려 들면 통제가 사라집니다. 마지막 항목 때문에, 이 프로젝트의 감지 로직은 「기준을 넘었는가」만 기계가 판정하고 그 다음부터 사람과 에이전트가 붙습니다.

리드는 «상시 승인자»가 아니라 «예외 판단자» 입니다. 리드가 모든 것을 승인하는 구조는 초판 설계였고 폐기됐습니다 — 항상 승인되는 승인은 승인이 아니라 서명이기 때문입니다.

이것은 이 저장소가 반복해 기록한 「공허한 검사는 초록과 구별되지 않는다」의 «사람 버전»입니다. 고칠 것은 리드의 주의력이 아니라, 판단이 필요한 소수를 나머지와 다르게 «생기게» 만드는 일입니다 — 그것이 방아쇠 다섯입니다.

문서가 낡는 것은 이 프로젝트에서 가장 자주 재발하는 사고 유형입니다.

낡은 문장은 틀렸다고 말해 주지 않고, 맞는 문장과 똑같이 생겼습니다. 이 교육자료를 만들면서 기존 문서를 재검증했고 거짓인 서술 다섯을 찾았습니다. 그리고 같은 날 오후에 여섯이 더 나왔습니다 — 그중 하나는 이 자료 자신이었습니다.

그래서 docs/onboarding/90-known-traps.md 의 각 항목에는 「이 함정에 서 있는지 스스로 묻는 질문」이 붙어 있습니다. 기억이 아니라 질문이 방어입니다.
