2. 핀 한 줄이 켠 것

①의 0 과 ④의 0 은 화면에서 구별되지 않습니다. 게이트는 두 경우 모두 초록을 냅니다. 「검사를 돌렸는데 통과했다」와 「검사가 아무것도 안 봤다」가 같은 출력입니다.

3. 왜 안 보였나 — 파일 하나가 켜고 끄는 스위치

파이썬 배포판에는 py.typed 라는 빈 파일을 넣는 규약이 있습니다(PEP 561). 내용이 없습니다. 이름만 있습니다. 그 파일이 하는 말은 하나입니다 — 「이 패키지의 타입 선언을 믿어도 된다」.

그 파일이 없으면 검사기는 그 패키지에서 들어오는 모든 것을 Any(= 무엇이든 될 수 있음)로 처리합니다. Any 는 어떤 검사에도 걸리지 않습니다.

여기에 두 번째 함정이 겹쳐 있었습니다. 이 저장소의 검사 설정에는 ignore_missing_imports = True 가 켜져 있습니다. 그래서 「이 패키지는 타입이 없습니다」라는 경고조차 뜨지 않았습니다. 아무 신호 없이 0건이 검사됐습니다.

4. 드러난 79건은 어떤 종류였나

전부 「선언이 사실과 다르다」였고, 어긋난 방향이 넷이었습니다. 처방이 각각 다릅니다.

갈래 ① — 이미 적혀 있는 사실을 손으로 지워 놓았다 15건

def _ingest() -> object:                    # ← 「무엇이든 돌려준다」고 선언
    return execute_platform_ingestion_plan(...)

# 그런데 «바로 그 파일»에:
def execute_platform_ingestion_plan(...) -> IngestionExecutionResult:

부르는 함수가 자기 반환형을 정확히 선언하고 있는데, 감싼 쪽이 그것을 object 로 버렸습니다. 그래서 그 결과의 .committed·.errors 를 읽는 자리가 전부 검사 밖이었습니다. 처방: 거짓말을 지우고 사실을 적는다.

갈래 ② — 값 종류가 섞인 표를 만들면 안이 안 보인다 12건

state = {
    'postgresql_setting': str(...),      # 문자열
    'fk_sample_id': { ... },             # 표
}
state['fk_sample_id']['on_delete_set_null']   # ← 여기서 막힌다

문자열과 표를 한 사전에 담으면 검사기는 값의 종류를 「둘의 공통 상위」로 합칩니다. 그러면 바깥 첨자가 내놓는 값에 안쪽 첨자를 걸 수 없습니다. 처방: 중첩된 표를 이름 있는 변수로 꺼내고 그 변수를 읽는다 — 같은 객체이므로 동작은 그대로입니다.

갈래 ③ — 선언이 모든 실제 호출자보다 넓다 8건

선언호출자 전수 조사고친 값
clock: Callable[[], object]생산 1 + 시험 2 = 셋 다 datetimeCallable[[], datetime]
rate_limit_policy: object생산은 정책, 시험은 None 또는 정책. 소비자 셋 다 정책만 요구Optional[RateLimitPolicy]

이 갈래에서 실제 고장 하나가 나왔습니다 — 로그인 전체가 멈출 수 있는 자리입니다.

잠금 판정 함수 is_lock_active 는 총함수라 이상한 값이 들어오면 예외를 잡아 True(=잠김) 로 접습니다. 즉 시각을 넘기는 배선이 잘못되면 타입 오류가 아니라 「전원 로그인 실패」로 나타납니다. 증상이 원인에서 멀리 떨어져 있어 현장에서 진단이 오래 걸리는 형태입니다.

선언이 object 로 넓게 열려 있는 동안, 그 오배선은 검사기에 안 걸렸습니다.

갈래 ④ — 사실이 두 문장에 흩어져 있어 검사기가 못 잇는다 7건

for name in names:
    match = PATTERN.match(name)
    if match and int(match.group('number')) <= 11:
        selected.append(name)          # ← 여기서 매치를 «버린다»

numbers = [int(PATTERN.match(n).group('number')) for n in selected]
#                              ↑ 다시 돌린다. 여기서는 None 이 아닌데
#                                그 사실이 위 루프에 있어서 검사기가 못 본다

처방: 매치를 버리지 않고 한 루프에서 이름과 번호를 함께 들고 나온다. 정규식 재실행도 같이 사라집니다.

5. 시험 증거에 직접 걸리는 자리 넷

위 네 갈래 중 동작이 실제로 바뀔 수 있던 것만 따로 모았습니다.

  1. 1
    진행률 조인 키에 None 이 실릴 수 있었습니다. 커널은 condition_hash 를 「materialize 전에는 None」 으로 정의합니다. 그런데 그것을 받는 모듈은 「materialized 된 행만 온다」는 전제를 산문으로만 갖고 있었습니다. 미materialize 행이 하나 섞이면 None 이 진행률 집계의 조인 키로 조용히 들어갑니다. 전제를 실행 가능한 검사로 바꿨습니다.
  2. 2
    fetchone() 결과를 검사 없이 첨자로 읽었습니다. provider_identity_live_proof_cli. 행이 없으면 무엇이 없었는지 못 말하고 죽습니다.
  3. 3
    폴백 값의 «종»이 달랐습니다. check_auth_mode_pairing_cli 가 계약 실패 시 쓰는 대체값이 빈 사전인데 진짜 선언은 집합입니다. 둘 다 비어 있어 오늘은 같아 보이지만, 그 이름을 집합으로 읽는 사람이 폴백 경로에서만 다른 것을 받습니다.
  4. 4
    라이브 증명 도구가 자기 연결을 따로 열고 있었습니다. 생산 배선에 이미 연결 팩토리가 있는데 익명 람다로 따로 열었습니다. 라이브 증명이 증명해야 하는 것은 생산 배선입니다 — 따로 열면 증명 대상이 갈립니다. 생산 팩토리를 쓰도록 바꿨습니다(동작 동일).

6. 「둘 중 하나를 포기하라」가 거짓이었다

설계서에 이런 판정이 적혀 있었습니다 — 「권한 표를 읽는 이 자리는 부재를 차단으로 읽는 성질을 지켜야 하므로, 타입 검사를 포기하는 것이 옳다」. 그리고 그 자리는 무접촉 대상이었습니다.

갈래를 둘만 봤습니다.

형태부재 → 차단오타를 잡나
OPS.get(op) or {} → .get('permission')✔✘
OPS[op]✘✔
OPS.get(op) → is None 분기 → 첨자✔✔

셋째를 아무도 보지 않았습니다. 주입으로 갈랐습니다 — 일부러 permisson 이라고 오타를 넣어 두 형태를 돌렸습니다. 첫째는 아무 말도 안 했고, 셋째는 키 이름을 짚어 잡았습니다. 부재 동작은 둘이 동일했습니다.

.get() 은 키 «이름»을 전혀 보지 않습니다. 그래서 「부재를 빈 표로 접는」 형태는 차단 성질을 사는 대신 검사 전부를 팝니다. 필수 키라면 is None 분기 하나로 둘 다 얻습니다.

⚠️ 다만 모든 자리가 그렇지는 않습니다. 계약 레인의 대칭 자리는 바로 아래에 missing_permission_contract 라는 선언된 결과가 있고 그것을 봉인하는 시험이 있습니다. 거기서 첨자로 바꾸면 그 분기가 예외로 바뀌어 사라집니다. 그래서 그 자리는 유지했습니다 — 결론은 살아남고 근거가 바뀐 경우입니다.

7. 임시 우회에 «지울 조건»을 적어 두면

상류(다른 저장소)가 틀려서 이쪽에 임시 우회를 둘 때가 있습니다. 이번에 형제 세션이 우회마다 같은 문장을 붙였습니다:

「이것은 수리가 아니다. 창이 열리면 지워라 — 지워도 초록이면 상류가 고쳐진 것이다.」

이번 세션에 그 사슬이 끝까지 돌았습니다.

시험 설계에 그대로 옮길 수 있는 형태입니다. 임시 조치를 남길 때 셋을 적으세요 — ⓐ 무엇이 틀렸는지(실측값) ⓑ 왜 여기서 못 고치는지 ⓒ 지우는 방법과, 지운 뒤 무엇이 참이어야 하는지. ⓒ 가 없으면 임시 조치는 영구화됩니다.

8. 게이트가 나를 세 번 막았고, 세 번 다 옳았습니다

  1. 1
    버전 봉인. 배포판을 고쳐 놓고 번호를 안 올렸습니다. ⚠️ 그 검사는 커밋한 «뒤»에만 답합니다(발행된 태그와 현재를 비교하므로). 커밋 전에 게이트를 세 번 돌려 세 번 다 초록을 봤습니다.
  2. 2
    핀 정합 봉인. 「선언된 핀 == 설치된 버전」을 요구하는데 제 검사 환경이 낡아 있었습니다. 장부 JSON 한 줄만 고치는 변경이었는데도 그 축을 지나야 했습니다.
  3. 3
    태그 push 게이트. 태그를 올릴 때도 검사가 돕니다. 그래서 태그가 가리키는 바로 그 트리를 펼쳐 거기서 통과시켰습니다 — 태그가 담을 내용으로 재는 것이 맞습니다.

이 기계에는 타입 검사기(mypy)가 어디에도 설치돼 있지 않습니다. 게이트의 mypy 팔은 「설치돼 있지 않으면 skip」인데, skipping 은 초록과 같은 모양입니다. CI 는 검사기를 함께 설치하므로 이빨이 있습니다.

즉 「내 손에서는 초록인데 올리면 빨갛다」가 되고, 그 원인이 아무 데도 안 적혀 있습니다. 저는 push 마다 FCC_LANE_CHECK_PYTHON 을 검사기가 «있는» 인터프리터로 가리켜 넘겼습니다.

① 무접촉 지시의 줄 번호를 «내» 트리에서 확인했습니다

형제 세션이 548-549 를 손대지 말라고 했습니다. 저는 제 트리의 546~551 을 열어 보고 「안 건드렸다」고 답했습니다. 그런데:

② 「그 태그는 존재하지 않는다」가 몇 시간 뒤 거짓이 됐습니다

커널 버전 번호를 고르면서 kernel-v0.5.3 이 없는 것을 확인하고 주석에 그렇게 적었습니다. 그날 08:18 에 형제가 그 태그를 냈습니다.

두 오류의 공통점: 동작을 하나도 바꾸지 않는 문장이라 어떤 게이트도 검사하지 않습니다. 스스로 빨개지지 않고, 사실이 움직여도 조용합니다.

⚠️ 그리고 ②의 문장은 태그 메시지에도 들어갔습니다. 태그는 옮기지 않는 것이 규칙이라 kernel-v0.5.4 안에 영구히 거짓인 채로 남습니다. 주석 두 곳만 정정했습니다(#142·#52).

처방 — 시점이 아니라 포함 관계로 적으세요.
「0.5.3 은 태그가 없어서」 → 사실이 움직이면 죽습니다.
「0.5.3 은 이 수정을 안 담아서」 → 태그가 생겨도 참입니다.

그리고 쓰는 순간 불변이 되는 자리(태그 메시지·머지 커밋 메시지)에는 시점형 문장을 아예 쓰지 않는 것이 유일한 방어입니다.

    커널의 요청 검증기는 「있고, 문자열이고, 비어 있지 않다」를 실제로 증명한 뒤 dict[str, object] 를 돌려줍니다. 증명한 것을 반환형이 안 담습니다. 정공은 그 검증기가 TypedDict 를 돌려주는 것이고, 이번에 고친 OperationSpec 과 같은 계급입니다. 계약 레인이라 새 태그가 걸립니다. 현재 우회가 자리에 있고 「지울 조건」이 달려 있습니다.
  2. 2
    api/platform_routes.py:1714 — 챔버 진행률 포트의 «폭».
    이것은 제가 판정할 수 없습니다. PR #132 의 장부가 「미해결로 남긴다 — 포트 주인의 판정이다」로 이미 등재해 뒀습니다. 다음 세션도 임의로 좁히지 마세요; 주인을 찾는 것이 먼저입니다.
  3. 3
    로컬과 CI 가 다른 답을 내는데 아무 데도 안 적혀 있습니다.
    이 기계에는 타입 검사기가 없어 pre-push 가 조용히 통과하고, CI 는 검사기를 함께 설치하므로 뒤에서 빨개집니다. CLAUDE.md 의 「오늘 거짓인 서술」 표 옆이 그 사실의 자리입니다. ⚠️ 이건 문서 한 줄이지만, 모르면 세션마다 같은 자리에서 놀랍니다.

셋 다 공통점이 있습니다 — 「여기서 못 고치는 이유」가 각각 다릅니다. ①은 다른 저장소라서, ②는 판정 권한이 없어서, ③은 코드가 아니라 문서라서입니다. 막힌 이유를 적지 않고 「나중에」로 두면 다음 사람이 같은 조사를 다시 합니다.

■ 함정 — 이번 세션이 실제로 밟은 것
    · 형제가 「이 줄은 손대지 마라」고 하면 그 줄 번호는 «그쪽 기저»의 것이다.
      내 트리의 같은 번호를 열어 보고 「무접촉」이라 답했는데 이미 고친 뒤였다.
      좌표는 «원문»으로 되찾아라: git show <그쪽기저>:<파일> | sed -n 'N,Mp'
    · 「지금 없다/있다」를 주석·태그 메시지에 적지 마라. 사실이 움직여도 조용하다.
      포함 관계로 적어라 — 「그 태그가 없어서」가 아니라 「그것이 이 판을 안 담아서」.
    · 버전 봉인은 «커밋 뒤»에만 답한다. 커밋 전 초록을 세 번 봐도 소용없다.
    · 열린 PR 의 브랜치 파일을 읽어 버전 번호 선점을 확인하라. 태그 목록만으로는
      「선언만 하고 태그가 없는」 번호를 못 본다. 같은 값을 쓰면 git 이 «조용히» 병합한다.
    · cast / # type: ignore 로 막지 마라 — 결함이 보존된 채 초록이 된다.
